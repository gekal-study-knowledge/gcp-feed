### What’s new in OKF v0.3: enterprise-ready knowledge, use cases, and skills

<details class="entry-summary">
<summary>詳細を表示</summary>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">In June we introduced the </span><a href="https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing"><span style="text-decoration: underline; vertical-align: baseline;">Open Knowledge Format (OKF)</span></a><span style="vertical-align: baseline;">, an open specification that provides plain markdown and YAML to give agents the context they need. In July, </span><a href="https://cloud.google.com/blog/products/data-analytics/okf-v0-2-adds-trust-signals"><span style="text-decoration: underline; vertical-align: baseline;">v0.2</span></a><span style="vertical-align: baseline;"> added trust signals: provenance, trust, freshness, lifecycle, and attestation.</span></p>
<p><span style="vertical-align: baseline;">In production, bundles move between organizations, multiple agents edit the same corpus, and independent tools need to read a bundle the same way. Released today, OKF v0.3</span><strong style="vertical-align: baseline;"> </strong><span style="vertical-align: baseline;">adds precise conformance rules, trust tiers that keep pace with agent edits, self-describing bundles with licensing, safe ways to retire and move knowledge, a stable extension model, and a clear versioning policy. However, the core idea behind OKF stays the same: </span><code style="vertical-align: baseline;">type</code><span style="vertical-align: baseline;"> is still the only required field, and your existing bundles keep working.</span></p>
<p><span style="vertical-align: baseline;">We're also launching </span><strong style="vertical-align: baseline;">OKF use cases</strong><span style="vertical-align: baseline;">, which are community guides for using OKF alongside other industry standards, and two </span><strong style="vertical-align: baseline;">agent skills</strong><span style="vertical-align: baseline;"> that let coding agents write and read OKF bundles. Finally, to make cross-organization collaboration easier, we’re moving OKF out of the Google Cloud Platform GitHub org into a standalone organization at </span><a href="https://github.com/open-knowledge-format/open-knowledge-format/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">https://github.com/open-knowledge-format/open-knowledge-format/</span></a><span style="vertical-align: baseline;">. </span></p>
<p><span style="vertical-align: baseline;">Let’s take a closer look at what’s new in OKF v0.3.</span></p>
<h3><span style="vertical-align: baseline;">Built for interoperability</span></h3>
<p><span style="vertical-align: baseline;">v0.3 adds a formal conformance section, allowing independent producers and consumers to work together by design. The spec is self-contained and uses RFC 2119 keywords. It gives one clear answer to the questions that come up when tools from different teams and vendors read the same bundle. The full detail is in the spec, but a few themes matter for anyone building on OKF:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Built on standard file formats.</strong><span style="vertical-align: baseline;"> OKF uses a small, widely supported set of standards: YAML 1.2 frontmatter, CommonMark with GFM tables and footnotes, and RFC 3339 timestamps. If your tools handle those, they handle OKF.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">OKF bundles share space with other markdown files.</strong><span style="vertical-align: baseline;"> A </span><code style="vertical-align: baseline;">.md</code><span style="vertical-align: baseline;"> file without a </span><code style="vertical-align: baseline;">type</code><span style="vertical-align: baseline;"> is skipped by OKF consumers, so </span><code style="vertical-align: baseline;">README.md</code><span style="vertical-align: baseline;">, </span><code style="vertical-align: baseline;">AGENTS.md</code><span style="vertical-align: baseline;">, </span><code style="vertical-align: baseline;">CONTRIBUTING.md</code><span style="vertical-align: baseline;">, and </span><code style="vertical-align: baseline;">SKILL.md</code><span style="vertical-align: baseline;"> can live inside a bundle without breaking it. Files that aren't markdown, like images or attester code, are </span><span style="font-style: italic; vertical-align: baseline;">assets</span><span style="vertical-align: baseline;"> that concepts can link to.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Consumers handle real-world input predictably.</strong><span style="vertical-align: baseline;"> Bundles written by many agents can contain nulls, empty strings, single values where a list was expected, and new vocabulary. v0.3 specifies how a consumer reads each of these. Consumers accept these inputs without failing, while validators log warnings for malformed entries. A bundle never fails because an optional field is missing or a link is broken.</span></p>
</li>
</ul>
<h4><span style="vertical-align: baseline;">Trust that keeps pace with agents</span></h4>
<p><span style="vertical-align: baseline;">v0.2 gave every concept a trust tier: </span><span style="font-style: italic; vertical-align: baseline;">unverified</span><span style="vertical-align: baseline;">, </span><span style="font-style: italic; vertical-align: baseline;">machine-confirmed</span><span style="vertical-align: baseline;">, or </span><span style="font-style: italic; vertical-align: baseline;">human-reviewed</span><span style="vertical-align: baseline;">. As agents take on more of the editing, v0.3 makes sure the tier always reflects the latest version of the content. Here's a typical sequence:</span></p>
<ol>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">A person reviews a metric definition and signs off.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">A week later, an agent refines the definition.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">The trust tier now reflects that the person hasn't yet reviewed the new text.</span></p>
</li>
</ol>
<p><span style="vertical-align: baseline;">In v0.3, </span><strong style="vertical-align: baseline;">only current verifications count</strong><span style="vertical-align: baseline;">. A verification is current when it happened at or after the last meaningful change to the content, recorded in </span><code style="vertical-align: baseline;">generated.at</code><span style="vertical-align: baseline;">:</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &#x27;generated: { by: reference_agent/gemini-2.5-pro, at: &quot;2026-09-02T10:00:00Z&quot; }\r\nverified:\r\n  - { by: &quot;human:jsmith&quot;, at: &quot;2026-08-25T09:00:00Z&quot; }        # before the rewrite: history\r\n  - { by: &quot;process:finance-nightly&quot;, at: &quot;2026-09-03T02:00:00Z&quot; }  # current&#x27;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f16a338cf90&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">This concept is now </span><strong style="vertical-align: baseline;">machine-confirmed</strong><span style="vertical-align: baseline;">, not human-reviewed, until a person confirms it again. The older sign-off stays in the file as history, and a UI can show it as "reviewed before the last change."</span></p>
<p><span style="vertical-align: baseline;">v0.3 also standardizes actor identifiers. Actors are </span><code style="vertical-align: baseline;">&lt;producer&gt;/&lt;version&gt;</code><span style="vertical-align: baseline;"> for tools, or </span><code style="vertical-align: baseline;">&lt;scheme&gt;:&lt;id&gt;</code><span style="vertical-align: baseline;"> for everything else, and v0.3 adds </span><code style="vertical-align: baseline;">team:</code><span style="vertical-align: baseline;"> next to </span><code style="vertical-align: baseline;">human:</code><span style="vertical-align: baseline;"> and </span><code style="vertical-align: baseline;">process:</code><span style="vertical-align: baseline;">. Only </span><code style="vertical-align: baseline;">human:</code><span style="vertical-align: baseline;"> earns human-reviewed, because a team name doesn't say which person actually checked the content.</span></p>
<h4><span style="vertical-align: baseline;">Bundles that describe themselves</span></h4>
<p><span style="vertical-align: baseline;">When an agent has access to dozens of bundles, bundle-level metadata supports progressive disclosure so it can pick the right bundle without reading every file. In v0.3, the bundle-root </span><code style="vertical-align: baseline;">index.md</code><span style="vertical-align: baseline;"> can carry frontmatter about the bundle itself:</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &#x27;---\r\nokf_version: &quot;0.3&quot;\r\ntitle: Acme retail analytics\r\ndescription: Tables, metrics, and sanctioned computations for Acme retail. Use it for sales and margin questions.\r\nlicense: CC-BY-4.0\r\n---&#x27;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f16a3419f90&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><ul>
<li style="vertical-align: baseline;">
<p><code><strong style="vertical-align: baseline;">description</strong></code><span style="vertical-align: baseline;"> is written for routing. In one sentence it says what the bundle covers and when to use it.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><code><strong style="vertical-align: baseline;">license</strong></code><span style="vertical-align: baseline;"> makes clear what you're allowed to do with knowledge you receive from someone else.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><code><strong style="vertical-align: baseline;">okf_version</strong></code><span style="vertical-align: baseline;"> tells a consumer which rules to apply, including compatibility fallbacks for older bundles.</span></p>
</li>
</ul>
<p><span style="vertical-align: baseline;">Tools that regenerate </span><code style="vertical-align: baseline;">index.md</code><span style="vertical-align: baseline;"> must keep this frontmatter.</span></p>
<h4><span style="vertical-align: baseline;">A lifecycle with forwarding addresses</span></h4>
<p><span style="vertical-align: baseline;">Knowledge evolves, and an agent that finds a deprecated concept should be able to get to its replacement. v0.3 adds </span><code style="vertical-align: baseline;">superseded_by</code><span style="vertical-align: baseline;">:</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &#x27;status: deprecated\r\nsuperseded_by: /metrics/gross-margin.md&#x27;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f16a3418210&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">Consumers that filter to current knowledge follow the pointer and return the replacement. The same mechanism handles moves and renames. Leave a short deprecated concept at the old path that points to the new one, and existing links and stored references keep working.</span></p>
<h4><span style="vertical-align: baseline;">One rule for links and paths</span></h4>
<p><span style="vertical-align: baseline;">Links in the body and path fields in frontmatter (</span><code style="vertical-align: baseline;">resource</code><span style="vertical-align: baseline;">, </span><code style="vertical-align: baseline;">superseded_by</code><span style="vertical-align: baseline;">, </span><code style="vertical-align: baseline;">executor.resource</code><span style="vertical-align: baseline;">, and others) now resolve the same way:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">A value with a scheme (</span><code style="vertical-align: baseline;">https:</code><span style="vertical-align: baseline;">) is an absolute URL.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">A value that starts with </span><code style="vertical-align: baseline;">/</code><span style="vertical-align: baseline;"> resolves from the bundle root.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">Anything else resolves from the directory of the file that contains it, just like on GitHub or in any markdown editor.</span></p>
</li>
</ul>
<p><span style="vertical-align: baseline;">For bundles marked v0.2 or earlier, or with no version, a consumer can also resolve paths from the bundle root, so existing bundles keep working.</span></p>
<p><span style="vertical-align: baseline;">v0.3 also makes explicit that </span><strong style="vertical-align: baseline;">links are not parent/child relationships.</strong><span style="vertical-align: baseline;"> Only the directory tree defines hierarchy. A link is an untyped, directed relationship, and the text around it says what kind ("joins with," "replaces," "depends on"). Path fields that point at concepts are edges in the bundle graph too.</span></p>
<h4><span style="vertical-align: baseline;">Room to extend, without collisions</span></h4>
<p><span style="vertical-align: baseline;">The community has been extending OKF since v0.1, with typed edges, routing hints, and erasure profiles. v0.3 makes a few extension mechanisms a first-class rule:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">Extension keys are allowed </span><strong style="vertical-align: baseline;">at any level</strong><span style="vertical-align: baseline;">, including inside </span><code style="vertical-align: baseline;">sources</code><span style="vertical-align: baseline;"> entries, </span><code style="vertical-align: baseline;">verified</code><span style="vertical-align: baseline;"> events, </span><code style="vertical-align: baseline;">executor</code><span style="vertical-align: baseline;">, and </span><code style="vertical-align: baseline;">attester</code><span style="vertical-align: baseline;">.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">A producer that edits a file </span><strong style="vertical-align: baseline;">must keep the keys it doesn't understand</strong><span style="vertical-align: baseline;"> so one tool doesn't overwrite metadata added by another.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">Future OKF versions </span><strong style="vertical-align: baseline;">will never define keys that start with </strong><strong style="vertical-align: baseline;">x-</strong><span style="vertical-align: baseline;">. Name your keys </span><code style="vertical-align: baseline;">x-&lt;producer&gt;-&lt;name&gt;</code><span style="vertical-align: baseline;">, for example </span><code style="vertical-align: baseline;">x-acme-owner</code><span style="vertical-align: baseline;">, and they won't collide with a future spec version.</span></p>
</li>
</ul>
<h4><span style="vertical-align: baseline;">A versioning policy before 1.0</span></h4>
<p><span style="vertical-align: baseline;">v0.3 defines OKF's versioning rules. Before 1.0, minor versions may include breaking changes as long as each is documented with a consumer fallback where possible. Starting at 1.0, minor versions will be strictly additive, and released normative text will not change in place.</span></p>
<p><span style="vertical-align: baseline;">The spec also lists what was </span><strong style="vertical-align: baseline;">considered and deferred</strong><span style="vertical-align: baseline;">: typed relationships, the full attestation runtime protocol (receipt and verdict wire formats), semantic-layer attestation, validity windows, and a </span><code style="vertical-align: baseline;">refuted</code><span style="vertical-align: baseline;"> verification event. Until the community agrees on a form for these, extension keys are the place to experiment. We'd like your proposals.</span></p>
<h3><span style="vertical-align: baseline;">Introducing OKF use cases</span></h3>
<p><span style="vertical-align: baseline;">OKF keeps its core specification small and links to existing domain schemas like Avro, Protobuf, or OpenAPI instead of duplicating them. In practice, though, when your organization already has an established artifact in another standard, such as a schema, a contract, or a spec, what should the OKF concept next to it say, and how should an agent use the two together?</span></p>
<p><span style="vertical-align: baseline;">Starting with v0.3, we're publishing </span><strong style="vertical-align: baseline;">use cases</strong><span style="vertical-align: baseline;">: guides for using OKF with other industry standards. Each one explains:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Where the boundary sits</strong><span style="vertical-align: baseline;">: what belongs in the other standard and what belongs in OKF.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">How to link the two</strong><span style="vertical-align: baseline;">: which frontmatter and link conventions point from a concept into the other artifact.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">What an agent should do</strong><span style="vertical-align: baseline;"> with the combination.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">A complete worked example</strong><span style="vertical-align: baseline;"> you can copy.</span></p>
</li>
</ul>
<p><span style="vertical-align: baseline;">Use cases are layered on the core spec, not part of it. A bundle that ignores them is still a conformant OKF bundle. When a convention proves itself across several use cases, it can be proposed for the core spec through the usual process.</span></p>
<p><span style="vertical-align: baseline;">Use cases are managed directly in GitHub. Each use case gets its own folder under </span><a href="https://github.com/open-knowledge-format/open-knowledge-format/tree/main/usecases" rel="noopener" target="_blank"><code style="text-decoration: underline; vertical-align: baseline;">usecases/</code></a><span style="vertical-align: baseline;"> in the OKF repository, for example </span><code style="vertical-align: baseline;">usecases/&lt;usecase&gt;/</code><span style="vertical-align: baseline;">. The guide is a </span><code style="vertical-align: baseline;">.md</code><span style="vertical-align: baseline;"> file in that folder, and any sample bundles or artifacts sit next to it. Use cases are reviewed, versioned, and discussed like any other change.</span></p>
<h4><span style="vertical-align: baseline;">Propose a use case</span></h4>
<p><span style="vertical-align: baseline;">If you pair OKF with a standard, please send us a proposal. A rough first draft is welcome. Open a pull request that adds a folder under </span><code style="vertical-align: baseline;">usecases/</code><span style="vertical-align: baseline;"> with a </span><code style="vertical-align: baseline;">.md</code><span style="vertical-align: baseline;"> file in it, and we'll refine it together in review.</span></p>
<h3><span style="vertical-align: baseline;">Compatibility</span></h3>
<p><span style="vertical-align: baseline;">v0.3 has two breaking changes, and existing v0.2 bundles stay readable:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Path fields resolve relative to their file.</strong><span style="vertical-align: baseline;"> Fallback: for bundles marked v0.2 or earlier, or with no version, consumers can resolve from the bundle root.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Only current verifications count toward the trust tier.</strong><span style="vertical-align: baseline;"> No fallback needed, since tiers can only go down.</span></p>
</li>
</ul>
<p><span style="vertical-align: baseline;">Everything else is a clarification or an optional addition. v0.1 fallbacks (</span><code style="vertical-align: baseline;">timestamp</code><span style="vertical-align: baseline;">, body </span><code style="vertical-align: baseline;"># Citations</code><span style="vertical-align: baseline;">) still apply.</span></p>
<h3><span style="vertical-align: baseline;">Agent skills for OKF</span></h3>
<p><span style="vertical-align: baseline;">The two skills live in the new repository and follow the open </span><a href="https://agentskills.io/specification" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Agent Skills</span></a><span style="vertical-align: baseline;"> format, so any agent that supports skills can load them.</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">okf-generate</strong><span style="vertical-align: baseline;"> writes, updates, migrates, and validates bundles from available sources. It cites a source for each claim, records a human review only when that person confirms it, and copies attested computations from a sanctioned source instead of writing them.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">okf-consume</strong><span style="vertical-align: baseline;"> answers questions from a bundle. For each concept used, it reports the trust tier, status, freshness, and attestation result, and runs attested computations only through the bundle's configured executor and attester.</span></p>
</li>
</ul>

### Testing changes, fast: Introducing agentic assessments in Database Center

- **Link**: [https://cloud.google.com/blog/products/databases/database-center-assessments-for-cloud-sql-for-postgresql/](https://cloud.google.com/blog/products/databases/database-center-assessments-for-cloud-sql-for-postgresql/)
- **Published**: 2026-11-19 02:00:00
- **Fetched**: 2026-11-19 07:50:49

<details class="entry-summary">
<summary>詳細を表示</summary>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">Applying recommendations to a production database can feel risky if you can’t easily quantify the performance benefit or justify the additional cost. While </span><a href="https://docs.cloud.google.com/database-center/docs/overview"><span style="text-decoration: underline; vertical-align: baseline;">Database Center</span></a><span style="vertical-align: baseline;"> flags fleet-level health issues and provides proactive recommendations, database administrators still face the challenge of testing recommended changes without disrupting live applications or spending hours manually configuring staging replicas. </span></p>
<p><span style="vertical-align: baseline;">To help solve this problem, we’re excited to announce the preview of </span><a href="https://docs.cloud.google.com/sql/docs/postgres/assessments-overview"><span style="text-decoration: underline; vertical-align: baseline;">assessments in Database Center for Cloud SQL for PostgreSQL</span></a><span style="vertical-align: baseline;">. Assessments is an agentic workflow that lets you run automated, isolated synthetic benchmarks on cloned instances, helping you verify potential performance gains before touching your production environment.</span></p>
<h3><strong style="vertical-align: baseline;">Moving from recommendations to production changes</strong></h3>
<p><span style="vertical-align: baseline;">Managing production databases means balancing system stability, performance, and infrastructure spend. When Database Center alerts you to a potential bottleneck and recommends a change, you need to evaluate the change before you can implement it. That workflow can be complex:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">Setting up dedicated staging environments to mirror production settings</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">Running benchmark workloads to simulate real-world traffic</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">Measuring latency, throughput, and resource saturation before and after applying changes</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">Calculating whether performance gains justify potential cost adjustments</span></p>
</li>
</ul>
<p><span style="vertical-align: baseline;">Because this manual benchmarking process takes a lot of time and engineering effort, it’s easy to put off making critical updates, leaving databases under-provisioned or inefficient.</span></p>
<h3><strong style="vertical-align: baseline;">How assessments automates the validation workflow</strong></h3>
<p><span style="vertical-align: baseline;">Assessments simplify performance validation by automating the entire testing cycle in an isolated environment. When you click "Assess impact" on a supported recommendation in Database Center, the assessments workflow handles each step of the benchmarking process:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Plan creation:</strong><span style="vertical-align: baseline;"> Assessments builds a customized test plan for running a synthetic benchmark tailored to your instance. You can refine parameters such as client connections, transaction counts, query mode, or benchmark duration using plain-language prompts to match your target workload requirements </span><strong style="vertical-align: baseline;">(for example, </strong><strong style="font-style: italic; vertical-align: baseline;">"Change the benchmark duration to 60 seconds"</strong><strong style="vertical-align: baseline;">).</strong></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Safe isolation:</strong><span style="vertical-align: baseline;"> The agentic workflow clones your primary instance so that benchmarks run without consuming production resources or affecting live traffic.</span></p>
</li>

### Sashiko: Lessons from building an agentic code review system for Linux

- **Link**: [https://cloud.google.com/blog/products/application-development/lessons-from-building-sashiko-an-agentic-code-review-system/](https://cloud.google.com/blog/products/application-development/lessons-from-building-sashiko-an-agentic-code-review-system/)
- **Published**: 2026-11-19 02:00:00
- **Fetched**: 2026-11-19 07:50:49

<details class="entry-summary">
<summary>詳細を表示</summary>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">The speed of development in large open-source projects has always been limited by code review, not code generation. Even as coding agents get better at writing code, they do not accelerate development on their own. This is especially true of patches to the Linux kernel. Without a way to build trust in proposed changes, more generated code simply piles up in front of the same small group of human maintainers. Some of those patches are solid changes, just written faster; many others are plausible-looking "AI slop" sent by contributors who do not fully understand the systems they are modifying. And the influx of AI-generated security reports, many of which are duplicates or inaccurate, only adds to maintainers’ load.</span></p>
<p><span style="vertical-align: baseline;">Linux runs billions of Android phones, most cloud providers, and nearly every supercomputer. It spans more than 35 million lines of code, and over 85,000 changes land every year. Automated build bots and fuzzers like </span><a href="https://github.com/google/syzkaller" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Syzkaller</span></a><span style="vertical-align: baseline;"> catch build errors and crashes, but code review has always been the main way to guarantee the stability and safety of the kernel. Every day, maintainers read hundreds and hundreds of proposed patches by hand to catch memory leaks, deadlocks, race conditions, and security bugs.</span></p></div>

      <p>To help maintainers handle the load and catch bugs before they land, the <a href="http://aiinfra.google/">Google AI &amp; Infrastructure</a> team built <a href="https://github.com/sashiko-dev/sashiko"><b>Sashiko</b></a>, an open-source, agentic code review system powered by Gemini. We named the project after the Japanese word 刺し子, a stitching technique for artistically reinforcing worn cloth, and donated it to the Linux Foundation earlier this year.</p><p>In this blog, we cover the problem Sashiko was designed to solve, how it works, what the data shows, and what we learned from building and running it in the wild.</p><h3><b>Reviewing code is hard</b></h3><p>Reviewing a change in a complex code base is objectively hard, both for humans and LLMs. It often requires a deep understanding of how the system works in general, well outside the proposed change. In fact, it’s pretty common to see patches that engineers claim perfectly solve the problem, but if they were to be merged, would actually introduce even worse problems (albeit subtle). Traditionally, only experienced maintainers have been able to spot and prevent these issues. The same is true for agentically generated code.</p><p>To verify the correctness of a change, a potentially large number of invariants should be proven, which is often a much larger and harder task than developing the change itself. This is true for both human and agentic reviewers. However, LLM-based reviewers have some unique properties, both positive and negative:</p><ol><li><b>LLMs often struggle to put in enough effort.</b> LLMs are trained to achieve the goal of spending fewer tokens. So they often tend to cut corners and dismiss concerns without proper investigation or flag false positives without proper due diligence.</li><li><b>LLMs are easier to bias</b>. The current generation of LLMs usually performs much better if provided a single relatively simple task (e.g., prove the patch for memory leaks) rather than multiple tasks (e.g., explore several complex, varied concerns). It’s pretty common for an LLM to find an obvious issue in the code and refuse to look deeper for other types of issues. Also, commit log text can sometimes affect the result of code review in a non-predicatable or even malicious way.</li><li><b>LLMs don’t have persistent memory.</b> Surprisingly, this is a positive thing for code review: An LLM can review the same or similar patch multiple times as if it were a new patch. No sane human can review the same patch applied to 100 slightly different branches to find the few that have incompatible changes.</li></ol><h3><b>How Sashiko reviews a patch</b></h3><p>To avoid these failure modes, Sashiko separates <b>finding candidate bugs</b> from <b>verification of those bugs</b>, and requires each pass to record what it ruled out:</p>
    </div>
  </div>
</div>

</div>

<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">Notes on each step:</span></p>
<ol>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Gather context and plan:</strong><span style="vertical-align: baseline;"> Sashiko first pulls in the code around the diff (modified functions, struct definitions, and direct callers) and loads the subsystem's domain guides, so the changed lines are never judged in isolation. A planner then decides which specialist passes are needed (skipping hardware checks on pure software code, for example) and sets a reasoning budget for each pass based on patch complexity.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Parallel specialist sessions:</strong><span style="vertical-align: baseline;"> Up to seven specialist sessions run in parallel, each focused on a single class of problems: commit intent, implementation match, control flow, resource lifetimes, locking, security, and hardware. Giving each pass a single focus prevents one type of bug from crowding out another. Each session searches and reads the repository with git tools (averaging about 100 tool calls per review) and outputs two lists: concerns it believes are real, and candidate concerns it investigated and ruled out, along with the code that supports that conclusion.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Triage:</strong><span style="vertical-align: baseline;"> A lead verifier audits those two lists together. Clear-cut bugs already proven by the code in front of it pass straight through; dismissals proven by a local check are dropped. Everything else deserves additional investigation. Crucially, that includes not only contested bugs where specialists disagreed, but also </span><strong style="vertical-align: baseline;">shaky self-dismissals </strong><span style="vertical-align: baseline;">— cases where a specialist spotted a real bug and dismissed it by assuming, without proof, that some unseen caller or lock would prevent it.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Per-bug deep checks:</strong><span style="vertical-align: baseline;"> Instead of checking all difficult cases in one shared prompt, Sashiko gives each difficult case its own verification agent that runs in parallel. Each agent gets one specific question to answer with git tools under a symmetrical rule: Neither a bug claim nor a dismissal is accepted without concrete code proof across </span><span style="font-style: italic; vertical-align: baseline;">all</span><span style="vertical-align: baseline;"> call sites. If a specialist talks itself out of a real bug based on a false assumption, this step catches it and promotes it back to a real finding.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Review report: </strong><span style="vertical-align: baseline;">Sashiko generates a report that sounds like a human maintainer asking questions about the proposed change, matching the style expected on a Linux mailing list.</span></p>
</li>
</ol>
<p><span style="vertical-align: baseline;">All this happens at no cost for developers. Deep agentic reviews at scale require a substantial token budget. If developers had to pay for them with their own API keys, many important contributors would be pushed away. Instead, Sashiko reviews patches sent to public Linux kernel mailing lists, and Google runs the service at </span><a href="https://sashiko.dev" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">sashiko.dev</span></a><span style="vertical-align: baseline;">. Everything runs in the open: every prompt, tool call, reasoning step, and ruled-out bug is public. The project initially used the open-source Linux review prompts started by Chris Mason, and more than 100 contributors, including prominent kernel maintainers and engineers, have since helped to improve prompts and Sashiko itself. Recently, Sashiko switched to a different prompt system that combines per-tree or per-version auto-generated notes on code with subjective maintainers notes, which contain directions and instructions from maintainers that can’t be derived from the code.</span></p>
<h3><strong style="vertical-align: baseline;">What the data shows</strong></h3>
<p><span style="vertical-align: baseline;">The real test of an automated reviewer is whether maintainers pay attention to the reports it sends out, and whether those reports track actual software quality. Seven months of Sashiko production data from the kernel mailing lists give a clear picture of both these questions.</span></p>
<p><strong style="vertical-align: baseline;">It is part of the daily workflow.</strong><span style="vertical-align: baseline;"> Sashiko completes roughly 1200 reviews a day across over 100 kernel mailing lists. It sends review emails only to lists whose maintainers opt in, and already over 70 of them have done so. Developers also engage directly with the reports: More than 1500 kernel developers have replied on the mailing lists, and their pushback on false alarms has directly driven improvements to Sashiko's prompts and verification engine. In fact, </span><a href="http://lwn.net" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">LWN.net</span></a><span style="vertical-align: baseline;"> recently </span><a href="https://lwn.net/Articles/1096963/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">wrote</span></a><span style="vertical-align: baseline;"> that </span><strong style="vertical-align: baseline;">Sashiko has already become an important part of the kernel's development process</strong><span style="vertical-align: baseline;"> and was </span><a href="https://lwn.net/Articles/1100241/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">the top bug reporter</span></a><span style="vertical-align: baseline;"> of issues in the 7.2 release cycle.</span></p>
<p><strong style="vertical-align: baseline;">It prevents new bugs and uncovers old ones.</strong><span style="vertical-align: baseline;"> When Sashiko flags a bug in a proposed patch, the author typically fixes it in the next revision before the change is ever merged. Many developers run Sashiko locally or in corporate private instances. The bugs that Sashiko helped to prevent leave no trace in the git commit log, making them hard to count directly. What </span><span style="font-style: italic; vertical-align: baseline;">can</span><span style="vertical-align: baseline;"> be counted are fixes for preexisting bugs that Sashiko finds and reports as a byproduct of reviewing new changes: Sashiko is cited in over 2000 mainline kernel commits and in over 500 of this year's official Linux kernel CVEs, spanning drivers, core kernel code, networking, GPUs, memory management, and virtualization.</span></p>
<p><strong style="vertical-align: baseline;">Fewer bugs are slipping into mainline releases.</strong><span style="vertical-align: baseline;"> Across the 18 kernel releases prior to Sashiko (Linux 6.2 through 6.19, covering 254000 commits), an average of 3.4% of merged commits required a follow-up fix within 60 days. Since Sashiko rolled out, that 60-day fix rate has fallen to 2.8% in Linux 7.1 and 2.2% in Linux 7.2, </span><strong style="vertical-align: baseline;">a 35% drop</strong><span style="vertical-align: baseline;"> (with the 30-day fix rate falling from 2.3% to 1.4%). It’s too early to make strong claims, and obviously many other factors can influence release-to-release numbers, so we cannot solely credit Sashiko for the entire drop, but the trend is optimistic.</span></p></div>

<h3><strong style="vertical-align: baseline;">What we learned from building and running Sashiko</strong></h3>
<p><span style="vertical-align: baseline;">First, </span><strong style="vertical-align: baseline;">benchmark-driven development beats intuition.</strong><span style="vertical-align: baseline;"> While developing Sashiko, we tried many ideas that looked very reasonable on their face but didn’t end up working out. Other ideas were less obvious but worked surprisingly well. What was crucial: Early on, we built a benchmark out of nearly 1,000 real Linux kernel bugs and used it to evaluate every major Sashiko change. Every bug in this set was a real mistake that had passed human review by kernel experts, had been merged into mainline Linux, and later had to be fixed. On that benchmark, Sashiko with the new </span><strong style="vertical-align: baseline;">Gemini 4 Carbon</strong><span style="vertical-align: baseline;"> model catches </span><strong style="vertical-align: baseline;">75.8%</strong><span style="vertical-align: baseline;"> of the bugs that human reviewers missed (using high thinking level).</span></p>
<p><span style="vertical-align: baseline;">Second, </span><strong style="vertical-align: baseline;">coding agents are not great at reviewing their own code.</strong><span style="vertical-align: baseline;"> Models are trained to produce a working solution within a limited token budget. Asking these agents to review their own code might work well for isolated tasks, but for real, large codebases, creating a functional solution is often just 5-10% of the work. What’s really hard is to produce a solution that works all of the time, is well-integrated into the surrounding code, and doesn’t introduce subtle regressions. This is often substantially more complex and requires additional effort. Similar to human developers, agents benefit from external code review: Reviewers often spot issues that the initial author missed, even if they are not more experienced.</span></p>
<p><span style="vertical-align: baseline;">Third, </span><strong style="vertical-align: baseline;">open source and shared community ownership and development help to build trust.</strong><span style="vertical-align: baseline;"> By being fully open and transparent from the <span style="vertical-align: baseline;">beginning</span>, Sashiko allowed anyone to run it the way they wanted: using different models (including open source and local models), customizing prompts, or even adopting Sashiko to other-than-Linux projects. This helped with community adoption and brought over 100 contributors to improve Sashiko, including some prominent kernel developers.</span></p>
<p><span style="vertical-align: baseline;">More and more engineers are putting local Sashiko instances into their coding-agent loops, so patches are checked against the community's review rules before a human maintainer ever sees them. We use the same workflow to build Sashiko itself ("Sashiko for Sashiko"), running it to review every change to its codebase and prompt pipeline both locally and through a Github integration.</span></p>
<p><span style="vertical-align: baseline;">Although Sashiko started in the Linux kernel, the need for an agentic trust layer applies across critical open-source software. Because the core review engine does not depend on C or on kernel-specific rules, the Linux kernel playbook (combining an open verification pipeline, community-owned domain guides, and a benchmark mined from historically known issues and fixes) can likely be applied to other foundational open-source projects such as GCC, LLVM, or Git.</span></p>
<p style="padding-left: 40px;"><span style="font-style: italic; vertical-align: baseline;">"Now, I think the other side of AI - and this is where Sashiko comes in - is that it basically does end up being a tool that can then increase the trust in the patch. So AI giveth, and AI taketh away. But the basic issue shouldn't be AI per se, it should be that notion of 'trust'." - </span><strong style="vertical-align: baseline;">Linus Torvalds</strong><span style="vertical-align: baseline;"> </span><a href="https://lore.kernel.org/all/CAHk-=wgbGarE7Ozw4VG6oUKDj9pk-8DRoDiX00bo1MwEMm9UWQ@mail.gmail.com/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">on LKML</span></a></p>

<div class="block-paragraph_advanced"><h3><span style="vertical-align: baseline;">Why autonomous agents challenge traditional L7 proxies</span></h3>
<p><span style="vertical-align: baseline;">Over the past decade, Envoy became the industry standard for cloud-native traffic management by operating cleanly at </span><strong style="vertical-align: baseline;">Layer 4</strong><span style="vertical-align: baseline;"> (TCP/UDP connection management) and </span><strong style="vertical-align: baseline;">Layer 7</strong><span style="vertical-align: baseline;"> (URI, method, and header-based routing).</span></p>
<p><span style="vertical-align: baseline;">Autonomous agents introduce two higher-order protocol layers:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Layer 8 (agentic interaction protocols):</strong><span style="vertical-align: baseline;"> such as </span><strong style="vertical-align: baseline;">LLM APIs</strong><span style="vertical-align: baseline;">, Anthropic’s </span><strong style="vertical-align: baseline;">Model Context Protocol (MCP)</strong><span style="vertical-align: baseline;"> and Google’s </span><strong style="vertical-align: baseline;">Agent2Agent (A2A)</strong><span style="vertical-align: baseline;">, running over JSON-RPC 2.0 or gRPC. Critical policy attributes—such as </span><code style="vertical-align: baseline;">tools/call</code><span style="vertical-align: baseline;">, </span><code style="vertical-align: baseline;">tool_name: "execute_sql"</code><span style="vertical-align: baseline;">, or </span><code style="vertical-align: baseline;">model: "gemini-1.5-pro"</code><span style="vertical-align: baseline;">—are serialized inside the request payload.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Layer 9 (agent framework interfaces):</strong><span style="vertical-align: baseline;"> Coordination frameworks such as UCP, AP2, and Google Cloud’s Agent Development Kit, where multi-turn workflows produce dynamic token consumption and non-linear execution graphs.</span></p>
</li>
</ul>
<p><span style="vertical-align: baseline;">Fronting these workloads with traditional L7 proxies creates four major architectural challenges:</span></p>
<ol>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Payload blindness:</strong><span style="vertical-align: baseline;"> Nearly all LLM traffic shares the same paths (such as </span><code style="vertical-align: baseline;">/v1/chat/completions</code><span style="vertical-align: baseline;">), so a header-based proxy cannot distinguish between a low-cost query and an expensive 500,000-token prompt, or one model from another.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Request rate limiting fallacy:</strong><span style="vertical-align: baseline;"> One request  per minute with a massive context window can use  more accelerator compute and memory bandwidth than dozens of  short queries, and agent loops can burn through budgets unnoticed.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Stateless load balancing: </strong><span style="vertical-align: baseline;">Each turn of an agent's conversation should go back to the server that already remembers it. Traditional load balancers send it to whichever server is next, so the model has to start over for every turn, this wastes time and GPUs.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Ungoverned tool execution:</strong><span style="vertical-align: baseline;"> Agents query databases, execute code in sandboxes, and call third-party APIs. Without inline inspection of MCP tool  calls, organizations risk prompt injection, data exfiltration, and runaway billing loops.</span></p>
</li>
</ol>

<h4><span style="vertical-align: baseline;">1. Native wire-format body parsing and transcoding</span></h4>
<p style="text-align: justify;"><span style="vertical-align: baseline;">Client applications often get locked into specific model APIs. For example, client code built for OpenAI's schema cannot communicate with Anthropic's endpoints or Google’s Gemini without client-side translation layers.</span></p>
<p><span style="vertical-align: baseline;">To help, Envoy ecosystem includes native body parsers that normalize requests across diverse model families, providing:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Client abstraction:</strong><span style="vertical-align: baseline;"> Upstream applications send a standardized schema. Envoy inspects the JSON payload at line-rate, extracts the target model, and dynamically transcodes the request into the downstream provider's native format.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">No application code changes:</strong><span style="vertical-align: baseline;"> Switching from an external commercial model to a self-hosted open-source model (such as Gemma or Llama on vLLM) requires only an Envoy configuration update. Application code remains unchanged.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Streaming token extraction:</strong><span style="vertical-align: baseline;"> Envoy parses server-sent events (SSE) response streams in real time, capturing token counts from usage chunks while maintaining ultra-low time-to-first-token latency.</span></p>
</li>
</ul>
<h4><span style="vertical-align: baseline;">2. Tokenomics engine: token-aware traffic management</span></h4>
<p><span style="vertical-align: baseline;">In AI networking, </span><strong style="vertical-align: baseline;">tokens are the fundamental unit of capacity</strong><span style="vertical-align: baseline;">. Envoy replaces coarse request counters with token-aware traffic management features such as:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Token rate limiting:</strong><span style="vertical-align: baseline;"> Enforces tokens per minute (TPM) and tokens per day (TPD) limits per tenant, project, or model.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Pre-inference throttling:</strong><span style="vertical-align: baseline;"> Envoy estimates input tokens from request payload bytes and extracts actual token usage from LLM responses to record in a quota database, rejecting subsequent over-quota requests with an HTTP </span><code style="vertical-align: baseline;">429</code><span style="vertical-align: baseline;"> before they reach the inference cluster.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Runaway loop protection:</strong><span style="vertical-align: baseline;"> Autonomous agents can enter recursive reasoning loops. By tracking cumulative token consumption and message counts per session or agent ID, Envoy throttles multi-turn sessions once an agent exceeds its assigned budget.</span></p>
</li>
</ul>
<h4><span style="vertical-align: baseline;">3. Model routing and Model Context Protocol (MCP) support</span></h4>
<p><span style="vertical-align: baseline;">Envoy manages traffic for both downstream model backends and outbound tool calls, with:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">KV-cache prefix affinity:</strong><span style="vertical-align: baseline;"> Using the Kubernetes Gateway API Inference Extensions and Endpoint Picker (EPP), Envoy routes prompts sharing identical system instructions to the GPU worker currently holding that cache in memory, reducing latency.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Model retry and fallback:</strong><span style="vertical-align: baseline;"> If a primary model returns a 429 status code or fails, Envoy automatically retries or redirects the request to a secondary model pool with zero client interruption.</span></p>
</li>
<li style="vertical-align: baseline;">
<p style="text-align: justify;"><strong style="vertical-align: baseline;">MCP tool routing:</strong><span style="vertical-align: baseline;"> For MCP agents, Envoy routes requests via JSON-RPC 2.0 bodies and HTTP headers. Per the </span><a href="https://blog.modelcontextprotocol.io/posts/2026-07-28/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">2026-07-28 MCP specification</span></a><span style="vertical-align: baseline;">, Envoy uses </span><code style="vertical-align: baseline;">Mcp-Method</code><span style="vertical-align: baseline;"> and </span><code style="vertical-align: baseline;">Mcp-Name</code><span style="vertical-align: baseline;"> headers for zero-body-parsing routing to backend servers. Backends reject header-body mismatches with an HTTP </span><code style="vertical-align: baseline;">400</code><span style="vertical-align: baseline;"> / </span><code style="vertical-align: baseline;">-32020</code><span style="vertical-align: baseline;"> (HeaderMismatch) error to prevent tampering.</span></p>
</li>
</ul>
<h4><span style="vertical-align: baseline;">4. AI security guardrails </span></h4>
<p><span style="vertical-align: baseline;">Inline safety filtering cannot come at the expense of network throughput. To prevent this, Envoy provides </span><strong style="vertical-align: baseline;">security callouts:</strong><span style="vertical-align: baseline;"> Using standardized external processing (</span><code style="vertical-align: baseline;">ext_proc</code><span style="vertical-align: baseline;">), Envoy connects to dedicated policy decision engines — such as Google Cloud’s Model Armor, ShieldGemma, or local classifiers — to detect prompt injections and sensitive data leaks with minimal latency overhead.</span></p>
<h3><span style="vertical-align: baseline;">High-density infrastructure: Envoy and Agent Substrate</span></h3>
<p><span style="vertical-align: baseline;">In enterprise production environments, agents frequently spend time idle between user queries or long-running tool executions. Running hundreds of thousands of idle agents in dedicated containers or virtual machines can create prohibitive infrastructure costs.</span></p>
<p><span style="vertical-align: baseline;">Envoy pairs directly with high-density execution runtimes like </span><a href="https://github.com/agent-substrate/substrate" rel="noopener" target="_blank"><strong style="text-decoration: underline; vertical-align: baseline;">Agent Substrate</strong></a><span style="vertical-align: baseline;"> to provide:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Scale-to-zero traffic steering:</strong><span style="vertical-align: baseline;"> Agent Substrate uses lightweight isolation runtimes (such as Cloud Hypervisor, microVMs and gVisor application sandboxes) that can suspend and resume in milliseconds. When traffic arrives for a suspended agent, Envoy buffers the initial packet while signaling the runtime to resume the instance, completing the end-to-end resume in milliseconds.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Egress perimeter defense:</strong><span style="vertical-align: baseline;"> Envoy functions as both an ingress and egress gateway for agent environments, routing the inbound traffic and restricting outbound network calls to verified domains and preventing untrusted autonomous code from reaching unauthorized endpoints.</span></p>
</li>
</ul>

<p><strong style="vertical-align: baseline;">医療承認申請や異議申し立てを効率化:</strong><span style="vertical-align: baseline;"> カルテから必要な根拠情報を抽出し、監査対応可能な資料を審査用に作成します。これは保険会社の方針に準拠しており、却下された後ではなく、提出前に文書上の不備を指摘します。申請が却下された場合でも、根拠を裏付ける記録により、臨床記録と保険プランの方針に直接基づいた異議申し立ての下書きを作成します。</span></p>
</li>
</ul>
<p><strong style="vertical-align: baseline;">保険適用判断:</strong></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">保険会社の審査を迅速化:</strong><span style="vertical-align: baseline;"> 受領した申請内容を医療保険の医療方針と照合し、審査担当者向けに結果を整理します。判断根拠は提出された文書と保険適用方針まで追跡可能です。審査担当者は、情報収集に費やす時間を減らし、専門的な判断に充てる時間を増やすことができます。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">給付内容と患者の自己負担額を明確化:</strong><span style="vertical-align: baseline;"> 複雑な給付規定を解析し、自己負担額の見積もり、免責額の追跡、ネットワーク内医療機関の状況確認を行い、保険加入者の実際の契約内容に基づいて、サービス担当者に詳細な説明を提供します。Medicare Advantage の加入者については、保険プランの内部規則がより厳格な場合には、Medicare の給付基準を適用します。</span></p>
</li>
</ul>

<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">The speed of development in large open-source projects has always been limited by code review, not code generation. Even as coding agents get better at writing code, they do not accelerate development on their own. This is especially true of patches to the Linux kernel. Without a way to build trust in proposed changes, more generated code simply piles up in front of the same small group of human maintainers. Some of those patches are solid changes, just written faster; many others are plausible-looking "AI slop" sent by contributors who do not fully understand the systems they are modifying. And the influx of AI-generated security reports, many of which are duplicates or inaccurate, only adds to maintainers’ load.</span></p>
<p><span style="vertical-align: baseline;">Linux runs billions of Android phones, most cloud providers, and nearly every supercomputer. It spans more than 35 million lines of code, and over 85,000 changes land every year. Automated build bots and fuzzers like </span><a href="https://github.com/google/syzkaller" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Syzkaller</span></a><span style="vertical-align: baseline;"> catch build errors and crashes, but code review has always been the main way to guarantee the stability and safety of the kernel. Every day, maintainers read hundreds and hundreds of proposed patches by hand to catch memory leaks, deadlocks, race conditions, and security bugs.</span></p></div>

      <p>To help maintainers handle the load and catch bugs before they land, the <a href="http://aiinfra.google/">Google AI &amp; Infrastructure</a> team built <a href="https://github.com/sashiko-dev/sashiko"><b>Sashiko</b></a>, an open-source, agentic code review system powered by Gemini. We named the project after the Japanese word 刺し子, a stitching technique for artistically reinforcing worn cloth, and donated it to the Linux Foundation earlier this year.</p><p>In this blog, we cover the problem Sashiko was designed to solve, how it works, what the data shows, and what we learned from building and running it in the wild.</p><h3><b>Reviewing code is hard</b></h3><p>Reviewing a change in a complex code base is objectively hard, both for humans and LLMs. It often requires a deep understanding of how the system works in general, well outside the proposed change. In fact, it’s pretty common to see patches that engineers claim perfectly solve the problem, but if they were to be merged, would actually introduce even worse problems (albeit subtle). Traditionally, only experienced maintainers have been able to spot and prevent these issues. The same is true for agentically generated code.</p><p>To verify the correctness of a change, a potentially large number of invariants should be proven, which is often a much larger and harder task than developing the change itself. This is true for both human and agentic reviewers. However, LLM-based reviewers have some unique properties, both positive and negative:</p><ol><li><b>LLMs often struggle to put in enough effort.</b> LLMs are trained to achieve the goal of spending fewer tokens. So they often tend to cut corners and dismiss concerns without proper investigation or flag false positives without proper due diligence.</li><li><b>LLMs are easier to bias</b>. The current generation of LLMs usually performs much better if provided a single relatively simple task (e.g., prove the patch for memory leaks) rather than multiple tasks (e.g., explore several complex, varied concerns). It’s pretty common for an LLM to find an obvious issue in the code and refuse to look deeper for other types of issues. Also, commit log text can sometimes affect the result of code review in a non-predicatable or even malicious way.</li><li><b>LLMs don’t have persistent memory.</b> Surprisingly, this is a positive thing for code review: An LLM can review the same or similar patch multiple times as if it were a new patch. No sane human can review the same patch applied to 100 slightly different branches to find the few that have incompatible changes.</li></ol><h3><b>How Sashiko reviews a patch</b></h3><p>To avoid these failure modes, Sashiko separates <b>finding candidate bugs</b> from <b>verification of those bugs</b>, and requires each pass to record what it ruled out:</p>

<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">Notes on each step:</span></p>
<ol>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Gather context and plan:</strong><span style="vertical-align: baseline;"> Sashiko first pulls in the code around the diff (modified functions, struct definitions, and direct callers) and loads the subsystem's domain guides, so the changed lines are never judged in isolation. A planner then decides which specialist passes are needed (skipping hardware checks on pure software code, for example) and sets a reasoning budget for each pass based on patch complexity.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Parallel specialist sessions:</strong><span style="vertical-align: baseline;"> Up to seven specialist sessions run in parallel, each focused on a single class of problems: commit intent, implementation match, control flow, resource lifetimes, locking, security, and hardware. Giving each pass a single focus prevents one type of bug from crowding out another. Each session searches and reads the repository with git tools (averaging about 100 tool calls per review) and outputs two lists: concerns it believes are real, and candidate concerns it investigated and ruled out, along with the code that supports that conclusion.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Triage:</strong><span style="vertical-align: baseline;"> A lead verifier audits those two lists together. Clear-cut bugs already proven by the code in front of it pass straight through; dismissals proven by a local check are dropped. Everything else deserves additional investigation. Crucially, that includes not only contested bugs where specialists disagreed, but also </span><strong style="vertical-align: baseline;">shaky self-dismissals </strong><span style="vertical-align: baseline;">— cases where a specialist spotted a real bug and dismissed it by assuming, without proof, that some unseen caller or lock would prevent it.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Per-bug deep checks:</strong><span style="vertical-align: baseline;"> Instead of checking all difficult cases in one shared prompt, Sashiko gives each difficult case its own verification agent that runs in parallel. Each agent gets one specific question to answer with git tools under a symmetrical rule: Neither a bug claim nor a dismissal is accepted without concrete code proof across </span><span style="font-style: italic; vertical-align: baseline;">all</span><span style="vertical-align: baseline;"> call sites. If a specialist talks itself out of a real bug based on a false assumption, this step catches it and promotes it back to a real finding.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Review report: </strong><span style="vertical-align: baseline;">Sashiko generates a report that sounds like a human maintainer asking questions about the proposed change, matching the style expected on a Linux mailing list.</span></p>
</li>
</ol>
<p><span style="vertical-align: baseline;">All this happens at no cost for developers. Deep agentic reviews at scale require a substantial token budget. If developers had to pay for them with their own API keys, many important contributors would be pushed away. Instead, Sashiko reviews patches sent to public Linux kernel mailing lists, and Google runs the service at </span><a href="https://sashiko.dev" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">sashiko.dev</span></a><span style="vertical-align: baseline;">. Everything runs in the open: every prompt, tool call, reasoning step, and ruled-out bug is public. The project initially used the open-source Linux review prompts started by Chris Mason, and more than 100 contributors, including prominent kernel maintainers and engineers, have since helped to improve prompts and Sashiko itself. Recently, Sashiko switched to a different prompt system that combines per-tree or per-version auto-generated notes on code with subjective maintainers notes, which contain directions and instructions from maintainers that can’t be derived from the code.</span></p>
<h3><strong style="vertical-align: baseline;">What the data shows</strong></h3>
<p><span style="vertical-align: baseline;">The real test of an automated reviewer is whether maintainers pay attention to the reports it sends out, and whether those reports track actual software quality. Seven months of Sashiko production data from the kernel mailing lists give a clear picture of both these questions.</span></p>
<p><strong style="vertical-align: baseline;">It is part of the daily workflow.</strong><span style="vertical-align: baseline;"> Sashiko completes roughly 1200 reviews a day across over 100 kernel mailing lists. It sends review emails only to lists whose maintainers opt in, and already over 70 of them have done so. Developers also engage directly with the reports: More than 1500 kernel developers have replied on the mailing lists, and their pushback on false alarms has directly driven improvements to Sashiko's prompts and verification engine. In fact, </span><a href="http://lwn.net" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">LWN.net</span></a><span style="vertical-align: baseline;"> recently </span><a href="https://lwn.net/Articles/1096963/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">wrote</span></a><span style="vertical-align: baseline;"> that </span><strong style="vertical-align: baseline;">Sashiko has already become an important part of the kernel's development process</strong><span style="vertical-align: baseline;"> and was </span><a href="https://lwn.net/Articles/1100241/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">the top bug reporter</span></a><span style="vertical-align: baseline;"> of issues in the 7.2 release cycle.</span></p>
<p><strong style="vertical-align: baseline;">It prevents new bugs and uncovers old ones.</strong><span style="vertical-align: baseline;"> When Sashiko flags a bug in a proposed patch, the author typically fixes it in the next revision before the change is ever merged. Many developers run Sashiko locally or in corporate private instances. The bugs that Sashiko helped to prevent leave no trace in the git commit log, making them hard to count directly. What </span><span style="font-style: italic; vertical-align: baseline;">can</span><span style="vertical-align: baseline;"> be counted are fixes for preexisting bugs that Sashiko finds and reports as a byproduct of reviewing new changes: Sashiko is cited in over 2000 mainline kernel commits and in over 500 of this year's official Linux kernel CVEs, spanning drivers, core kernel code, networking, GPUs, memory management, and virtualization.</span></p>
<p><strong style="vertical-align: baseline;">Fewer bugs are slipping into mainline releases.</strong><span style="vertical-align: baseline;"> Across the 18 kernel releases prior to Sashiko (Linux 6.2 through 6.19, covering 254000 commits), an average of 3.4% of merged commits required a follow-up fix within 60 days. Since Sashiko rolled out, that 60-day fix rate has fallen to 2.8% in Linux 7.1 and 2.2% in Linux 7.2, </span><strong style="vertical-align: baseline;">a 35% drop</strong><span style="vertical-align: baseline;"> (with the 30-day fix rate falling from 2.3% to 1.4%). It’s too early to make strong claims, and obviously many other factors can influence release-to-release numbers, so we cannot solely credit Sashiko for the entire drop, but the trend is optimistic.</span></p></div>

<h3><strong style="vertical-align: baseline;">What we learned from building and running Sashiko</strong></h3>
<p><span style="vertical-align: baseline;">First, </span><strong style="vertical-align: baseline;">benchmark-driven development beats intuition.</strong><span style="vertical-align: baseline;"> While developing Sashiko, we tried many ideas that looked very reasonable on their face but didn’t end up working out. Other ideas were less obvious but worked surprisingly well. What was crucial: Early on, we built a benchmark out of nearly 1,000 real Linux kernel bugs and used it to evaluate every major Sashiko change. Every bug in this set was a real mistake that had passed human review by kernel experts, had been merged into mainline Linux, and later had to be fixed. On that benchmark, Sashiko with the new </span><strong style="vertical-align: baseline;">Gemini 4 Carbon</strong><span style="vertical-align: baseline;"> model catches </span><strong style="vertical-align: baseline;">75.8%</strong><span style="vertical-align: baseline;"> of the bugs that human reviewers missed (using high thinking level).</span></p>
<p><span style="vertical-align: baseline;">Second, </span><strong style="vertical-align: baseline;">coding agents are not great at reviewing their own code.</strong><span style="vertical-align: baseline;"> Models are trained to produce a working solution within a limited token budget. Asking these agents to review their own code might work well for isolated tasks, but for real, large codebases, creating a functional solution is often just 5-10% of the work. What’s really hard is to produce a solution that works all of the time, is well-integrated into the surrounding code, and doesn’t introduce subtle regressions. This is often substantially more complex and requires additional effort. Similar to human developers, agents benefit from external code review: Reviewers often spot issues that the initial author missed, even if they are not more experienced.</span></p>
<p><span style="vertical-align: baseline;">Third, </span><strong style="vertical-align: baseline;">open source and shared community ownership and development help to build trust.</strong><span style="vertical-align: baseline;"> By being fully open and transparent from the <span style="vertical-align: baseline;">beginning</span>, Sashiko allowed anyone to run it the way they wanted: using different models (including open source and local models), customizing prompts, or even adopting Sashiko to other-than-Linux projects. This helped with community adoption and brought over 100 contributors to improve Sashiko, including some prominent kernel developers.</span></p>
<p><span style="vertical-align: baseline;">More and more engineers are putting local Sashiko instances into their coding-agent loops, so patches are checked against the community's review rules before a human maintainer ever sees them. We use the same workflow to build Sashiko itself ("Sashiko for Sashiko"), running it to review every change to its codebase and prompt pipeline both locally and through a Github integration.</span></p>
<p><span style="vertical-align: baseline;">Although Sashiko started in the Linux kernel, the need for an agentic trust layer applies across critical open-source software. Because the core review engine does not depend on C or on kernel-specific rules, the Linux kernel playbook (combining an open verification pipeline, community-owned domain guides, and a benchmark mined from historically known issues and fixes) can likely be applied to other foundational open-source projects such as GCC, LLVM, or Git.</span></p>
<p style="padding-left: 40px;"><span style="font-style: italic; vertical-align: baseline;">"Now, I think the other side of AI - and this is where Sashiko comes in - is that it basically does end up being a tool that can then increase the trust in the patch. So AI giveth, and AI taketh away. But the basic issue shouldn't be AI per se, it should be that notion of 'trust'." - </span><strong style="vertical-align: baseline;">Linus Torvalds</strong><span style="vertical-align: baseline;"> </span><a href="https://lore.kernel.org/all/CAHk-=wgbGarE7Ozw4VG6oUKDj9pk-8DRoDiX00bo1MwEMm9UWQ@mail.gmail.com/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">on LKML</span></a></p>
