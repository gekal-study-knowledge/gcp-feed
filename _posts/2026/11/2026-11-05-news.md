### Introducing Compute Engine API multi-versioning: Predictable evolution without breaking production

- **Link**: [https://cloud.google.com/blog/topics/developers-practitioners/introducing-compute-engine-api-multi-versioning-predictable-evolution-without-breaking-production/](https://cloud.google.com/blog/topics/developers-practitioners/introducing-compute-engine-api-multi-versioning-predictable-evolution-without-breaking-production/)

<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">Ready to modernize your infrastructure without risking production stability? API multi-versioning for Compute Engine, now in general availability, helps you do just that. With date-based API versions, Compute Engine can now regularly deliver modern API semantics, stronger resilience defaults, and improved developer experience while preserving the rock-solid stability of the </span><code style="vertical-align: baseline;">/v1</code><span style="vertical-align: baseline;"> API.</span></p>
<p><span style="vertical-align: baseline;">For more than a decade, the Google Compute Engine </span><code style="vertical-align: baseline;">/v1</code><span style="vertical-align: baseline;"> API has served as the foundational control plane for millions of virtual machines, Google Kubernetes Engine (GKE) clusters, and large-scale AI infrastructure. For platform teams and developers who build on Google Cloud, that single </span><code style="vertical-align: baseline;">/v1</code><span style="vertical-align: baseline;"> endpoint delivered an extraordinary promise: write your integration once, and trust that it will keep running year after year.</span></p>
<p><span style="vertical-align: baseline;">Yet as cloud architectures have grown in scale and sophistication, infrastructure teams have faced a growing tension. On one hand, mission-critical production workloads require absolute API stability and strict backward compatibility. On the other hand, customers want faster access to safer security defaults, stronger regional resilience, machine-readable error models, and modern, declarative-friendly APIs, but introducing these improvements in place risks disrupting existing automation. The new versioning model helps avoid that disruption by giving you the flexibility to adopt modern semantics on your own schedule without touching your production workloads.</span></p>
<h2><span style="vertical-align: baseline;">Date-based API versions for Compute Engine</span></h2>
<p><span style="vertical-align: baseline;">Historically, Compute Engine relied on </span><strong style="vertical-align: baseline;">channel-based versioning (CBV)</strong><span style="vertical-align: baseline;"> with three long-lived channels: </span><code style="vertical-align: baseline;">/v1</code><span style="vertical-align: baseline;"> (generally available), </span><code style="vertical-align: baseline;">/beta</code><span style="vertical-align: baseline;">, and </span><code style="vertical-align: baseline;">/alpha</code><span style="vertical-align: baseline;">. Because </span><code style="vertical-align: baseline;">/v1</code><span style="vertical-align: baseline;"> was a single, mutable production surface shared by every customer worldwide, any behavioral improvement–even changing a counter-intuitive default or modernizing an error format–carried the risk of breaking existing scripts or required multi-year migrations.</span></p>
<p><span style="vertical-align: baseline;">With </span><strong style="vertical-align: baseline;">interface-based versioning (IBV)</strong><span style="vertical-align: baseline;">, aligned with Google </span><a href="https://google.aip.dev/185" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">AIP-185</span></a><span style="vertical-align: baseline;">, Compute Engine introduces immutable, date-based API snapshots alongside </span><code style="vertical-align: baseline;">/v1</code><span style="vertical-align: baseline;">:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Stable versions (</strong><code><strong style="vertical-align: baseline;">YYYY-MM-DD</strong></code><strong style="vertical-align: baseline;">)</strong><span style="vertical-align: baseline;">: Released on a predictable </span><strong style="vertical-align: baseline;">quarterly cadence</strong><span style="vertical-align: baseline;"> (starting with </span><code style="vertical-align: baseline;">2026-09-01</code><span style="vertical-align: baseline;">), each stable version represents a locked, point-in-time contract of all generally available Compute Engine features and behavioral defaults. Stable versions don't receive breaking changes after they're published. They have no end-of-support date today.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Preview versions (</strong><code><strong style="vertical-align: baseline;">YYYY-MM-DD-preview</strong></code><strong style="vertical-align: baseline;">)</strong><span style="vertical-align: baseline;">: Released on a rapid cadence (such as </span><code style="vertical-align: baseline;">2026-10-01-preview</code><span style="vertical-align: baseline;">), preview versions branch from a stable parent to give developers early access to upcoming features and API designs, carrying a predictable one-year lifespan for testing and feedback.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Uninterrupted </strong><code><strong style="vertical-align: baseline;">/v1</strong></code><strong style="vertical-align: baseline;"> support</strong><span style="vertical-align: baseline;">: The existing </span><code style="vertical-align: baseline;">/v1</code><span style="vertical-align: baseline;"> API remains fully supported and it continues to serve as the default if no date-based version is specified. Your existing applications, scripts, and integrations continue to work without modification.</span></p>
</li>
</ul>
<h2><span style="vertical-align: baseline;">Primary benefits for builders</span></h2>
<h3><span style="vertical-align: baseline;">1. Stability and customer-controlled upgrades</span></h3>
<p><span style="vertical-align: baseline;">In a traditional single-version API, changing a default behavior forces a trade-off between platform progress and customer stability. But date-based multi-versioning puts upgrade timing entirely in your hands:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Pin to a known contract</strong><span style="vertical-align: baseline;">: Direct REST callers and SDK users can lock onto a specific version identifier (such as </span><code style="vertical-align: baseline;">2026-09-01</code><span style="vertical-align: baseline;">) knowing its request and response schemas are frozen.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Upgrade on your schedule</strong><span style="vertical-align: baseline;">: When a new quarterly stable version introduces updated defaults or modified resource schemas, your team can evaluate the release notes, test in staging by changing a single version string, and roll out to production at your own pace.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Consistent resource URIs</strong><span style="vertical-align: baseline;">: Date-based versions continue to use the </span><code style="vertical-align: baseline;">/compute/v1/</code><span style="vertical-align: baseline;"> base URL path. You specify the target version via the </span><code style="vertical-align: baseline;">X-Goog-Api-Version</code><span style="vertical-align: baseline;"> HTTP header or the </span><code style="vertical-align: baseline;">$apiVersion</code><span style="vertical-align: baseline;"> query parameter. This means that resource </span><code style="vertical-align: baseline;">selfLink</code><span style="vertical-align: baseline;"> URIs remain uniform across tools and services.</span></p>
</li>
</ul></div>

<div class="block-paragraph_advanced"><h3><span style="vertical-align: baseline;">2. Safer defaults, stronger resilience, and modern API standards</span></h3>
<p><span style="vertical-align: baseline;">By isolating behavioral changes to new date-based versions, Compute Engine is delivering improvements that make cloud applications more resilient, more secure, and easier to automate:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Resilient global queries by default</strong><span style="vertical-align: baseline;">: In legacy </span><code style="vertical-align: baseline;">/v1</code><span style="vertical-align: baseline;">, calling </span><code style="vertical-align: baseline;">AggregatedList</code><span style="vertical-align: baseline;"> across all zones and regions defaults </span><code style="vertical-align: baseline;">returnPartialSuccess</code><span style="vertical-align: baseline;"> to </span><code style="vertical-align: baseline;">false</code><span style="vertical-align: baseline;">. This means a transient issue in a single zone could cause a global list request to fail unless callers explicitly opted in. In new date-based versions, partial success is enabled by default so global fleet queries remain resilient during localized maintenance or disruptions.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Actionable, machine-readable errors (AIP-193)</strong><span style="vertical-align: baseline;">: Date-based versions adopt standardized </span><a href="https://google.aip.dev/193" rel="noopener" target="_blank"><code style="text-decoration: underline; vertical-align: baseline;">google.rpc.ErrorInfo</code></a><span style="vertical-align: baseline;"> payloads with structured </span><code style="vertical-align: baseline;">reason</code><span style="vertical-align: baseline;">, </span><code style="vertical-align: baseline;">domain</code><span style="vertical-align: baseline;">, and contextual </span><code style="vertical-align: baseline;">metadata</code><span style="vertical-align: baseline;"> (such as returning the list of </span><code style="vertical-align: baseline;">supported_versions</code><span style="vertical-align: baseline;"> if an invalid version identifier is requested), eliminating brittle regex parsing of error strings.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Stronger security and least-privilege hygiene</strong><span style="vertical-align: baseline;">: New API versions allow Compute Engine to tighten overly broad legacy IAM permission checks and introduce safer configuration defaults without disrupting legacy automation running on </span><code style="vertical-align: baseline;">/v1</code><span style="vertical-align: baseline;">.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Cleaner, declarative-friendly API design</strong><span style="vertical-align: baseline;">: Multi-versioning provides a clean path to evolve complex, decade-old resource schemas toward modern Google API Improvement Proposals (AIPs).</span></p>
</li>
</ul>

<p><span style="vertical-align: baseline;">Agentic coding tools have dramatically accelerated software delivery, but human review can’t keep up with machine-speed commits and unvetted dependencies. Because autonomous agents are now part of the supply chain, blind trust can turn them into direct backdoors for attackers.</span></p>
<p><span style="vertical-align: baseline;">Our approach to securing the development lifecycle builds native, real-time guardrails in the integrated development environment (IDE), unifies asset graphs across code and identity and access management (IAM,) and verifies models to weed out logic flaws before code merges.</span></p>

These include identifying previously-unknown vulnerabilities, and generating tested patches before they can be exploited. </span></p>
<p><span style="vertical-align: baseline;">Most recently, Wiz used Gemini 4 Argon along with other models to identify and help remediate </span><a href="https://www.wiz.io/blog/php2shell-php-rce" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">core PHP vulnerabilities that affected 70% of websites</span></a><span style="vertical-align: baseline;">. Gemini 4 Argon made a notable contribution to finding the vulnerability, developing a likely exploit path, detecting attacks, and validating the patch.</span></p>
<p><span style="vertical-align: baseline;">Currently in preview, CodeMender delivers new capabilities for secure isolation and flexible scanning:</span></p>

<p><strong style="vertical-align: baseline;">Secure autonomous remediation</strong><span style="vertical-align: baseline;">: CodeMender isolates vulnerability verification and exploit simulation inside your choice of operating system-level sandbox or isolated virtual machine, and adds human-in-the-loop checks for local write and command execution helping to reduce the risks of malicious exploits and zero-day testing gone awry.</span></p>

<p><strong style="vertical-align: baseline;">Flexible scanning modes</strong><span style="vertical-align: baseline;">: CodeMender now allows you to scan a specific folder, entire repository, or only modified files since the last scan so you have fine grain control on how many files to scan to optimize for scanning speed and costs.</span></p>

<h3><span style="vertical-align: baseline;">Securing workloads everywhere</span></h3>
<p><span style="vertical-align: baseline;">When autonomous workloads transition to production, the threat landscape shifts entirely. Adversaries target your plumbing — credentials, data boundaries, and integrations that connect agents to the enterprise. Once inside, attackers exploit over-privileged credentials and unsegmented environments to move laterally across enterprise data boundaries.</span></p>
<p><span style="vertical-align: baseline;">To eliminate these flat-trust architectures, Google Cloud delivers a unified framework of foundational security and governance controls for agents everywhere they run. Whether your agents are operating on the Gemini platform, Google Kubernetes Engine (GKE) and Cloud Run, the new </span><a href="https://cloud.google.com/blog/topics/ai-infrastructure/introducing-agent-compute-engine-and-expanded-agent-governance"><span style="text-decoration: underline; vertical-align: baseline;">Agent Compute Engine</span></a><span style="vertical-align: baseline;">, or are coordinating across multi-cloud environments — they are bound by the same rigorous enterprise controls.</span></p>
<p><span style="vertical-align: baseline;">To enforce our agents everywhere framework at the transaction level, we are introducing critical identity, network, and content controls:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Auth Manager (Agent Identity)</strong><span style="vertical-align: baseline;">: Centralizes credential management inside a Google-managed vault governed by IAM. Now generally available, </span><a href="https://docs.cloud.google.com/iam/docs/auth-manager-overview"><span style="text-decoration: underline; vertical-align: baseline;">Auth Manager</span></a><span style="vertical-align: baseline;"> automates OAuth 2.0/PKCE flows and refreshes user-delegated tokens to minimize consent fatigue and reduce credential theft. Alongside Auth Manager, </span><a href="https://docs.cloud.google.com/iam/docs/agent-identity-overview"><span style="text-decoration: underline; vertical-align: baseline;">Agent Identity</span></a><span style="vertical-align: baseline;"> </span><a href="https://docs.cloud.google.com/iam/docs/auth-agent-own-identity-external"><span style="text-decoration: underline; vertical-align: baseline;">JWT support</span></a><span style="vertical-align: baseline;">, now in preview, issues standard OIDC tokens, allowing agents to authenticate securely across AWS, Azure, on-premises backends, and MCP servers without static, long-lived API keys.</span></p>

<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">こうしたパフォーマンス目標を達成するには、組織には AI 評価を実施してリアルタイムのボトルネックを特定するための体系的なアプローチが必要です。そこで、KDDI がこのアプリケーションをリリースするのに役立った自動評価フレームワークとパフォーマンス最適化手法をご紹介します。</span></p>
<p><span style="vertical-align: baseline;">これらは素晴らしい結果をもたらしました。KDDI はアプリケーションの合計レスポンス レイテンシを 38% 削減し、目標のレスポンス パフォーマンスを達成しました。また、TTFT も 18% 近く改善しました。</span></p>
<p><span style="vertical-align: baseline;">「私たちのビジョンは、コンテンツを取り込んですぐに RAG システムとして機能するプラットフォームを構築することでした。Google の丁寧かつ実践的なガイダンスのおかげで、それを実現できました。Google のサポートに心から感謝しています。」- KDDI、AI プロダクト部、小野田 隼也 氏</span></p>
<p><span style="vertical-align: baseline;">パフォーマンスと精度の向上により、Buffmee はユーザーがインタラクティブな Q&amp;A や詳細な分析を通じてお気に入りのメディアを安全に探索できるようになりました。このように、コンテンツ プロバイダの信頼性とコンプライアンスを厳格に維持しながら、高度にパーソナライズされたエクスペリエンスを実現しています。</span></p>
<p><span style="vertical-align: baseline;">同社がどのようにこれらの成果を達成したのか、詳しく見ていきましょう。</span></p>
<h4><strong style="vertical-align: baseline;">多様なコンテンツの自動評価を確立する</strong></h4>
<p><span style="vertical-align: baseline;">従来の手動テストは多大な労力を必要とし、大規模なコンテンツ ライブラリに対応するよう拡張することはできませんでした。この問題を解決するため、開発チームは Gemini Enterprise Agent Platform Evaluation Service を使用して、体系的な AI 評価プロセスを設計しました。</span></p>
<p><span style="vertical-align: baseline;">LLM-as-a-Judge や Rule of Hundreds（100 の法則）などの自動評価フレームワークを実装することで、チームは手間のかかる手動テストをデータドリブンなプロセスに置き換えました。同社は、膨大なドキュメント コーパスを取り込み、数百の自動評価テストを構築し、各ユースケースの回答の信頼性を測定するための包括的なベンチマーク データセットを構築しました。チームはその結果、根拠性スコアを 25% 高め、高精度で信頼性の高い出力を提供できるようになりました。</span></p></div>

<div class="block-paragraph_advanced"><h4><strong style="vertical-align: baseline;">エージェント ループでボトルネックを特定し、パフォーマンスを最適化する</strong></h4>
<p><span style="vertical-align: baseline;">応答速度を向上させるため、チームは BigQuery Agent Analytics と Agent Development Kit（ADK）ログ分析エージェントを実装しました。実際のプロダクション ログを分析することで、スキルの分割とプロンプトの肥大化（特に、非常に複雑な複数ページのシステム プロンプトの場合）が、最初のトークンまでの時間（TTFT）にどのように影響するかを可視化しました。</span></p>
<p><span style="vertical-align: baseline;">チームは、スキルのインライン統合を含むシステム プロンプトを最適化し、サブエージェントのルーティングを見直しました。これにより、回答の精度を維持したまま、複雑に組み合わさったシステムのボトルネックをリアルタイムで特定して解決できました。</span></p>
<h4><strong style="vertical-align: baseline;">信頼性の高い評価のための 4 つの基本原則</strong></h4>
<p><span style="vertical-align: baseline;">これらの結果を得るために、チームは 4 つの主要な技術的手法を実施しました。</span></p>
<ol>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">バイナリ評価への移行: </strong><span style="vertical-align: baseline;">重要な指標について、曖昧な 1～5 の評価からバイナリの「合格（1） / 不合格（0）」システムに選択的に移行することで、チームはばらつきとノイズを最小限に抑え、自動化の精度を向上させました。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">戦略的なコンテンツ サンプリング:</strong><span style="vertical-align: baseline;"> すべてのドキュメントを評価しようとするのではなく、チームはコーパス全体を 2 次元グリッドに沿って分類しました。それらの軸は、ファイル形式（ウェブ記事、EPUB、PDF、構造化データ）とメディア構成（テキスト中心、画像中心、混合）です。この難易度グリッドの各セルから代表サンプルを選択することで、包括的なテスト範囲を維持しながら、評価のワークロードを 75% 削減しました。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">プロダクト判断に基づくしきい値:</strong><span style="vertical-align: baseline;"> プロダクト オーナーは、デフォルトのツール パラメータのみに依存するのではなく、ランダムにサンプリングされた回答と自動スコアを突き合わせて検証しました。これにより、ユーザー エクスペリエンスの観点から「リリース基準を満たす品質とは何か」を具体的に定義し、評価のしきい値を調整および確立しました。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">大規模なプロンプトを ADK スキルにモジュール分割:</strong><span style="vertical-align: baseline;"> 800 行を超える大規模なシステム プロンプトは、LLM の指示の見落としやレイテンシの低下を引き起こす可能性があるため、チームはプロンプトを機能ごとに Agent Development Kit（ADK）スキルに分割し、必要なロジックのみを動的に読み込んでレスポンス時間を最適化しました。</span></p>
</li>
</ol>
