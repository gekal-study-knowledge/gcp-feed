### Experimenting with ClusterNetworkPolicy in GKE

<summary>詳細を表示</summary>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">Standard </span><a href="https://kubernetes.io/docs/concepts/services-networking/network-policies/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Network Policies</span></a><span style="vertical-align: baseline;"> limit you to applying policies at the namespace level, but </span><a href="https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-cluster-network-policy"><span style="text-decoration: underline; vertical-align: baseline;">ClusterNetworkPolicy (CNP)</span></a><span style="vertical-align: baseline;"> lets you apply granular networking policies across an entire cluster. When you use CNP, you can easily scale security and governance policies. Recently, I experimented with this functionality in </span><a href="https://docs.cloud.google.com/kubernetes-engine/docs/concepts/kubernetes-engine-overview"><span style="text-decoration: underline; vertical-align: baseline;">Google Kubernetes Engine (GKE)</span></a><span style="vertical-align: baseline;"> and saw the benefits for myself.</span></p>
<p><span style="vertical-align: baseline;">In this post, we'll explore using CNP to control traffic to an LLM and cluster. If you want to jump right into a hands-on lab, check out this Codelab: </span><a href="https://codelabs.developers.google.com/codelabs/inference-gke-clusternetworkpolicy" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Secure AI Inference Workloads with GKE ClusterNetworkPolicy</span></a><span style="vertical-align: baseline;">.</span></p>
<h2><strong style="vertical-align: baseline;">How CNP works</strong></h2>
<p><strong style="vertical-align: baseline;">CNP </strong><span style="vertical-align: baseline;">follows a </span><a href="https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-cluster-network-policy#policy_evaluation_hierarchy"><span style="text-decoration: underline; vertical-align: baseline;">three-tier</span></a><span style="vertical-align: baseline;"> flow with a precedence match:</span></p>
<ol>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Admin tier (top precedence)</strong><span style="vertical-align: baseline;">: Cluster administrator enforces mandatory security rules that can't be bypassed (for example, blocking metadata access).</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Network policy tier (middle precedence)</strong><span style="vertical-align: baseline;">: Standard namespace-scoped policies that are managed by application teams to control ingress and egress for their microservices.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Baseline tier (bottom precedence)</strong><span style="vertical-align: baseline;">: Cluster administrator establishes fallback defaults (for example, a default-deny posture across namespaces).</span></p>
</li>
</ol>
<h2><strong style="vertical-align: baseline;">Design pattern example</strong></h2>
<p><span style="vertical-align: baseline;">The aim of the </span><a href="https://codelabs.developers.google.com/codelabs/inference-gke-clusternetworkpolicy#0" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">experiment in the Codelab</span></a><span style="vertical-align: baseline;"> is to restrict traffic to the LLM namespace, allow only authorized clients, and prevent cluster-wide access to the metadata API except for DNS port 53. It uses these services:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><a href="https://docs.cloud.google.com/vpc/docs/create-modify-vpc-networks"><strong style="text-decoration: underline; vertical-align: baseline;">Virtual Private Cloud (VPC)</strong></a><span style="vertical-align: baseline;">: Provides private networking, subnets for pods and services, and secure outbound egress via Cloud NAT.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><a href="https://docs.cloud.google.com/tpu/docs/v5e"><strong style="text-decoration: underline; vertical-align: baseline;">TPU v5e</strong></a><span style="vertical-align: baseline;">: High-efficiency accelerator hardware (2x2 topology) running optimized model inference.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">GKE</strong><span style="vertical-align: baseline;">: Managed Kubernetes platform that's powered by GKE Dataplane V2 (eBPF) to enforce multi-tier networking policies.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><a href="https://huggingface.co/google/gemma-4-E2B-it" rel="noopener" target="_blank"><strong style="text-decoration: underline; vertical-align: baseline;">Gemma 4 (</strong><strong style="text-decoration: underline; vertical-align: baseline;">google/gemma-4-E2B-it</strong><strong style="text-decoration: underline; vertical-align: baseline;">)</strong></a><span style="vertical-align: baseline;">: Lightweight open model served with vLLM to act as a sensitive AI workload.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">ClusterNetworkPolicy (CNP)</strong><span style="vertical-align: baseline;">: Cluster-wide policies that let administrators enforce mandatory administrator and baseline guardrails across all namespaces.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><a href="https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/network-policy"><strong style="text-decoration: underline; vertical-align: baseline;">NetworkPolicies</strong></a><span style="vertical-align: baseline;">: Standard namespace-scoped rules that let developers grant access to authorized clients.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Cloud Logging / </strong><a href="https://docs.cloud.google.com/kubernetes-engine/docs/how-to/network-policy-logging?utm_campaign=CDR_0x78e4a6e6_default_b565725300&amp;utm_medium=external&amp;utm_source=lab"><strong style="text-decoration: underline; vertical-align: baseline;">GKE Network Policy Logging</strong></a><span style="vertical-align: baseline;">: Captures real-time packet verdicts (</span><code style="vertical-align: baseline;">allow</code><span style="vertical-align: baseline;">/</span><code style="vertical-align: baseline;">deny</code><span style="vertical-align: baseline;">) and policy audit trails.</span></p>
</li>
</ul></div>

<div class="block-paragraph_advanced"><h2><strong style="vertical-align: baseline;">Putting it together: Setup overview</strong></h2>
<p><span style="vertical-align: baseline;">Setting up this environment begins with building a custom private network infrastructure and deploying your TPU-enabled clusters:</span></p>
<ol>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Custom VPC &amp; Cloud NAT</strong><span style="vertical-align: baseline;">: Establish a custom VPC with a dedicated subnet that hosts primary nodes, plus secondary CIDR IP address ranges for GKE pods (</span><code style="vertical-align: baseline;">10.20.0.0/16</code><span style="vertical-align: baseline;">) and services (</span><code style="vertical-align: baseline;">10.30.0.0/20</code><span style="vertical-align: baseline;">). A Cloud Router and Cloud NAT are configured to handle secure outbound egress for nodes while blocking inbound internet exposure.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">GKE Standard cluster</strong><span style="vertical-align: baseline;">: Spin up a Standard GKE cluster running GKE Dataplane V2 (</span><code style="vertical-align: baseline;">ADVANCED_DATAPATH</code><span style="vertical-align: baseline;">). GKE Dataplane V2 acts as the core engine that leverages eBPF under the hood to enforce both standard and cluster-scoped policies dynamically.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Dedicated TPU v5e node pool</strong><span style="vertical-align: baseline;">: Provision a node pool featuring </span><code style="vertical-align: baseline;">ct5lp-hightpu-4t</code><span style="vertical-align: baseline;"> machines arranged in a 2x2 topology slice. The nodes carry a dedicated taint (</span><code style="vertical-align: baseline;">google.com/tpu=present:NoSchedule</code><span style="vertical-align: baseline;">) to ensure that only accelerator workloads run on them.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Deploying the Gemma 4 workload</strong><span style="vertical-align: baseline;">: Isolate the pods by creating three distinct namespaces:</span></p>
<ul>
<li><code style="vertical-align: baseline;">gemma-llm</code><span style="vertical-align: baseline;"> (</span><code style="vertical-align: baseline;">tier: ai-core</code><span style="vertical-align: baseline;">): Serves the lightweight Gemma 4 model using the high-performance </span><code style="vertical-align: baseline;">vllm/vllm-tpu:latest</code><span style="vertical-align: baseline;"> engine on port 8000.</span></li>
<li><code style="vertical-align: baseline;">client-ns</code><span style="vertical-align: baseline;"> (</span><code style="vertical-align: baseline;">tier: app-frontend</code><span style="vertical-align: baseline;">): Runs the authorized chat client that must query the model.</span></li>
<li><code style="vertical-align: baseline;">untrusted-tenant</code><span style="vertical-align: baseline;"> (</span><code style="vertical-align: baseline;">tier: untrusted</code><span style="vertical-align: baseline;">): Represents an unauthorized probe container simulating a rogue client.</span></li>
</ul>
</li>
</ol>
<h2><strong style="vertical-align: baseline;">Securing the LLM and metadata: Code walkthrough</strong></h2>
<p><span style="vertical-align: baseline;">By default in Kubernetes, all cross-namespace and egress traffic is open. To enforce a defense-in-depth posture, we apply network policies across the GKE evaluation tiers.</span></p>
<h3><strong style="vertical-align: baseline;">Step 1: Establish zero-trust posture (baseline tier)</strong></h3>
<p><span style="vertical-align: baseline;">To deny all unauthorized ingress cluster-wide, the cluster administrator applies a ClusterNetworkPolicy at the baseline tier. This tier acts as a fallback safety net.</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &#x27;apiVersion: policy.networking.k8s.io/v1alpha2\r\nkind: ClusterNetworkPolicy\r\nmetadata:\r\n  name: baseline-default-deny\r\nspec:\r\n  tier: Baseline\r\n  priority: 1000\r\n  subject:\r\n    namespaces: {}\r\n  ingress:\r\n    - name: allow-dns-ingress\r\n      action: Accept\r\n      from:\r\n        - namespaces: {}\r\n      protocols:\r\n        - udp:\r\n            destinationPort:\r\n              number: 53\r\n        - tcp:\r\n            destinationPort:\r\n              number: 53\r\n    - name: baseline-deny-cross-ns\r\n      action: Deny\r\n      from:\r\n        - namespaces: {}&#x27;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f126d5da0d0&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><h4><strong style="vertical-align: baseline;">How it works</strong></h4>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Precedence placement</strong><span style="vertical-align: baseline;">: Setting </span><code style="vertical-align: baseline;">tier: Baseline</code><span style="vertical-align: baseline;"> places this policy at the very bottom of the GKE evaluation chain, and the </span><code style="vertical-align: baseline;">priority: 1000</code><span style="vertical-align: baseline;"> value orders it within that tier. It only processes traffic that hasn't matched a rule in any higher tier.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Global target</strong><span style="vertical-align: baseline;">: Specifying </span><code style="vertical-align: baseline;">subject.namespaces: {}</code><span style="vertical-align: baseline;"> ensures that this fallback applies globally to every pod in every namespace.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">DNS isolation exemption</strong><span style="vertical-align: baseline;">: The first ingress rule accepts incoming DNS traffic on TCP and UDP port 53. Without this explicit exemption, cluster-wide DNS resolution would fail.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Fallback deny</strong><span style="vertical-align: baseline;">: The second rule matches any incoming pod-to-pod connection attempt and drops it. At this stage, both the </span><code style="vertical-align: baseline;">client-ns</code><span style="vertical-align: baseline;"> and </span><code style="vertical-align: baseline;">untrusted-tenant</code><span style="vertical-align: baseline;"> namespaces are blocked from contacting Gemma.</span></p>
</li>
</ul>
<h3><strong style="vertical-align: baseline;">Step 2: Delegate access to developers (networkpolicy tier)</strong></h3>
<p><span style="vertical-align: baseline;">With the baseline default-deny active, the application team that manages </span><code style="vertical-align: baseline;">gemma-llm</code><span style="vertical-align: baseline;"> can safely delegate access to legitimate clients. They define a standard namespace-scoped </span><code style="vertical-align: baseline;">NetworkPolicy</code><span style="vertical-align: baseline;"> to allow incoming port 8000 traffic from </span><code style="vertical-align: baseline;">rag-agent</code> <span style="vertical-align: baseline;">pods in the</span><strong style="vertical-align: baseline;"> </strong><code style="vertical-align: baseline;">client-ns</code><span style="vertical-align: baseline;"> namespace.</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &#x27;apiVersion: networking.k8s.io/v1\r\nkind: NetworkPolicy\r\nmetadata:\r\n  name: allow-rag-client\r\n  namespace: gemma-llm\r\nspec:\r\n  podSelector:\r\n    matchLabels:\r\n      app: gemma-service\r\n  policyTypes:\r\n    - Ingress\r\n  ingress:\r\n    # Explicitly permit ingress only from pods matching app: rag-agent in client-ns\r\n    - from:\r\n        - namespaceSelector:\r\n            matchLabels:\r\n              kubernetes.io/metadata.name: client-ns\r\n          podSelector:\r\n            matchLabels:\r\n              app: rag-agent\r\n      ports:\r\n        - protocol: TCP\r\n          port: 8000&#x27;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f126e6d4810&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><h4><strong style="vertical-align: baseline;">How it works</strong></h4>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Developer control</strong><span style="vertical-align: baseline;">: This resource resides within the </span><code style="vertical-align: baseline;">gemma-llm</code><span style="vertical-align: baseline;"> namespace and it's managed directly by the developer, matching the GKE focus on operational separation.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Middle precedence matching</strong><span style="vertical-align: baseline;">: Standard Kubernetes </span><code style="vertical-align: baseline;">NetworkPolicies</code><span style="vertical-align: baseline;"> map directly to the NetworkPolicy Tier. Because this tier is evaluated before the baseline tier, incoming TCP packets from the authorized client to port 8000 match this rule and are immediately accepted.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Fall-through block</strong><span style="vertical-align: baseline;">: Connections that originate from the </span><code style="vertical-align: baseline;">untrusted-tenant</code><span style="vertical-align: baseline;"> namespace fail to match this rule, pass through to the baseline tier, and are dropped.</span></p>
</li>
</ul>
<h3><strong style="vertical-align: baseline;">Step 3: Enforce global egress guardrails (admin tier)</strong></h3>
<p><span style="vertical-align: baseline;">By default, Pods can query the GKE link-local Compute Engine metadata server (</span><code style="vertical-align: baseline;">169.254.169.254</code><span style="vertical-align: baseline;">). Those queries expose instance metadata and potentially high-privilege service account tokens. To lock this down, the cluster administrator applies an egress guardrail at the highest tier in the GKE hierarchy.</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &#x27;apiVersion: policy.networking.k8s.io/v1alpha2\r\nkind: ClusterNetworkPolicy\r\nmetadata:\r\n  name: admin-global-guardrails\r\nspec:\r\n  tier: Admin\r\n  priority: 10\r\n  subject:\r\n    namespaces: {}  # Targets every namespace in the cluster\r\n  ingress:\r\n    # Delegate all ingress decisions down to developer and baseline tiers\r\n    - name: delegate-all-ingress\r\n      action: Pass\r\n      from:\r\n        - namespaces: {}\r\n  egress:\r\n    # Allow DNS resolution so pods can locate endpoints\r\n    - name: allow-all-dns\r\n      action: Accept\r\n      to:\r\n        - networks:\r\n            - 0.0.0.0/0\r\n      protocols:\r\n        - udp:\r\n            destinationPort:\r\n              number: 53\r\n        - tcp:\r\n            destinationPort:\r\n              number: 53\r\n    # Hard deny on the Compute Engine metadata server\r\n    - name: block-metadata-server-global\r\n      action: Deny\r\n      to:\r\n        - networks:\r\n            - 169.254.169.254/32\r\n    # Delegate remaining egress traffic to lower tiers\r\n    - name: delegate-other-egress\r\n      action: Pass\r\n      to:\r\n        - namespaces: {}&#x27;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f126e6d5d10&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><h4><strong style="vertical-align: baseline;">How it works</strong></h4>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Admin tier precedence</strong><span style="vertical-align: baseline;">: Deploying this policy in the admin tier ensures that it's evaluated first, and priority 10 orders it within that tier. GKE processes this policy before standard NetworkPolicies and baseline rules.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Controlled delegation</strong><span style="vertical-align: baseline;">: The </span><code style="vertical-align: baseline;">delegate-all-ingress</code><span style="vertical-align: baseline;"> and </span><code style="vertical-align: baseline;">delegate-other-egress</code><span style="vertical-align: baseline;"> rules have an </span><code style="vertical-align: baseline;">action: Pass</code><span style="vertical-align: baseline;"> directive that instructs the engine to forward evaluation down to the next tier for remaining in-cluster traffic.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Inviolable guardrail</strong><span style="vertical-align: baseline;">: When any pod attempts to query </span><code style="vertical-align: baseline;">169.254.169.254/32</code><span style="vertical-align: baseline;"> on non-DNS ports, the query matches the </span><code style="vertical-align: baseline;">block-metadata-server-global</code><span style="vertical-align: baseline;"> rule and it's dropped. Because this drop occurs at the top admin tier, it can't be bypassed or overridden, even if a namespace developer deploys an allow-all egress policy.</span></p>
</li>
</ul>
<h2><strong style="vertical-align: baseline;">Verifying with Observability for GKE</strong></h2>
<p><span style="vertical-align: baseline;">Verifying and auditing security policies is straightforward using the built-in telemetry capabilities of GKE Dataplane V2:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Hubble eBPF streams</strong><span style="vertical-align: baseline;">:</span><strong style="vertical-align: baseline;"> </strong><span style="vertical-align: baseline;">Provides real-time, kernel-level packet inspection without injecting sidecars. Administrators can stream live network flows to observe policy verdicts as they happen, making it easy to validate allowed communication paths and identify dropped packets immediately.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">GKE Network Logging and Cloud Logging</strong><span style="vertical-align: baseline;">: Automatically exports structured connection telemetry and policy enforcement verdicts directly into Cloud Logging. Teams can filter and alert on policy decisions using attributes such as </span><code style="vertical-align: baseline;">disposition="deny"</code><span style="vertical-align: baseline;">, source/destination namespaces, and </span><code style="vertical-align: baseline;">jsonPayload.policies[0].name</code><span style="vertical-align: baseline;"> to maintain audit compliance and investigate blocked connection attempts.</span></p>
</li>
</ul>
<p><span style="vertical-align: baseline;">CNP can be useful and, as always, when you use it in your production environment, you'll need to plan and design the rules based on your setup.</span></p>

<h2><strong style="vertical-align: baseline;">Choosing the right architecture: agents, MCPs, skills, and plugins</strong></h2>
<p><span style="vertical-align: baseline;">In previous iterations of enterprise AI, third-party integrations often operated as isolated top-level agents, forcing employees to leave their workflow. When software providers arrive at the Gemini factory, they evaluate how their capabilities plug into Gemini across four complementary architectural primitives rather than competing extremes:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Model Context Protocol (MCP) connectors:</strong><span style="vertical-align: baseline;"> The foundational data and tool pipe for exposing external APIs, search, and CRUD operations to Gemini as callable tools registered in Agent Registry in Gemini platform.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Declarative Skills (</strong><strong style="vertical-align: baseline;">.md</strong><strong style="vertical-align: baseline;">):</strong><span style="vertical-align: baseline;"> Open Markdown configurations stored in Skills Registry that equip Gemini with domain-specific instructions, operational guardrails, and repeatable multi-step workflows across connectors.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Plugins:</strong><span style="vertical-align: baseline;"> The composite packaging and governance primitive in Gemini and Google Cloud Marketplace that bundles one or more Connectors and Skills into a single turnkey solution for IT administrators to govern and Gemini users to invoke.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">AI agents (A2A):</strong><span style="vertical-align: baseline;"> For enterprise ISVs whose value lies in proprietary algorithms, regulated workflows, or strict compliance rules, standalone A2A agents run in an isolated partner environment while plugging into Gemini as callable connectors—keeping intellectual property protected, guaranteeing deterministic execution sequences, and maintaining tamper-proof audit trails.</span></p>
</li>
</ul>
<p><span style="vertical-align: baseline;">Rather than forcing developers into a single mold, Gemini unifies all four primitives into a coherent enterprise fabric—passing shared session context into partner connectors and chaining outputs across the enterprise ecosystem.</span></p>

- **Link**: [https://cloud.google.com/blog/products/data-analytics/bigquery-measures-ga-unifying-bi-metrics-and-knowledge-graphs/](https://cloud.google.com/blog/products/data-analytics/bigquery-measures-ga-unifying-bi-metrics-and-knowledge-graphs/)

<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">To answer a complex business question, an AI agent must understand two things: </span><span style="font-style: italic; vertical-align: baseline;">what</span><span style="vertical-align: baseline;"> happened, and </span><span style="font-style: italic; vertical-align: baseline;">why</span><span style="vertical-align: baseline;">. The </span><span style="font-style: italic; vertical-align: baseline;">what</span><span style="vertical-align: baseline;"> is a governed metric, like revenue at risk; the </span><span style="font-style: italic; vertical-align: baseline;">why</span><span style="vertical-align: baseline;"> is the network of relationships that produced it. Because metric definitions, a.k.a. measures, traditionally live in business intelligence (BI) platforms while relationships live in knowledge graphs, an AI agent only ever sees half the picture. It guesses the rest, leading to confident but sometimes wrong answers. To solve this hallucination problem, </span><a href="https://cloud.google.com/blog/products/data-analytics/bigquery-graphs-with-measures-for-trusted-agentic-workloads"><span style="text-decoration: underline; vertical-align: baseline;">we introduced measures in BigQuery</span></a><span style="vertical-align: baseline;">, which are now generally available.</span></p>
<p><span style="vertical-align: baseline;">Historically, organizations needing both BI and knowledge graphs had to run two siloed technology stacks: one to calculate reliable metrics, the other to map out entity relationships. Bridging them entailed brittle data pipelines and runtime reconciliation by analysts and AI agents, who held the connections in their heads or in sprawling prompts. This patchwork approach wasn't just slow and expensive — it’s where data governance broke down, as every analyst and prompt may define joins and metrics differently.</span></p></div>

<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">To replace manual reconciliation, you need a single model that understands both the structure of your business and the math that measures it. BigQuery measures builds directly on </span><a href="https://cloud.google.com/blog/products/data-analytics/bigquery-graph-connecting-data-and-ai-at-scale"><span style="text-decoration: underline; vertical-align: baseline;">BigQuery Graph</span></a><span style="vertical-align: baseline;"> to deliver that unified foundation. By defining measures directly on the graph entities they describe, your BI dashboards and AI agents don't just get a number they can trust — they get the relational context behind it. Finally, they can reliably answer both the </span><span style="font-style: italic; vertical-align: baseline;">what</span><span style="vertical-align: baseline;"> and the </span><span style="font-style: italic; vertical-align: baseline;">why</span><span style="vertical-align: baseline;">.</span></p>

Defining measures natively in BigQuery ensures Looker Dashboards, Conversational Agents and our Data team queries operate on identical logic, guaranteeing metric alignment across leadership and significantly reducing data team maintenance overhead."</span><span style="vertical-align: baseline;"> - Amanda Reelick, Head of Data Enablement, Woolworths NZ</span></p>
<h3><strong style="vertical-align: baseline;">One model to answer both the </strong><strong style="font-style: italic; vertical-align: baseline;">what </strong><strong style="vertical-align: baseline;">and the </strong><strong style="font-style: italic; vertical-align: baseline;">why</strong></h3>
<p><span style="vertical-align: baseline;">Let's walk through an example. Suppose your retail bank's risk analytics team spots a sudden spike in transaction activity in the Prague district. You need to know whether this represents healthy customer growth or concentrated risk exposure. Answering requires two pieces of evidence: how much money actually moved (the </span><span style="font-style: italic; vertical-align: baseline;">what</span><span style="vertical-align: baseline;">), and which specific accounts it flowed through (the </span><span style="font-style: italic; vertical-align: baseline;">why</span><span style="vertical-align: baseline;">). At most banks, getting that answer takes two teams, two tools, and two numbers that are rarely reconciled.</span></p>
<p><span style="vertical-align: baseline;">With BigQuery, your underlying data is already in place — whether in native tables or in a</span> <a href="https://docs.cloud.google.com/lakehouse/docs/introduction"><span style="text-decoration: underline; vertical-align: baseline;">borderless Lakehouse</span></a><span style="vertical-align: baseline;">. With a single schema, you can define a semantic model directly over your existing transaction, account, and district tables — with no data movement and no secondary system:</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &#x27;-- Entities, relationships, and measures, declared in one model\r\nCREATE OR REPLACE PROPERTY GRAPH retail_banking.BankingGraph\r\n  NODE TABLES (\r\n    retail_banking.trans AS Trans\r\n      KEY (trans_id)\r\n      PROPERTIES (\r\n        trans_id, account_id, amount,\r\n        MEASURE(SUM(amount)) AS total_trans_amount\r\n      ),\r\n    retail_banking.account AS Account\r\n      KEY (account_id)\r\n      PROPERTIES (\r\n        account_id, district_id, stmt_frq,\r\n        MEASURE(COUNT(account_id)) AS account_count\r\n      ),\r\n    retail_banking.district AS District\r\n      KEY (district_id)\r\n      PROPERTIES (district_id, city, state)\r\n  )\r\n  EDGE TABLES (\r\n    retail_banking.trans AS POSTED_TO\r\n      KEY (trans_id)\r\n      SOURCE KEY (trans_id) REFERENCES Trans (trans_id)\r\n      DESTINATION KEY (account_id) REFERENCES Account (account_id)\r\n      NO PROPERTIES,\r\n    retail_banking.account AS LOCATED_IN\r\n      KEY (account_id)\r\n      SOURCE KEY (account_id) REFERENCES Account (account_id)\r\n      DESTINATION KEY (district_id) REFERENCES District (district_id)\r\n      NO PROPERTIES\r\n  );&#x27;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f126df9ab50&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">To determine whether the Prague spike reflects broad growth or concentrated exposure, your team checks whether the transaction volume is spread across many accounts or driven by just a few. Using </span><code style="vertical-align: baseline;">GRAPH_EXPAND</code><span style="vertical-align: baseline;">, you flatten the graph and roll up both measures with the </span><code style="vertical-align: baseline;">AGG()</code><span style="vertical-align: baseline;"> function:</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &#x27;-- Volume by city, and the accounts behind it, each counted once\r\nSELECT\r\n  District_city,\r\n  AGG(Trans_total_trans_amount) AS total_volume,\r\n  AGG(Account_account_count)    AS accounts_involved\r\nFROM GRAPH_EXPAND(&quot;retail_banking.BankingGraph&quot;)\r\nGROUP BY District_city;&#x27;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f126df98ed0&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">You can ensure accurate reporting by using measures that have been “grain-locked” — where a fixed level of granularity has been assigned to how facts and dimensions are modeled. Because a single account can have thousands of transactions, joining the two tables can duplicate account rows. A standard SQL </span><code style="vertical-align: baseline;">COUNT(account_id)</code><span style="vertical-align: baseline;"> would overcount those accounts, leaving your risk and finance teams with conflicting numbers. BigQuery measures preserve the native grain of each entity, counting every account only once regardless of how the tables are joined.</span></p>
<p><span style="vertical-align: baseline;">The second half of the investigation is about connectivity: Which accounts are driving the Prague activity? You can answer that with a traversal in GQL (the ISO-standard Graph Query Language) over the exact same model:</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &quot;-- Which accounts moved money in Prague\r\nGRAPH retail_banking.BankingGraph\r\nMATCH (:Trans)-[:POSTED_TO]-&gt;(a:Account)-[:LOCATED_IN]-&gt;(d:District)\r\nWHERE d.city = &#x27;Prague&#x27;\r\nRETURN DISTINCT a.account_id&quot;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f126df9a790&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">Neither query requires a separate system, and both evaluate against the same governed definitions.</span></p>
<h3><strong style="vertical-align: baseline;">New features in BigQuery measures</strong></h3>
<p><span style="vertical-align: baseline;">While the preview introduced grain-locked measures tightly integrated with BigQuery Graph, real-world production analytics demand more than basic sums — and enterprise AI agents need programmatic ways to discover and interpret those metrics. The GA of BigQuery measures focuses on two key areas: richer modeling and visualization for complex business logic, and native semantic discovery for the agentic ecosystem.</span></p>
<h4><span style="vertical-align: baseline;">Richer modeling, querying and BI visualization</span></h4>
<p><span style="vertical-align: baseline;">To enable more expressive and flexible measure definitions, </span><code style="vertical-align: baseline;">MEASURE()</code><span style="vertical-align: baseline;"> supports both composite expressions and derived measures; this capability is GA. Rather than repeating conditional logic across queries, you can define baseline aggregates once and compose them into higher-order calculations on the same table using </span><code style="vertical-align: baseline;">AGG()</code><span style="vertical-align: baseline;">. BigQuery validates these formula dependencies at schema compilation time to catch circular references or invalid aggregations early. Downstream dashboards and AI agents can then query complex ratios and net metrics at any dimensionality with consistent accuracy.</span></p>
<p><span style="vertical-align: baseline;">For example, on your </span><code style="vertical-align: baseline;">Trans</code><span style="vertical-align: baseline;"> node, you can define settled volume alongside total volume, and then derive unsettled volume and unsettled percentage directly from those building blocks:</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &#x27;-- Compose custom calculations, conditional expressions, and derived ratios\r\nPROPERTIES (\r\n  trans_id, account_id, amount, fee, is_settled,\r\n  MEASURE(SUM(amount)) AS total_trans_amount,\r\n  MEASURE(SUM(CASE WHEN is_settled = TRUE THEN amount ELSE 0.0 END))\r\n    AS settled_volume,\r\n  MEASURE(AVG(CASE WHEN amount &gt; 10000 THEN amount ELSE NULL END))\r\n    AS avg_large_trans,\r\n  -- Derived: written in terms of the measures above\r\n  MEASURE(AGG(total_trans_amount) - AGG(settled_volume)) AS unsettled_volume,\r\n  MEASURE(\r\n    SAFE_DIVIDE(AGG(total_trans_amount) - AGG(settled_volume),\r\n                NULLIF(AGG(total_trans_amount), 0)) * 100.0\r\n  ) AS unsettled_pct\r\n)&#x27;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f126df983d0&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><p><strong style="vertical-align: baseline;">Query across multiple fact tables</strong></p>
<p><span style="vertical-align: baseline;">Enterprise data models routinely span multiple business processes. Joining separate fact tables that share a common dimension — such as transactions and credit cards linked to the same bank account — traditionally causes a "chasm trap," where cross-fact multiplication inflates both metrics.</span></p>
<p><span style="vertical-align: baseline;">The new </span><code style="vertical-align: baseline;">start_node</code><span style="vertical-align: baseline;"> argument in </span><code style="vertical-align: baseline;">GRAPH_EXPAND</code><span style="vertical-align: baseline;"> solves this by isolating each fact table into its own expansion tree. BigQuery evaluates each measure at its native grain before joining the results on the shared entity:</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &#x27;-- Transactions and cards per account, each evaluated at its own root grain\r\nSELECT\r\n  ET.Account_account_id,\r\n  AGG(ET.Trans_settled_volume) AS settled_volume,\r\n  AGG(EC.Card_card_count)      AS total_cards_issued\r\nFROM\r\n  GRAPH_EXPAND(&quot;retail_banking.BankingGraph&quot;, start_node =&gt; &quot;Trans&quot;) AS ET\r\nLEFT JOIN\r\n  GRAPH_EXPAND(&quot;retail_banking.BankingGraph&quot;, start_node =&gt; &quot;Card&quot;) AS EC\r\nON ET.Account_account_id = EC.Account_account_id\r\nGROUP BY ET.Account_account_id;&#x27;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f126df99190&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">By expanding each fact table from its own root (</span><code style="vertical-align: baseline;">Trans</code><span style="vertical-align: baseline;"> and </span><code style="vertical-align: baseline;">Card</code><span style="vertical-align: baseline;">), each branch maintains its exact grain — even for accounts with transactions but no issued cards.</span></p>
<p><strong style="vertical-align: baseline;">Visualize in Data Studio </strong></p>
<p><span style="vertical-align: baseline;">With the updated BigQuery connector in </span><a href="https://cloud.google.com/data-studio"><span style="text-decoration: underline; vertical-align: baseline;">Data Studio</span></a><span style="vertical-align: baseline;">, you can now connect directly to BigQuery graphs and build interactive visualizations powered by native measures. Data Studio honors the aggregation logic defined in your graph model, keeping complex calculations consistent across charts while preventing accidental client-side re-aggregations.</span></p></div>

<p><strong style="vertical-align: baseline;">Attach business meaning to your measures</strong></p>
<p><span style="vertical-align: baseline;">In a large enterprise schema, it’s nice to be able to attach business meaning to your measures, as multiple metrics often share similar names. In our banking model alone, </span><code style="vertical-align: baseline;">total_trans_amount</code><span style="vertical-align: baseline;">, </span><code style="vertical-align: baseline;">settled_volume</code><span style="vertical-align: baseline;">, and </span><code style="vertical-align: baseline;">unsettled_volume</code><span style="vertical-align: baseline;"> could all casually be called "volume" by a business user. <p><span style="vertical-align: baseline;">With the GA, you can embed rich semantic metadata directly into each measure definition using the </span><code style="vertical-align: baseline;">OPTIONS</code><span style="vertical-align: baseline;"> clause, including plain-language description strings, domain synonyms, and custom key-value extensions:</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &quot;-- Business meaning and governance metadata travel with the metric\r\nMEASURE(SUM(CASE WHEN is_settled = TRUE THEN amount ELSE 0.0 END)) \r\n  AS settled_volume\r\n  OPTIONS (\r\n    description = &#x27;Transaction value that settled. </dl></div>

<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">Engineer for failure modes in your verification pipeline. If your harness only searches for a successful exploit string, then any test failure — such as a crashed mock server or an execution timeout — can cause the pipeline to fail open and mistakenly label a real vulnerability as safe. </span></p>
<p><span style="vertical-align: baseline;">Ensure your parser separates true negative results from test crashes. If an exploit fails to complete cleanly, flag the status as inconclusive rather than giving it a clean bill of health.</span></p>

<h3><span style="vertical-align: baseline;">No stored keys between GitHub and Cloud Run</span></h3>
<p><span style="vertical-align: baseline;">None of this happens until GitHub and Google Cloud trust each other. This agent needs write access to your source code, precisely the credential you don't want sitting in a secret store waiting to leak. GitHub Actions can mint a short-lived OIDC token instead, and Google can be configured to accept it, so nothing long-lived exists to steal.</span></p>
<p><span style="vertical-align: baseline;">Nearly all the security here rests on one line:</span></p></div>

    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &#x27;resource &quot;google_iam_workload_identity_pool_provider&quot; &quot;github&quot; {\r\n  workload_identity_pool_provider_id = &quot;github-provider&quot;\r\n\r\n  oidc {\r\n    issuer_uri = &quot;https://token.actions.githubusercontent.com&quot;\r\n  }\r\n\r\n  attribute_mapping = {\r\n    &quot;google.subject&quot;          = &quot;assertion.sub&quot;\r\n    &quot;attribute.repository_id&quot; = &quot;assertion.repository_id&quot;\r\n  }\r\n\r\n  # Without this, any repository on GitHub can exchange a token against your pool\r\n  attribute_condition = &quot;assertion.repository_id == \&#x27;123456789\&#x27;&quot;\r\n}&#x27;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f126dbedd50&gt;)])]&gt;</dd>

<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">Every GitHub Actions workflow shares that issuer URL, so validating the issuer alone buys you nothing. The condition is the part doing the work.</span></p>
<p><span style="vertical-align: baseline;">Note what it matches on. </span><code style="vertical-align: baseline;">assertion.repository</code><span style="vertical-align: baseline;"> would also work here, but it matches a name and names get renamed, or claimed by someone else once you release them. </span><code style="vertical-align: baseline;">repository_id</code><span style="vertical-align: baseline;"> and </span><code style="vertical-align: baseline;">repository_owner_id</code><span style="vertical-align: baseline;"> are immutable, which is why Google recommends mapping those instead.</span></p>
<h3><span style="vertical-align: baseline;">Give the exploit somewhere safe to run</span></h3>
<p><span style="vertical-align: baseline;">Verification runs attack code that nobody reviewed, written on demand, pointed at a mock target, doing what the vulnerability class implies. As recent headlines have reminded everyone, the last thing you want is an autonomous agent deciding the fastest way to complete a task is to break out of its container and port-scan your internal network. </span></p>
<p><span style="vertical-align: baseline;">Before you can trust the verdict, you have to answer two important questions: Where does that code execute, and what can it reach while it does? The answer is to run it as a Cloud Run job. </span></p>
<p><span style="vertical-align: baseline;">Every Cloud Run instance is sandboxed, and jobs always run in the second-generation execution environment, a microVM with full Linux compatibility. The execution starts, does one thing, and exits.</span></p></div>

It needs no registry access, because Cloud Run imports the container image when you deploy rather than pulling it at the instance start. </span></p>
<p><span style="vertical-align: baseline;">Skip the Compute Engine default account, which may carry </span><code style="vertical-align: baseline;">roles/editor</code><span style="vertical-align: baseline;"> depending on your organization policy. Take the network away too: Direct VPC egress into a subnet with no route out means code that can't call anywhere can't exfiltrate what it finds or fetch a second stage. </span></p>
<p><span style="vertical-align: baseline;">Run one job per finding. The execution ends, the instance goes with it, and the verdict is the only thing that outlives either.</span></p>

In the instance, process execution is isolated from the parent workload, its environment variables, its secrets, and the Google Cloud metadata server, so the credential the platform hands out by default is out of reach as well. It's built for agents running code they just wrote.</span></p>
