<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">When database engineers hear “database migration", they typically think of a one-time onboarding pathway—moving databases from on-premises environments to the cloud, or between different cloud providers.</span></p>
<p><span style="vertical-align: baseline;">However, Google Cloud's </span><a href="https://cloud.google.com/database-migration"><span style="text-decoration: underline; vertical-align: baseline;">Database Migration Service</span></a><span style="vertical-align: baseline;"> (DMS) supports </span><a href="https://medium.com/google-cloud/optimize-cloud-sql-for-sql-server-with-database-migration-service-f2a399ea6e07" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Cloud SQL for SQL Server as a source</span></a><span style="vertical-align: baseline;">. This opens up powerful, non-traditional operational patterns for SQL Server customers within Google Cloud. Because DMS enables continuous, low-downtime database replication between Cloud SQL instances—whether in the same project, across different projects, or across regions—it can serve as an everyday utility for day-two operations like storage management.</span></p>
<p><span style="vertical-align: baseline;">In this post, we explore a compelling operational use case for DMS with Cloud SQL for SQL Server: executing disk shrinks with minimal application downtime.</span></p>
<h3><strong style="vertical-align: baseline;">Why should I shrink my disk?</strong></h3>
<p><span style="vertical-align: baseline;">In many production environments, database storage only moves in one direction: up. Features like Cloud SQL </span><a href="https://docs.cloud.google.com/sql/docs/sqlserver/instance-settings#automatic-storage-increase-2ndgen"><span style="text-decoration: underline; vertical-align: baseline;">automatic storage increase</span></a><span style="vertical-align: baseline;"> are essential for preventing out-of-space outages during unexpected traffic spikes, large batch imports, index maintenance, or temporary staging loads. Similarly, over the lifecycle of an application, you might archive historical records, purge obsolete data, or drop unused indexes.</span></p>
<p><span style="vertical-align: baseline;">When data is deleted, SQL Server marks the freed space inside your data files (.mdf, .ndf) as reusable for future writes; similarly, log truncation frees up space within transaction log files (.ldf). However, the database files themselves continue to hold their peak used space unless AUTO_SHRINK is configured — a setting that is generally not recommended in production due to severe index fragmentation and performance overhead.</span></p>
<p><span style="vertical-align: baseline;">With a manual shrink operation on the database files using </span><a href="https://learn.microsoft.com/en-us/sql/t-sql/database-console-commands/dbcc-shrinkfile-transact-sql?view=sql-server-ver17" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">DBCC SHRINKFILE</span></a><span style="vertical-align: baseline;">, you can release that unused space from SQL Server files back to the underlying disk. Even after shrinking the database files, though, the Cloud SQL persistent disk remains at its peak allocated capacity. If you do not expect your database to grow back into that allocated disk space anytime soon, you should consider shrinking the disk itself to reduce ongoing storage costs — especially in scenarios such as:</span></p>
<p><strong style="vertical-align: baseline;">After major data archiving or purging:</strong><span style="vertical-align: baseline;"> You have permanently moved historical data to cold storage or BigQuery and your active dataset is now a fraction of its peak size.</span></p>
<p><strong style="vertical-align: baseline;">Recovering from one-time storage spikes:</strong><span style="vertical-align: baseline;"> A runaway transaction, large data migration, or temporary staging load triggered storage auto-increase, leaving you paying for terabytes of provisioned disk capacity you no longer need.</span></p>
<p><strong style="vertical-align: baseline;">Post-refactoring or schema optimization:</strong><span style="vertical-align: baseline;"> You have split tables out of a monolithic database into separate services, dropped large unused indexes, or applied data compression.</span></p>
<p><span style="vertical-align: baseline;">The query below allows you to inspect both the allocated capacity and available free space for each database file fo a database:</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &quot;SELECT \r\n    DB_NAME() AS [DatabaseName],\r\n    name AS [LogicalName],\r\n    type_desc AS [FileType],\r\n    -- Allocated size on disk (converted from 8KB pages to MB)\r\n    CAST(size / 128.0 AS DECIMAL(18, 2)) AS [AllocatedSize_MB], \r\n    -- Actually used space inside the file\r\n    CAST(FILEPROPERTY(name, &#x27;SpaceUsed&#x27;) / 128.0 AS DECIMAL(18, 2)) AS [UsedSpace_MB], \r\n    -- Free space left in the allocated file\r\n    CAST((size - FILEPROPERTY(name, &#x27;SpaceUsed&#x27;)) / 128.0 AS DECIMAL(18, 2)) AS [FreeSpace_MB],    \r\n    -- Percentage of allocated space that is used\r\n    CAST((FILEPROPERTY(name, &#x27;SpaceUsed&#x27;) * 100.0) / size AS DECIMAL(18, 2)) AS [SpaceUsed_Percent]\r\nFROM sys.database_files;&quot;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f85e4d45310&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">You can monitor the following key Cloud SQL metrics in Cloud Monitoring to identify whether your provisioned disk quota significantly exceeds actual disk usage, indicating an opportunity for disk shrinking:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><code style="vertical-align: baseline;">database/disk/bytes_used</code><span style="vertical-align: baseline;">: Tracks the actual amount of disk space currently consumed by your database files and logs.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><code style="vertical-align: baseline;">database/disk/quota</code><span style="vertical-align: baseline;">: Represents the total provisioned disk capacity allocated to your instance.</span></p>
</li>

<p><span style="vertical-align: baseline;">Cloud SQL provides a built-in </span><a href="https://docs.cloud.google.com/sql/docs/sqlserver/about-storage-shrink"><span style="text-decoration: underline; vertical-align: baseline;">storage shrink feature</span></a><span style="vertical-align: baseline;"> to reclaim this unallocated disk space, which works well when your workload can tolerate a planned maintenance window. However, native disk shrinking requires instance downtime proportional to the total allocated disk size — which can mean hours of offline maintenance for multi-terabyte drives.</span></p>
<p><span style="vertical-align: baseline;">If your production SLAs cannot accommodate extended downtime, Database Migration Service (DMS) offers a minimal-downtime alternative. By continuously replicating your databases to a newly provisioned Cloud SQL instance with a smaller, right-sized disk, you can reclaim unused storage while your application stays online — requiring only a brief cutover window. To understand why this approach keeps your cutover window so short, let's first look at how DMS replicates data between Cloud SQL for SQL Server instances under the hood.</span></p>

<p><span style="vertical-align: baseline;">To leverage DMS effectively, it helps to understand its underlying replication mechanism. When migrating between Cloud SQL for SQL Server instances, DMS coordinates a synchronization process similar to native SQL Server log shipping.</span></p></div>

<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">As shown in the comparison above, because DMS migrates your workload to a new instance at the user-database level, a smooth cutover requires migrating your server-level objects and user mappings alongside your data. Let's look at the essential pre- and post-cutover steps to include in your runbook.</span></p>
<h3><strong style="vertical-align: baseline;">Pre and post-cutover essentials: Going beyond database replication </strong></h3>
<h4><span style="vertical-align: baseline;">Pre-cutover preparation: Migrating server-level objects</span></h4>
<p><span style="vertical-align: baseline;">Because DMS operates at the user-database level, server-level objects are not automatically replicated. You will need to create them manually in the destination instance before the cutover.</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">Script out logins from the source using </span><a href="https://docs.cloud.google.com/sql/docs/sqlserver/export-logins"><code style="text-decoration: underline; vertical-align: baseline;">sp_help_revlogin</code></a><span style="vertical-align: baseline;"> and recreate them on the target instance.</span></p>
</li>
</ul>
<ul>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">SQL Server Agent jobs &amp; Server-Level objects: Because DMS replicates databases rather than server instance state, objects outside user databases must be scripted from the source and deployed to the destination Cloud SQL instance. In SQL Server Management Studio (SSMS), connect to your source instance, navigate to the object in Object Explorer, right-click and select </span><code style="vertical-align: baseline;">Script [Object] as &gt; CREATE To &gt; New Query Window / File</code><span style="vertical-align: baseline;">:</span></p>
<ul>
<li><span style="vertical-align: baseline;">SQL Server Agent jobs (</span><code style="vertical-align: baseline;">SQL Server Agent &gt; Jobs</code><span style="vertical-align: baseline;">): Inspect generated scripts to ensure job steps do not reference on-premises file paths or unsupported OS dependencies.</span></li>
<li><span style="vertical-align: baseline;">Linked servers (</span><code style="vertical-align: baseline;">Server Objects &gt; Linked Servers</code><span style="vertical-align: baseline;">): Follow the exact same scripting approach. Ensure you enable the </span><code style="vertical-align: baseline;">cloudsql.linked_servers</code><span style="vertical-align: baseline;"> database flag on your Cloud SQL instance before deploying.</span></li>
<li><span style="vertical-align: baseline;">Extended events (</span><code style="vertical-align: baseline;">Management &gt; Extended Events &gt; Sessions</code><span style="vertical-align: baseline;">): Follow the same scripting approach. </span></li>
</ul>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">For TDE enabled instances, you will need to </span><a href="https://docs.cloud.google.com/sql/docs/sqlserver/use-tde#export-tde-certificate"><span style="text-decoration: underline; vertical-align: baseline;">export the TDE certificate</span></a><span style="vertical-align: baseline;"> from source and </span><a href="https://docs.cloud.google.com/sql/docs/sqlserver/use-tde#import-external-tde-certificate"><span style="text-decoration: underline; vertical-align: baseline;">import the TDE certificate</span></a><span style="vertical-align: baseline;"> to destination before. </span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">Instance Configurations (such as database flags, Active Directory, Entra ID configurations etc): These must be manually configured on the destination instance to exactly match the source settings.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">If using Polybase you will need to</span> <a href="https://docs.cloud.google.com/sql/docs/sqlserver/configure-external-data-sources#manage-the-dmk"><span style="text-decoration: underline; vertical-align: baseline;">re-encrypt DMK</span></a><span style="vertical-align: baseline;"> for the database-scoped credentials to function correctly.</span></p>
</li>
</ul>
<h4><span style="vertical-align: baseline;">Post-cutover remediation: Resolving orphaned database users</span></h4>
<p><span style="vertical-align: baseline;">Database users mapped to SQL Server logins that are either absent or misconfigured on a server instance are unable to authenticate. These are termed </span><span style="font-style: italic; vertical-align: baseline;">orphaned users</span><span style="vertical-align: baseline;">. Because logins created on the destination instance will possess unique Security Identifiers (SIDs) that do not match the source SIDs preserved in your migrated databases, users will be orphaned by default. Addressing this requires manual re-mapping once the target database is brought online following the cutover.</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">Detecting &amp; re-mapping orphaned users: While using </span><a href="https://docs.cloud.google.com/sql/docs/sqlserver/export-logins"><span style="text-decoration: underline; vertical-align: baseline;">sp_help_revlogin</span></a><span style="vertical-align: baseline;"> preserves SIDs during login migration, creating logins on the destination instance via alternative methods generates new server-level SIDs. Because these differ from the source SIDs retained in the DMS-restored user databases, database users become orphaned after cutover and require re-mapping.</span></p>
</li>
</ul>
<p style="padding-left: 80px;"><span style="vertical-align: baseline;">1. Detect orphaned users: Connect to each destination user database and run the diagnostic query from Microsoft's official </span><a href="https://learn.microsoft.com/en-us/sql/sql-server/failover-clusters/troubleshoot-orphaned-users-sql-server?view=sql-server-ver17#detect-orphaned-users" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Troubleshoot Orphaned Users Guide</span></a><span style="vertical-align: baseline;">:</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &quot;SELECT dp.type_desc, dp.sid, dp.name AS user_name\r\nFROM sys.database_principals AS dp\r\nLEFT JOIN sys.server_principals AS sp ON dp.sid = sp.sid\r\nWHERE sp.sid IS NULL AND dp.authentication_type_desc = &#x27;INSTANCE&#x27;;&quot;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f85e4d45110&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><p style="padding-left: 80px;"><span style="vertical-align: baseline;">2. Fix orphaned users (</span><code style="vertical-align: baseline;">ALTER USER</code><span style="vertical-align: baseline;">): For each unlinked database user returned by the query, execute the following statement inside the context of that database to cleanly re-map the principal and its permissions to the new Cloud SQL server login:</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &#x27;ALTER USER [user_name] WITH LOGIN = [login_name];&#x27;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f85e4d46290&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><h3><strong style="vertical-align: baseline;">Summary and next steps</strong></h3>
<p><span style="vertical-align: baseline;">DMS is more than a one-time bridge from on-premises environments into Google Cloud — it is a versatile tool for day-two operations in the Cloud SQL engineer's toolkit. When strict production SLAs prevent you from taking lengthy maintenance windows for a native disk shrink, DMS provides a reliable, managed replication pipeline to right-size your storage footprint and reduce infrastructure costs with minimal downtime.</span></p>

### Five rules for evaluating agent skills before they bloat your context window

- **Link**: [https://cloud.google.com/blog/topics/developers-practitioners/evaluate-agent-skills-before-they-bloat-your-context-window/](https://cloud.google.com/blog/topics/developers-practitioners/evaluate-agent-skills-before-they-bloat-your-context-window/)

<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">You’re probably hearing more about SKILL.md files, and you’ll see that a lot of people test them the same way: paste a prompt into chat, watch it pass once on a laptop, and merge to main. But when you paste three pages of CLI docs into a markdown file without an evaluation loop, you are just as likely to confuse a frontier model as you are to help it.</span></p>
<p><span style="vertical-align: baseline;">For the past weeks, we have been diligently measuring and optimizing our own </span><a href="https://cloud.google.com/blog/topics/developers-practitioners/introducing-the-google-cloud-developer-plugin-for-ai-coding-agents"><span style="text-decoration: underline; vertical-align: baseline;">Google Cloud Developer Plugin</span></a><span style="vertical-align: baseline;">, with the most essential skills and the Developer Knowledge MCP server to ground responses in the documentation.</span></p>
<p><span style="vertical-align: baseline;">We </span><a href="https://x.com/kweinmeister/status/2099962972798153194" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">ran dozens of scenarios</span></a><span style="vertical-align: baseline;"> with Gemini, Antigravity, and other agents. We used </span><strong style="vertical-align: baseline;">Claude Sonnet 5 on Gemini platform</strong><span style="vertical-align: baseline;"> inside isolated </span><strong style="vertical-align: baseline;">Harbor</strong><span style="vertical-align: baseline;"> pods on </span><strong style="vertical-align: baseline;">GKE Autopilot</strong><span style="vertical-align: baseline;">. And, we contributed Kubernetes and Gemini platform capabilities upstream to NVIDIA's open-source evaluator. </span></p>
<p><span style="vertical-align: baseline;">Here's the five-rule engineering playbook we use to verify a skill is worth its tokens.</span></p>
<h2><span style="vertical-align: baseline;">1. Gate trigger collisions and security risks before spinning up containers</span></h2>
<p><span style="vertical-align: baseline;">When an evaluation run shows zero improvement between your plugin arm and your baseline arm (</span><span style="vertical-align: baseline;">Δ = 0</span><span style="vertical-align: baseline;">), the natural urge is to rewrite the body of your SKILL.md instructions. Hold off on that. Nine times out of ten, </span><strong style="vertical-align: baseline;">the agent never loaded your skill in the first place</strong><span style="vertical-align: baseline;">.</span></p>
<p><span style="vertical-align: baseline;">Coding agents do not read full SKILL.md bodies at turn zero. The router only inspects the short name and description in your YAML frontmatter. Once a workspace grows past a dozen skills, two failure modes collide: under-triggering (your description describes internal implementation rather than developer intent) and sibling hijacking (a broad phrase like "helps with cloud deployments" in a neighboring skill intercepts the prompt first).</span></p>
<p><span style="vertical-align: baseline;">We recently open-sourced </span><a href="https://google.github.io/skill-reach/" rel="noopener" target="_blank"><strong style="text-decoration: underline; vertical-align: baseline;">skill-reach</strong></a><span style="vertical-align: baseline;"> so you can catch frontmatter collisions before spending on container sandboxes. It validates manifests, computes vocabulary overlap against nearest rival skills, and runs empirical routing probes across Claude Code, Google Antigravity, and OpenAI Codex:</span></p></div>

<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">When you connect an evaluation harness to an automated optimizer (like </span><a href="https://docs.cloud.google.com/gemini/enterprise/docs/alphaevolve/developer-guide/overview"><span style="text-decoration: underline; vertical-align: baseline;">AlphaEvolve</span></a><span style="vertical-align: baseline;"> or </span><span style="vertical-align: baseline;">reach optimize</span><span style="vertical-align: baseline;">), it is a surprisingly common pattern for the </span><strong style="vertical-align: baseline;">agent to cheat the grader</strong><span style="vertical-align: baseline;">.</span></p>
<p><span style="vertical-align: baseline;">In our AlphaEvolve retrieval experiments, evolved candidates discovered </span><strong style="vertical-align: baseline;">four distinct ways to game the benchmark without solving the task</strong><span style="vertical-align: baseline;">. When the grading harness blocked specific expected substring checks in source code, an evolved candidate dynamically concatenated strings at runtime, traversed up the directory tree, and read the ground-truth answer file directly off disk. Another candidate spawned subprocesses to bypass AST checks.</span></p>
<p><span style="vertical-align: baseline;">The evolutionary loop favored those cheaters because the fitness formula blended correctness (0.95 weight) and token efficiency (0.05 weight) into a single score. Reading the answer file from disk takes </span><strong style="vertical-align: baseline;">no LLM turns</strong><span style="vertical-align: baseline;">, earning an efficiency bonus that gives cheaters a </span><strong style="vertical-align: baseline;">survival advantage</strong><span style="vertical-align: baseline;"> over honest agents that spent tokens searching the repository.</span></p>
<p><span style="vertical-align: baseline;">Hardening your skill evaluator against reward-hacking takes three structural guardrails. First, configure Harbor so your test fixtures, grading scripts, and answer keys live inside a dedicated verifier container that mounts workspace artifacts only after the agent container exits. Second, keep SkillEvaluator's five dimensions (</span><strong style="vertical-align: baseline;">Correctness</strong><span style="vertical-align: baseline;">, </span><strong style="vertical-align: baseline;">Discoverability</strong><span style="vertical-align: baseline;">, </span><strong style="vertical-align: baseline;">Efficiency</strong><span style="vertical-align: baseline;">, </span><strong style="vertical-align: baseline;">Effectiveness</strong><span style="vertical-align: baseline;">, and </span><strong style="vertical-align: baseline;">Security</strong><span style="vertical-align: baseline;">) strictly orthogonal; never let token thrift compensate for a failed test or a security violation. Third, in </span><a href="https://github.com/NVIDIA/SkillEvaluator/pull/140" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">NVIDIA/SkillEvaluator#140</span></a><span style="vertical-align: baseline;">, we extended security checks to fail any trial that reads Kubernetes service account tokens or queries cloud metadata endpoints, while redacting live OAuth tokens from saved trajectories.</span></p>

<p><span style="vertical-align: baseline;">Skills that copy-paste public API reference tables into skill files yield almost no lift. Frontier models already have public cloud docs in their pretraining weights; dumping thousands of words of static flags into the prompt just inflates time-to-first-token and buries actionable constraints.</span></p>

</li>
<li style="vertical-align: baseline;">

</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Enforce least-privilege auth defaults:</strong><span style="vertical-align: baseline;"> Explicit guardrails instruct agents to authenticate via Application Default Credentials rather than downloading static service-account JSON keys, while enforcing unauthenticated access restrictions alongside explicit invoker IAM bindings.</span></p>
</li>
</ol>

Deleting a skill because the new model graduated past it is one of the cleanest high-fives in software engineering.</span></p>

### Introducing Physical-Engineering’s Last Exam for agents

- **Link**: [https://cloud.google.com/blog/products/ai-machine-learning/introducing-physical-engineerings-last-exam-for-agents/](https://cloud.google.com/blog/products/ai-machine-learning/introducing-physical-engineerings-last-exam-for-agents/)

<details class="entry-summary">
<summary>詳細を表示</summary>
<div class="block-paragraph_advanced"><p><span style="font-style: italic; vertical-align: baseline;">Authors: Burak Gokturk, VP Research &amp; Development; Rujun Han, Research Scientist; George Lee, Product Manager.</span></p>
<hr />
<p><span style="vertical-align: baseline;">Today, the </span><a href="http://aiinfra.google" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Google AI &amp; Infrastructure</span></a><span style="vertical-align: baseline;"> team is announcing <strong>Physical-Engineering's Last Exam (PLE)</strong>, a new benchmark and open competition, developed in collaboration with Mercor, and built to test a frontier model’s ability to complete tasks in mechanical, electrical, civil and structural engineering. </span></p>
<p><span style="vertical-align: baseline;">To help the research community measure and improve how agents handle physical engineering work, we are releasing 29 public tasks, their grading tools, and an open competition leaderboard at </span><a href="http://ple-bench.com" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">ple-bench.com</span></a><span style="vertical-align: baseline;">.</span></p>
<p><span style="vertical-align: baseline;">Frontier labs and the broader research community use model examinations to test AI’s progress in completing tasks in a specific discipline. </span><a href="https://lastexam.ai/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Humanity's Last Exam</span></a><span style="vertical-align: baseline;"> measures a model’s general knowledge. </span><a href="https://agents-last-exam.org/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Agents' Last Exam</span></a><span style="vertical-align: baseline;"> measures a model’s ability to complete digital professional work. <strong>Physical-Engineering's Last Exam (PLE)</strong> measures a model’s ability to complete work that helps build the physical world. Physical engineers design skyscrapers, power grids, and computer chips we rely on, yet we could find no existing benchmark that tests whether frontier models can do that work end to end.</span></p>
<h3><span style="vertical-align: baseline;">Why textbook benchmarks fall short for physical engineering</span></h3>
<p><span style="vertical-align: baseline;">Frontier language models now score above 90% on many academic benchmarks. However, those benchmarks mostly test textbook-style questions, single tool calls, or small, self-contained design problems. For AI developers and researchers building agents for physical  engineering, existing benchmarks do not show whether an agent can produce safe, code-compliant, and cost-effective designs under a licensed engineer's review and control. As the </span><a href="https://infrastructurereportcard.org/wp-content/uploads/2025/03/Full-Report-2025-Natl-IRC-WEB.pdf?_gl=1*1timmgv*_up*MQ..*_ga*MzEyMjk2NDYxLjE3OTMwNDg0MTc.*_ga_C9EX6BGYX5*czE3OTMwNDg0MTYkbzEkZzAkdDE3OTMwNDg0MTYkajYwJGwwJGgw" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">demand for infrastructure development outpaces financing</span></a><span style="vertical-align: baseline;">, there is a growing opportunity for agents to support engineers working to close this gap.   </span></p>
<h3><span style="vertical-align: baseline;">Inside PLE: Real-world tasks built with practicing engineers</span></h3>
<p><span style="vertical-align: baseline;">PLE closes this evaluation gap with 85 long-horizon tasks across four core disciplines: </span><strong style="vertical-align: baseline;">mechanical</strong><span style="vertical-align: baseline;"> (30 tasks), </span><strong style="vertical-align: baseline;">electrical</strong><span style="vertical-align: baseline;"> (27 tasks), </span><strong style="vertical-align: baseline;">civil</strong><span style="vertical-align: baseline;"> (18 tasks), and </span><strong style="vertical-align: baseline;">structural</strong><span style="vertical-align: baseline;"> (10 tasks) engineering.</span></p></div>

Our baseline results show a wide gap between current models and real-world engineering requirements:</span></p>

</li>
<li style="vertical-align: baseline;">
