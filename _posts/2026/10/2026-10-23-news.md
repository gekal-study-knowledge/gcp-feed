### Introducing new self-learning context enrichment in Knowledge Catalog

- **Link**: [https://cloud.google.com/blog/products/data-analytics/knowledge-catalog-self-learning-context-enrichment-for-ai-agents/](https://cloud.google.com/blog/products/data-analytics/knowledge-catalog-self-learning-context-enrichment-for-ai-agents/)
- **Published**: 2026-10-23 01:00:00
- **Fetched**: 2026-10-23 03:18:12

<details class="entry-summary">
<summary>詳細を表示</summary>
<div class="block-paragraph"><p>Today, we’re launching self-learning context enrichment (preview) and a reimagined Knowledge Studio experience (preview) in <a href="https://docs.cloud.google.com/knowledge-catalog/docs/introduction">Knowledge Catalog</a>, Google Cloud’s context engine for agents. Building on Knowledge Catalog's existing Gemini-powered enrichment, self-learning enrichment analyzes agent and user interactions to find gaps and keep your business context accurate and current. <a href="https://docs.cloud.google.com/knowledge-catalog/docs/knowledge-studio">Knowledge Studio</a> is the new command center for context engineers and data stewards to explore their data estate conversationally, navigate a visual context graph, and review proposed changes to the context graph before they are published to their users and agents.</p><p>An agent is only as good as the organization-wide definitions, rules, and relationships it reasons over — the context, as it were. That’s why curating context has become one of the most important disciplines in enterprise agentic capabilities. Today, most of that work happens by hand. Context engineers write prompts and mappings agent by agent, while data stewards try to manually keep definitions current across thousands of assets. But this breaks down as organizations move from a handful of agents to thousands, and eventually millions.</p><p>Knowledge Catalog’s Gemini-powered self-learning enrichment turns that manual upkeep into a continuous feedback loop. By analyzing agent and user interactions, it pinpoints missing or outdated context and pulls verified definitions from playbooks, code repositories, and business documents into governed, reusable context sets. Then, with optimized search, every agent gets precisely the right context it needs instead of reasoning over bloated prompts and raw schemas, and benefits from shared learning across your organization. Knowledge Catalog makes AI agents nearly 4X more accurate, with up to 33% lower latency, and using up to 75% fewer tokens, based on internal benchmarks.</p><h3><b>Keep context current with Gemini-powered self-learning enrichment</b></h3><p>Consider a simple question to a Gemini agent: "What was the net revenue in EMEA last quarter?" Answering it correctly requires knowing how your company defines net revenue, which tables hold the bookings, and how they join, yet that knowledge is typically scattered across a finance playbook in Google Docs, a data model in GitHub, and a Confluence page. Static catalogs expect subject matter experts to manually capture and update business definitions, metrics, and other context upfront so that an agent can effectively query the right data. However, in reality, experts rarely have the time to document every asset, and the moment the finance team revises how partner credits are treated next quarter, static definitions fall behind and every agent with a hardcoded formula starts giving the wrong answer.</p><p>Knowledge Catalog’s enrichment capability acts where you already keep your business knowledge: across your team’s every doc, repo, and table. It connects to your structured data across first-party and third-party sources and unstructured data in Cloud Storage, Google Workspace, GitHub, Confluence, and SharePoint. It finds, extracts, assembles, and maintains that business knowledge for you, linking those unstructured sources like playbooks and wikis and their context to your structured metadata in Knowledge Catalog like tables and schemas to make your structured data far more discoverable and actionable. On demand or on a schedule, it proposes business definitions, table and column descriptions, join relationships, golden queries, and task-specific agent instructions, each with source citations and a confidence score. On every run, it detects what changed at the source, retires obsolete definitions, and flags conflicts for review.</p><p>It learns from both your user and agent interactions. You can configure enrichment to analyze interaction traces from Gemini agents, Conversational Analytics in BigQuery, or your custom agents while redacting PII, and it pinpoints where agents struggled, such as ambiguous column lookups, ungrounded metrics, missing definitions, or users rephrasing the same question. It then finds the authoritative answer and stages a fix, so the same mistake doesn't happen twice. That's how context engineering keeps pace with millions of agent interactions, freeing experts to review changes instead of writing them from scratch.</p></div>

<div class="block-paragraph"><h3><b>Set the right context for each audience with context sets</b></h3><p>By design, an enterprise context graph is quite broad, but for a given task, both agents and users often only need the right, trusted segment of it. Knowledge Catalog achieves that with context sets — curated, governed subsets of the context graph that contains the definitions, metrics, join logic, and golden queries for a specific domain, team, agent, or group of end users. For instance, a sales agent can be bound to the Sales context set, while a finance analyst's assistant can be bound to the Finance context set. Because "net revenue" can legitimately mean different things to each group, every domain maintains its own definitions in the same catalog. However, agents don't have to be bound to a single set; with search in Knowledge Catalog, an agent can also dynamically search and find the right context set for any given task.</p><p>Context sets also provide built-in data governance and fine-grained access control. Access to each context set is managed with IAM, so stewards decide which agents and users can read, use, or edit it. Agents only retrieve context from the sets they're authorized to use, and access to the underlying data continues to follow your existing permissions. Every update is traceable, and reversible, and because context sets build on the <a href="https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing">Open Knowledge Format</a> (OKF), you can import an OKF bundle to become a context set and export it back out as OKF so your context stays portable.</p></div>

<h4><strong style="vertical-align: baseline;">ペタバイト規模のパフォーマンスと推論</strong></h4>
<p><span style="vertical-align: baseline;">エージェントのコンテキスト ウィンドウは通常、一度に取り込めるデータ量が数百キロバイトに制限されていますが、エンタープライズ ワークフローでは、複数のクラウドにわたりペタバイト規模のデータを結合することがあります。製品データや顧客データといったさまざまなソースのデータを、CRM クラウドやウェアハウスのテレメトリーと結合する必要があるエージェント ネイティブなデータ プラットフォームは、大規模なデータ処理が可能でなければなりません。MCP を使用してこれを行う場合、コンテキスト ウィンドウとペイロード サイズの制約により、処理の規模がメガバイト単位に制限されます。ボーダーレス Lakehouse は、データと AI スタックをあらゆるレイヤで連携させることで、エンタープライズ グレードのスケーラビリティを提供します。これにより、エージェントはペタバイト規模のデータをローカルに保存されている場合と同様のパフォーマンスで推論できます。</span></p>
<p><span style="vertical-align: baseline;">ネットワーキング レイヤでは、</span><a href="https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/cci-overview"><span style="text-decoration: underline; vertical-align: baseline;">Cross-Cloud Interconnect</span></a><span style="vertical-align: baseline;"> と</span><a href="https://docs.cloud.google.com/lakehouse/docs/about-cross-cloud-data-access"><span style="text-decoration: underline; vertical-align: baseline;">クロスクラウド キャッシュ</span></a><span style="vertical-align: baseline;">により、AWS と Azure への高スループット、低レイテンシのパスが提供され、変動する外向きデータ送信料金が不要になります。エージェントが Amazon や Azure Data Lake Storage の Iceberg テーブルを BigQuery のデータと結合すると、スキャンするキャッシュ保存されていないバイトがすべてクラウドの境界を越えるため、ネットワークにより処理速度が決まります。Cross-Cloud Interconnect は、Google Cloud と AWS または Azure の間に、1 接続あたり 10 Gbps または 100 Gbps の専用プライベート接続を Lakehouse に提供します。Lakehouse のクエリは、パブリック インターネットではなく、この接続を介して送信されるため、低レイテンシの予測可能な状態が維持されます。また、クロスクラウド キャッシュは、Google Cloud 内から繰り返し行われる読み取り処理に対応するため、エージェントは他のクラウドのデータを移行することなく直接クエリできます。</span></p>
<p><span style="vertical-align: baseline;">ボーダーレス Lakehouse には、Iceberg メタデータをクエリエンジンに統合するための重要な最適化がいくつか盛り込まれています。BigQuery で、バイナリ削除ベクトルや並べ替え順など、</span><a href="https://docs.cloud.google.com/lakehouse/docs/use-iceberg-v3-binary-deletion-vectors"><span style="text-decoration: underline; vertical-align: baseline;">Apache Iceberg V3 仕様</span></a><span style="vertical-align: baseline;">がサポートされるようになりました。これらの機能により、データファイル全体を書き換える必要がなくなるため、エンジンは行レベルの更新や削除をより効率的に処理できるようになります。また、BigQuery の実行エンジンをアップグレードし、新しい FlatBuffers ベースの Parquet リーダーと並列化された I/O を導入しました。これにより、CPU オーバーヘッドやシリアル化によるボトルネックを軽減し、オープン フォーマットとネイティブ ストレージのパフォーマンスの差を縮めました。</span></p>
<p><span style="vertical-align: baseline;">これは、エージェントのワークロードをサポートするように設計されたクエリ エンジンの最近のパフォーマンス イノベーションに基づいています。エージェントのワークロードは一斉に大量発生することが多く、小規模なクエリを迅速かつ費用対効果の高い方法で処理することが求められます。</span><a href="https://cloud.google.com/blog/ja/products/data-analytics/bigquery-performance-optimizations?e=48754805&amp;hl=ja"><span style="text-decoration: underline; vertical-align: baseline;">BigQuery の流動的なスケーリングと履歴ベースの最適化</span></a><span style="vertical-align: baseline;">により、Apache Iceberg とのオープン性を維持しながら、スケーラブルかつ効率的なエージェント ワークロードを実行できます。</span></p>
<p><span style="vertical-align: baseline;">一方、</span><a href="https://cloud.google.com/bigquery"><span style="text-decoration: underline; vertical-align: baseline;">BigQuery</span></a><span style="vertical-align: baseline;"> と </span><a href="https://cloud.google.com/products/managed-service-for-apache-spark"><span style="text-decoration: underline; vertical-align: baseline;">Managed Service for Apache Spark</span></a><span style="vertical-align: baseline;"> の両方で Apache Iceberg テーブルの読み取り / 書き込みの相互運用性が確保されているため、すべてのデータチームが Google Cloud Storage 内の同じ Iceberg テーブルを簡単に利用できます。この垂直方向に最適化されたスタックは、BigQuery と </span><a href="https://cloud.google.com/blog/ja/products/data-analytics/introducing-lightning-engine-for-apache-spark?e=48754805&amp;hl=ja"><span style="text-decoration: underline; vertical-align: baseline;">Lightning Engine</span></a><span style="vertical-align: baseline;"> の力を活用してデータを移動することなく有効化し、エージェントの高速化と費用対効果の向上を実現します。Lakehouse の分析能力をさらに拡張するため、BigQuery の Iceberg 向けグラフ機能のサポートにより、サプライ チェーンなどの関係ネットワークをオープン テーブル データセットで直接分析できるようになりました。</span></p>
<h4><strong style="vertical-align: baseline;">エージェント向けの包括的なコンテキストとデータアクセス</strong></h4>
<p><span style="vertical-align: baseline;">AI エージェントの能力は、アクセスできるコンテキストに左右されます。ハルシネーションを防止し、メタデータ レイヤの精度を向上させるために、ボーダーレス Lakehouse は </span><a href="https://docs.cloud.google.com/lakehouse/docs/about-lakehouse-catalogs"><span style="text-decoration: underline; vertical-align: baseline;">Lakehouse ランタイム カタログ</span></a><span style="vertical-align: baseline;">を使用してエンタープライズ データを統合します。Apache Iceberg REST カタログをベースに、AWS Glue、Databricks Unity Catalog、Snowflake Horizon Catalog との双方向のカタログ連携を実現します。Lakehouse ランタイム カタログには、新たな標準の Hive Metastore 互換エンドポイントも含まれており、Apache Spark、Trino、Presto などのエンジンがアーキテクチャを変更することなくメタデータを参照できます。</span></p>
<p><span style="vertical-align: baseline;">ボーダーレス Lakehouse は、分散したデータアセットを自動的にインデックス化する </span><a href="https://cloud.google.com/products/knowledge-catalog"><span style="text-decoration: underline; vertical-align: baseline;">Knowledge Catalog</span></a><span style="vertical-align: baseline;"> とも直接連携しており、エージェントがエンタープライズ コーパス全体（Cloud Storage 内の非構造化データを含む）を推論するために必要な、正確なビジネス メタデータとセマンティック定義を提供します。これにより、エージェントはトークン費用を抑えながら、正確性を確保するのに十分なコンテキストを得られるため、インテリジェントで持続可能なエージェント活用戦略を策定できます。</span></p>
<p><span style="vertical-align: baseline;">ボーダーレス Lakehouse は、Salesforce、SAP、Workday などの SaaS アプリケーションとのゼロコピー データ統合を実現し、より広範なパートナー エコシステムと連携することにより、Knowledge Catalog を通じてエンタープライズ データをキャプチャし、エージェントのための単一のコンテキスト エンジンとして機能します。このたび Google は、パートナー エコシステムを拡大し、Confluent Tableflow との新たな連携機能の一般提供を開始しました。これにより、Lakehouse ランタイム カタログと同期され、生成された Iceberg テーブルが BigQuery に直接表示されるようになります。コピーや追加の ETL は不要です。</span></p>
<p><span style="vertical-align: baseline;">最後に、Databricks 中心のリポジトリを持つ組織は、</span><a href="https://docs.cloud.google.com/lakehouse/docs/import-delta-lake-tables"><span style="text-decoration: underline; vertical-align: baseline;">Lakehouse コンソール</span></a><span style="vertical-align: baseline;">経由で Dataflow を使用して、Delta Lake アセットを Lakehouse に簡単にインポート、変換、同期できるようになりました。</span></p>
<h4><strong style="vertical-align: baseline;">モダナイゼーションを容易に</strong></h4>
<p><span style="vertical-align: baseline;">2025 年初頭以降、Apache Iceberg の利用は 3 倍以上に増加しており、Google Cloud のボーダーレス Lakehouse を使用してデータ基盤を構築している企業は、大きな成果を上げています。</span></p>

<div class="block-paragraph"><h3><b>エージェント化によって営業メンバーもクリエイティブ制作の担い手に</b></h3><p>次の転機となったのが AI エージェント機能の追加です。もともと社内では 2024 年 6 月頃から、クリエイティブ制作をエージェンティックにできないかという要望がありました。これを受けて 2025 年 3 月に検証が開始され、翌 4 月には、Google がリリースしたオープンソースのエージェント開発フレームワーク「Agent Development Kit（ADK）」の採用を決定。そのわずか 3 か月後の 2025 年 7 月に、エージェント基盤をリリースしています。</p><p>「ADK を選んだ理由は 3 つあります。オープンソースかつ Google の長期サポートが見込めること、Agent2Agent（A2A）プロトコルというエージェント間連携の仕組みが設計に組み込まれていること、そして Google Cloud のマネージド サービスと親和性が高いことです。」（瓜生氏）</p><p>短期間でのリリースを可能にしたのは、新規構築と既存資産の見極めでした。エージェント基盤そのものは ADK、Cloud Run、PostgreSQL で別アプリケーションとしてゼロから設計したのに対し、画像生成については既存基盤をそのまま呼び出す形にしたのです。現在稼働する主なエージェントは、プロンプトから画像を生成する「画像生成」、画像内のテキストを差し替える「ブラッシュアップ」、LP（ランディング ページ）や参考画像をもとに広告バナーを作る「バナー生成」、アスペクト比に合わせてレイアウトを組み替える「リサイズ」の 4 種類。これらはすでに現場での活用が進んでいます。</p><p>「2026 年 4 月にはエージェント機能を用いて約 1 万枚の広告クリエイティブが生成され、そのうち約 20% にあたる約 2,000 枚が実用候補としてダウンロードされました。従来、生成機能のダウンロード率は 7～8% 程度だったので、予想以上の数字だったと言えるでしょう。利用の拡大は、用途が明確なリサイズ機能に牽引されている面もありますが、バナー生成単体でもダウンロード率は 10% 弱となっています。素材生成が中心だった従来の生成機能より、バナー生成やリサイズなど制作工程をより先まで進められるエージェント機能の方が、ダウンロードにつながりやすい傾向が見られます。」（瓜生氏）</p><p>エージェント機能の提供開始により、営業担当者が自らバナーを制作し、それを叩き台に広告主企業とすり合わせたりするといった事例も生まれ始めました。まだ制作・外注コストの削減効果までは確認できていないものの、生成 AI の利用者をクリエイター以外の職種にも広げられたことは、エージェント化がもたらした大きな成果と言えます。</p></div>

<p><span style="vertical-align: baseline;">このリリースにより、世界で最も広く採用されているエンタープライズ向けエコシステムの一つで、最高水準の型安全なエージェント オーケストレーションが実現します。Java の成熟したアーキテクチャは、厳しい要求に対応できるよう構築されており、本番環境でミッションクリティカルな AI エージェントを安全にスケールするために必要な高い同時実行性、厳格なトランザクション整合性、堅牢な状態管理を提供します。</span></p>
<p><span style="vertical-align: baseline;">この投稿では、Java SDK v1.0 の新機能について説明し、実際の例を示しながら、独自の実装を始めるためのステップを解説します。</span></p>
<h4><strong style="vertical-align: baseline;">MCP: ユニバーサル インターフェース</strong></h4>
<p><span style="vertical-align: baseline;">現在、デベロッパーは複雑化する統合のボトルネックに直面しています。</span><span style="font-style: italic; vertical-align: baseline;">N</span><span style="vertical-align: baseline;"> 個の異なる AI モデルと </span><span style="font-style: italic; vertical-align: baseline;">M</span><span style="vertical-align: baseline;"> 個のエンタープライズ データソースがある場合、</span><span style="font-style: italic; vertical-align: baseline;">N × M</span><span style="vertical-align: baseline;"> 個のカスタム接続を構築、保護、維持する必要があります。このように統一されたインテグレーション レイヤがないため、エンジニアリング チームは、断片化されたアドホックなパイプラインが複雑に入り組んだ状態に頼らざるを得ません。その結果、エージェント アーキテクチャのスケーリングはすぐに持続不可能になり、機密性の高いエンタープライズ データベースが深刻なセキュリティ脆弱性、断片化されたアクセス制御、膨大なメンテナンス オーバーヘッドにさらされることになります。</span></p>
<p><span style="vertical-align: baseline;">Model Context Protocol（MCP）が解決する根本的な課題は、複雑に絡み合った独自のインテグレーションを解消することです。MCP は、AI オーケストレーションの「USB Type-C」のようなユニバーサル インターフェースとして機能し、モデルをデータソースから分離します。デベロッパーは、新しいモデルやデータベースごとにカスタムまたはマネージド API 統合コードを記述する代わりに、単一の標準化されたプロトコルに準拠してコードを記述します。このアプローチにより、MCP 準拠のエージェントは、MCP 対応のシステムとセキュアかつ即座にやり取りできます。MCP 接続により、デベロッパーは新しいモデルごとに個別のインテグレーションを構築することなく、エージェントを実世界のシステムに接続できます。</span></p>
<h4><strong style="vertical-align: baseline;">Java SDK v1.0 の新機能: 本番環境ワークロードに対応</strong></h4>
<p><span style="vertical-align: baseline;">「MCP ツールボックス」Java SDK の</span><a href="https://medium.com/google-cloud/announcing-the-mcp-toolbox-java-sdk-2ed3171bbaa0" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">公開ベータ版</span></a><span style="vertical-align: baseline;">を発表した際、Google の目標は、最高水準の型安全なエージェント オーケストレーションをエンタープライズ Java 環境に提供することでした。それ以来、Google はデベロッパーやオープンソースのコントリビューターと協力して API の堅牢化に努めてきました。</span></p>
<p><span style="vertical-align: baseline;">v1.0 リリースは、エンタープライズ ワークロードに適した、安定した後方互換性を備えた基盤となります。v0.2 リリース以降の新機能と堅牢化された機能は次のとおりです。</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">トランスポート層の抽象化と </strong><strong style="vertical-align: baseline;">HttpMcpTransport</strong><span style="vertical-align: baseline;">: </span><code style="vertical-align: baseline;">HttpMcpTransport</code><span style="vertical-align: baseline;"> とともに、クリーンなトランスポート層の抽象化を導入しました。この機能により、コア プロトコル ロジックが基盤となる HTTP クライアントから分離されるため、ネットワーク実装の入れ替えや接続プールのカスタマイズが容易になります。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">クライアント認証の疎結合化</strong><span style="vertical-align: baseline;">: 企業のセキュリティ コンプライアンスを簡素化するため、</span><code style="vertical-align: baseline;">CredentialsProvider</code><span style="vertical-align: baseline;"> クラスと </span><code style="vertical-align: baseline;">AuthMethods</code><span style="vertical-align: baseline;"> クラスを使用してクライアント認証を切り離しました。認証情報はリクエストごとに非同期で解決されるため、チームはトークンを動的に更新したり、独自のトークンソースをプラグインしたりできます（ADC 経由の Google OIDC は標準で組み込まれており、それ以外は 1 つのメソッドを実装するだけのインターフェースです）。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">デフォルト パラメータのサポート</strong><span style="vertical-align: baseline;">: ツール パラメータのデフォルト値をネイティブにサポートすることで、プロンプトのペイロード サイズを削減し、エージェントの信頼性を高めます。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">バインドされたパラメータのプルーニング</strong><span style="vertical-align: baseline;">: サーバーサイドでバインドされた機密性の高いパラメータ（</span><code style="vertical-align: baseline;">tenant_id</code><span style="vertical-align: baseline;"> など）が、公開されたツール定義から自動的に削除されるようになり、LLM による操作を防ぎます。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">バージョン選択とセッション トラッキング</strong><span style="vertical-align: baseline;">: 標準化された MCP バージョン選択と堅牢なセッション トラッキングにより、一貫したプロトコル ネゴシエーションと会話状態のライフサイクルを実現します。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">HTTP 認証情報の漏洩に関する警告</strong><span style="vertical-align: baseline;">: 認証情報が平文の HTTP 接続で送信されようとしているときに、実行時に警告を発する組み込みの検出機能を追加しました。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">汎用クライアント ヘッダーのマップ</strong><span style="vertical-align: baseline;">: カスタムの企業プロキシ ヘッダー、トランザクション トレース ID、相関メタデータを、すべての送信リクエストに簡単に追加できます。</span></p>
</li>
</ul>

<h4><strong style="vertical-align: baseline;">Spring Boot のステートフル エージェント アーキテクチャ</strong></h4>
<p><span style="vertical-align: baseline;">エンタープライズ アプリケーションで会話型 AI を構築するうえで最も難しいのは、状態の管理です。ユーザーが「空席がある便の出発時間は？」と尋ねた後、「午前 8 時の便を予約して」と言った場合、エージェントはターンをまたいで前のコンテキストを覚えておく必要があります。</span></p>
<p><span style="vertical-align: baseline;">「MCP ツールボックス」Java SDK を Spring Boot および LangChain4j と併せて使用すると、HTTP セッションで会話のメモリを適切に維持し、エージェントを次の 2 つの宣言型コンポーネントに明確に分離できます。</span></p>
<ol>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">HTTP セッションを介してプロンプト、ツール、会話のメモリを管理する宣言型エージェント インターフェース。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">エージェントのリクエストを MCP ツールボックス サーバーに直接ルーティングするツール実行サービス。</span></p>
</li>
</ol></div>

<div class="block-paragraph_advanced"><p><code style="vertical-align: baseline;">@MemoryId</code><span style="vertical-align: baseline;"> アノテーションがセッション トラッキングを抽象化している点に注目してください。これにより、Spring Boot は会話のコンテキストをユーザーの HTTP セッションに自動的に関連付けることができます。その一方で、LangChain4j と MCP ツールボックスが舞台裏でスキーマ変換とツール ルーティングを処理するため、手動で if/else 文によるインテント解析を書く必要はありません。</span></p>
<p><span style="vertical-align: baseline;">「MCP ツールボックス」Java SDK と LangChain4j を組み合わせることで、関心の分離を明確にし、手間をかけずに状態を管理できるようになります。</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">ボイラープレート不要のセッション管理</strong><span style="vertical-align: baseline;">: </span><code style="vertical-align: baseline;">@MemoryId String sessionId</code><span style="vertical-align: baseline;"> パラメータにより、会話履歴がユーザーの HTTP セッションに直接バインドされます。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">宣言型エージェント コントラクト</strong><span style="vertical-align: baseline;">: </span><code style="vertical-align: baseline;">TransitAgent</code><span style="vertical-align: baseline;"> インターフェースは、複雑なプロンプト テンプレートを使用せずに、モデルのペルソナとシステム指示を定義します。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">型安全なツールの実行</strong><span style="vertical-align: baseline;">: </span><code style="vertical-align: baseline;">TransitAgentTools</code><span style="vertical-align: baseline;"> Spring サービスが、リモート MCP データベース ツールをネイティブ Java メソッドとしてラップします。</span></p>
</li>
</ul>
<p><span style="vertical-align: baseline;">このアーキテクチャにより、エージェントのモジュール性を保つことができます。インターフェースでプロンプト ガイダンスを改良し、ユーザー セッションを自動的に管理しながら、密結合させることなく MCP ツールボックスを介して安セキュアなデータベース クエリを実行できます。</span></p>

<div class="block-paragraph_advanced"><h4><strong style="vertical-align: baseline;">セキュア バイ デフォルト: 認証とデプロイ</strong></h4>
<p><span style="vertical-align: baseline;">AI エージェントを本番環境に移行するには、堅牢な認証情報処理と、需要に応じてスケールするインフラストラクチャが必要です。さまざまな環境で認証情報の安全性を確保し、Cloud Run に独立してデプロイする方法を見ていきましょう。</span></p>
<p><strong style="vertical-align: baseline;">アプリケーションのデフォルト認証情報（ADC）と安全性</strong></p>
<p><code style="vertical-align: baseline;">GoogleCredentialsProvider</code><span style="vertical-align: baseline;"> サービスを使用すると、Java アプリはアプリケーションのデフォルト認証情報（ADC）を介して、実行環境（ローカルまたは Google Cloud）から安全な ID を継承します。ハードコードされた鍵は不要で、OIDC トークンがオーディエンスごとにバックグラウンドで生成され、キャッシュに保存されます。さらに、v1.0 では HTTP 認証情報の漏洩警告が提供されます。これは、認証情報が平文の HTTP 接続で送信されようとしていることを自動的に検出し、HTTPS に切り替えるよう指示するランタイム警告を発します。</span></p>
<p><strong style="vertical-align: baseline;">フリートを Cloud Run にデプロイ</strong></p>
<p><span style="vertical-align: baseline;">MCP ツールボックスと Spring Boot エージェントは完全に疎結合化されているため、Google Cloud Run で独立してスケールし、高い同時実行性とステートフルな会話の要件に対応できます。</span></p>
<p><span style="vertical-align: baseline;">Cloud Run でツールボックスをセットアップして構成するには、オープンソースのデータベース向け MCP ツールボックスをダウンロードしてから、</span><a href="https://mcp-toolbox.dev/documentation/deploy-to/cloud-run" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">デプロイガイド</span></a><span style="vertical-align: baseline;">に沿って操作します。</span></p>
