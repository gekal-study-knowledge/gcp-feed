<div class="block-paragraph"><p>Enterprise AI needs to go beyond simple chat interfaces. To provide real value, AI agents must access your data warehouses to generate actionable insights, all while maintaining strict security and data governance.</p><p>This guide explores how to build a secure bridge between Google Cloud’s Gemini Enterprise and Snowflake. By using the Model Context Protocol (MCP) and the Google Agent Development Kit (ADK), you can empower your agent to act as an assistant that understands natural language, generates precise SQL via Snowflake Cortex and executes queries with user-level permissions.</p><h3><b>Choosing the right integration pattern</b></h3><p><b>Direct Connection vs. custom orchestration</b></p><p>The Google ADK architecture demonstrated in this post represents the advanced / custom orchestration pattern. It is designed for developers building complex, multi-agent systems on Google Cloud, such as workflows that combine Snowflake insights with external enterprise tools, custom reasoning loops, or cross-platform state management in Gemini Agent Engine.</p><p>For standard enterprise basic use cases where you want to connect Gemini Enterprise directly to Snowflake use the joint solutions mentioned in <a href="https://www.snowflake.com/en/developers/guides/quickstart-iceberg-cortex-gemini/" target="_blank">this link</a>.</p><h3><b>The architectural approach</b></h3><p>This architecture allows a business user to ask questions like, <i>"What were our top 5 selling items in Texas last quarter?"</i></p><p>Rather than exposing raw SQL execution to the client, the agent delegates both query generation and execution to a governed Snowflake Cortex Agent exposed through the Snowflake MCP server:</p><ol><li><b>Governed translation</b>: The ADK agent passes the user's natural language question to the Snowflake MCP server, which invokes the Cortex Agent (CORTEX_AGENT_RUN) backed by Cortex Analyst semantic view.</li><li><b>Direct execution within the governed boundary</b>: The Cortex Agent translates the question into SQL and executes it directly inside Snowflake using the authenticated user's OAuth session and role privileges, returning the structured results to the ADK agent.</li></ol><p>This approach provides deterministic text-to-SQL translation mapped to your corporate semantic definitions, keeps query execution inside Snowflake's governed boundary, and reduces the risk of schema hallucinations or unvalidated SQL execution.</p><h3><b>System architecture flow</b></h3><p>The diagram below illustrates the trust boundaries and the numbered flow of execution between the Gemini Enterprise app and Snowflake ecosystems.</p></div>

<div class="block-paragraph"><p><b>IMPORTANT</b></p><ul><li>The user context must have SELECT privileges on the physical tables backing the semantic view. Because Snowflake views execute with <b>Owner's Rights</b>, the user's GenAI role only needs SELECT privileges on the Secure View and Semantic View rather than the raw tables.</li><li><b>Snowflake OAuth tokens</b> capture and bind to the user's DEFAULT_ROLE and DEFAULT_WAREHOUSE at the exact moment of authorization. If a user authorizes the connection before these defaults are configured, the session will be locked to the wrong role(role available at that time) and query execution will fail if the intended role will not have required privileges.<ul><li><b>Set defaults(as shown below)</b> prior to authorizing in Gemini Enterprise.</li><li><b>Authorize connection:</b> Have the user perform the one-time OAuth authorization in Gemini Enterprise.</li><li><b>(Optional) Revert defaults:</b> Once authorized, the user can safely revert their default role and warehouse in Snowflake back to their standard operational preferences.</li></ul></li></ul></div>
