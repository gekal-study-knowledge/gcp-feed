### Announcing Spanner queues: Transactional messaging for agentic workloads and beyond

- **Link**: [https://cloud.google.com/blog/products/databases/spanner-queues-provide-native-transactional-messaging/](https://cloud.google.com/blog/products/databases/spanner-queues-provide-native-transactional-messaging/)
- **Published**: 2026-10-03 01:00:00
- **Fetched**: 2026-10-03 03:58:29

<details class="entry-summary">
<summary>詳細を表示</summary>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">AI agents don't just answer queries — they can autonomously issue refunds, manage inventory, execute multi-step handoffs, and orchestrate sub-agents, to name but a few complex agentic workflows. That frequently requires the agents to maintain internal state in an operational database while dispatching asynchronous actions through a separate messaging or event queue system. And unfortunately for the teams building these applications, managing two systems with disjointed commit points destroys transactional consistency in agentic systems.</span></p>
<p><span style="vertical-align: baseline;">Today, we are excited to announce the general availability of </span><a href="https://docs.cloud.google.com/spanner/docs/queues/queues-overview"><strong style="text-decoration: underline; vertical-align: baseline;">Spanner queues</strong></a><span style="vertical-align: baseline;">: native transactional messaging embedded directly within Spanner. Designed specifically for reliable agentic execution, with Spanner queues, creating a message is simply another write in your transaction. An agent's state change and intended downstream actions commit together atomically or fail completely.</span></p>
<p><span style="vertical-align: baseline;">Compare this to traditional approaches: When a database state update succeeds, but the action dispatch fails, your AI agent decides to act but doesn’t execute. If the message dispatch succeeds but the state transaction rolls back, your agent executes an action based on an invalid state. In asynchronous multi-agent coordination, retries, speculation, and race conditions amplify these failures, forcing developers to build complex outbox patterns, idempotency layers, and reconciliation workers — a heavy reliability tax on agentic architecture.</span></p>
<h3><strong style="vertical-align: baseline;">Key capabilities for agentic architectures</strong></h3>
<p><span style="vertical-align: baseline;">Spanner queues introduces several core capabilities to support these complex asynchronous workflows without introducing infrastructure overhead.</span></p>
<p><strong style="vertical-align: baseline;">Atomic decide-and-act enqueue.</strong><span style="vertical-align: baseline;"> Within a single Spanner read-write transaction, agents can update internal memory or state tables and enqueue tasks to peer agents simultaneously. Backed by Spanner's strict serializability and global external consistency, state changes and execution intent commit as a single atomic unit.</span></p>
<p><strong style="vertical-align: baseline;">Scheduled execution and delays.</strong><span style="vertical-align: baseline;"> Queue messages can be dispatched immediately upon commit or scheduled for future delivery. Agentic patterns such as delayed retries, scheduled agent check-ins, or SLA escalation timers can be enqueued transactionally alongside memory updates without requiring external cron schedulers or polling infrastructure.</span></p>
<p><strong style="vertical-align: baseline;">Streaming SQL pull for agent workers.</strong><span style="vertical-align: baseline;"> Autonomous agents consume tasks dynamically using streaming SQL reads. Agent runtimes stream incoming tasks, process them as capacity becomes available, and acknowledge task completion within a transaction to guarantee end-to-end task execution state reliability.</span></p>
<p><strong style="vertical-align: baseline;">Episodic memory persistence and handoffs.</strong><span style="vertical-align: baseline;"> Agent memory updates — including long-term episodic summaries, reflective state transitions, and context handoffs across sub-agents — can be persisted asynchronously and transactionally via queues. This guarantees that an agent's internal memory remains fully synchronized with its execution history without blocking real-time interactive turns.</span></p>
<h3><strong style="vertical-align: baseline;">Why Spanner queues are essential for autonomous agents</strong></h3>
<p><strong style="vertical-align: baseline;">Transactional exactly-once agent execution: </strong><span style="vertical-align: baseline;">When an agent evaluates tool call results, state modification, reasoning persistence, and downstream tool invocation tasks are saved in one transaction. We guarantee at-least-once delivery and at-most-once ACK, enabling you to achieve exactly-once processing.</span></p>
<p><strong style="vertical-align: baseline;">Robust multi-agent orchestration and handoffs:</strong><span style="vertical-align: baseline;"> In multi-agent systems (A2A), handing off state from a primary agent to a specialist agent is represented as a durable, transactionally committed message. Specialist agent workers receive deliverable messages while maintaining a fully auditable lineage of agent interactions.</span></p>
<p><strong style="vertical-align: baseline;">First-class timeouts and human-in-the-loop workflows:</strong><span style="vertical-align: baseline;"> Agent workflows frequently require pausing for human approvals or scheduled follow-ups. Spanner queues handles timeout management natively: A single transaction records the pending approval state and schedules an automated escalation message, resolving whichever triggers first.</span></p>
<p><strong style="vertical-align: baseline;">SQL-native observability for agent queues:</strong><span style="vertical-align: baseline;"> Inspecting in-flight agent workloads, monitoring task backlogs, or auditing agent execution history can be accomplished with standard SQL queries over queue tables, avoiding opaque message-store black boxes.</span></p>
<h3><strong style="vertical-align: baseline;">Beyond agentic workflows</strong></h3>
<p><span style="vertical-align: baseline;">Beyond AI agents, Spanner queues serves as a flexible, multi-purpose messaging platform across a variety of traditional event-driven architectures. Whether powering real-time activity feeds in social applications, delivering live updates in news publishing, orchestrating order processing and inventory workflows in retail, or handling high-throughput asynchronous task processing and transaction notifications in financial services, Spanner queues provides a robust foundation for asynchronous message delivery and transactional event-driven workflows within your primary database.</span></p>
<h3><strong style="vertical-align: baseline;">Under the hood: Transactional mechanics of Spanner queues</strong></h3>
<p><span style="vertical-align: baseline;">Because Spanner queues are represented as first-class relational structures in Spanner, you define, inspect, and manage queues using familiar GoogleSQL.</span></p>
<h4><span style="vertical-align: baseline;">1. Defining a queue and enqueuing atomically</span></h4>
<p><span style="vertical-align: baseline;">When an agent decides to approve a customer refund, it updates the </span><span style="vertical-align: baseline;">Orders</span><span style="vertical-align: baseline;"> table and dispatches an execution task to the </span><span style="vertical-align: baseline;">OrderAgentTasks</span><span style="vertical-align: baseline;"> queue within a single ACID transaction:</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &#x27;-- Assume parent table:\r\n-- CREATE TABLE Orders (\r\n--   OrderId STRING(64) NOT NULL, ...\r\n-- )\r\n-- PRIMARY KEY (OrderId);\r\n\r\n-- Define the transactional queue table\r\nCREATE QUEUE OrderAgentTasks (\r\n  OrderId STRING(64) NOT NULL,\r\n  TaskId STRING(64) NOT NULL,\r\n  TaskType STRING(64) NOT NULL,\r\n  Payload JSON NOT NULL\r\n) PRIMARY KEY (OrderId, TaskId, TaskType), INTERLEAVE IN Orders;\r\n\r\n-- Inside a Read-Write Transaction:\r\n-- 1. Update business state atomically\r\n\r\n-- BEGIN TRANSACTION;\r\n\r\nUPDATE Orders\r\nSET Status = \&#x27;REFUND_APPROVED\&#x27;,\r\n    UpdatedAt = PENDING_COMMIT_TIMESTAMP()\r\nWHERE OrderId = @orderId;\r\n\r\n-- 2. Enqueue the asynchronous agent action in the same transaction\r\nINSERT INTO OrderAgentTasks (OrderId, TaskId, TaskType, Payload)\r\nVALUES (\r\n  @orderId,\r\n  @taskId,\r\n  \&#x27;EXECUTE_REFUND\&#x27;,\r\n  JSON \&#x27;{&quot;action&quot;: &quot;execute_refund&quot;, &quot;amount&quot;: 49.99}\&#x27;\r\n);\r\n\r\n-- COMMIT;&#x27;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f569b7cf090&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">This ensures that the </span><span style="vertical-align: baseline;">EXECUTE_REFUND</span><span style="vertical-align: baseline;"> task exists if and only if the order status successfully transitioned to </span><span style="vertical-align: baseline;">REFUND_APPROVED</span><span style="vertical-align: baseline;">.</span></p>
<h4><span style="vertical-align: baseline;">2. Temporal scheduling and atomic cancellation</span></h4>
<p><span style="vertical-align: baseline;">For workflows that depend on time — such as waiting up to 72 hours for a manager's approval before escalating — agents populate the system </span><span style="vertical-align: baseline;">DeliverTime</span><span style="vertical-align: baseline;"> column to defer message visibility:</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &#x27;-- Schedule an automated escalation check-in 72 hours in the future\r\nINSERT INTO OrderAgentTasks (OrderId, TaskId, TaskType, Payload, DeliverTime)\r\nVALUES (\r\n  @orderId,\r\n  @escalationTaskId,\r\n  \&#x27;ESCALATE_UNAPPROVED_ORDER\&#x27;,\r\n  JSON \&#x27;{&quot;action&quot;: &quot;escalate_to_supervisor&quot;}\&#x27;,\r\n  TIMESTAMP_ADD(CURRENT_TIMESTAMP(), INTERVAL 72 HOUR)\r\n);&#x27;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f569b7ce410&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">If the manager approves the request after four hours, your application doesn't have to deal with phantom escalation alerts firing  days later. In a single transaction, you update the order status and cancel the pending escalation task using a standard SQL </span><span style="vertical-align: baseline;">DELETE</span><span style="vertical-align: baseline;">:</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &quot;-- BEGIN TRANSACTION;\r\n\r\nUPDATE Orders\r\nSET Status = &#x27;MANAGER_APPROVED&#x27;,\r\n    ApprovedBy = @managerId\r\nWHERE OrderId = @orderId;\r\n\r\n-- Atomically cancel the pending delayed escalation task. `ASSERT_ROWS_MODIFIED 1` will\r\n-- act as a safeguard and cause a statement level error.\r\n\r\n-- A statement level error can be captured and the transaction can be\r\n-- user-aborted/cancelled in case the queue entry was already deleted.\r\n-- Otherwise the transaction will complete successfully regardless if the \r\n-- queue entry still exists and you&#x27;ll only know if a queue entry was deleted by\r\n-- checking the number of rows affected by the DELETE.\r\nDELETE FROM OrderAgentTasks\r\nWHERE OrderId = @orderId\r\n  AND TaskId = @escalationTaskId\r\n  AND TaskType = &#x27;ESCALATE_UNAPPROVED_ORDER&#x27;,\r\nASSERT_ROWS_MODIFIED 1;\r\n\r\n-- COMMIT;&quot;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f569b7cf210&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><h4><span style="vertical-align: baseline;">3. Streaming consumption, lease renewal, and atomic acknowledgment</span></h4>
<p><span style="vertical-align: baseline;">Downstream agent workers consume tasks using the </span><span style="vertical-align: baseline;">RECEIVE_&lt;QueueName&gt;</span><span style="vertical-align: baseline;"> table-valued function (TVF) over a streaming SQL connection (</span><span style="vertical-align: baseline;">ExecuteStreamingSql</span><span style="vertical-align: baseline;">). Spanner automatically manages message leases, returning a unique </span><span style="vertical-align: baseline;">SpannerLeaseToken</span><span style="vertical-align: baseline;"> and expiration timestamp with each leased task:</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &quot;-- Step 1: Consume tasks via a long-lived streaming SQL query\r\nSELECT\r\n  OrderId,\r\n  TaskId,\r\n  TaskType,\r\n  Payload,\r\n  SpannerLeaseToken,\r\n  SpannerLeaseExpirationTimestamp\r\nFROM RECEIVE_OrderAgentTasks(max_duration =&gt; &#x27;20m&#x27;);&quot;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f569b7cfed0&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">Because AI agent tasks often involve multi-turn LLM reasoning or external API calls that take longer than default lease windows, workers can actively extend their lease using the </span><span style="vertical-align: baseline;">RENEWLEASE_&lt;QueueName&gt;</span><span style="vertical-align: baseline;"> function:</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &#x27;-- Step 2: Extend lease ownership during long-running agent execution\r\nSELECT *\r\nFROM RENEWLEASE_OrderAgentTasks(lease_tokens =&gt; [@leaseToken]);&#x27;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f569b7cdd90&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">When the agent finishes executing its external tool (passing </span><span style="vertical-align: baseline;">TaskId</span><span style="vertical-align: baseline;"> as the external API's idempotency key), it opens a read-write transaction to record the final state and acknowledge the message by deleting it with </span><span style="vertical-align: baseline;">ASSERT_ROWS_MODIFIED 1</span><span style="vertical-align: baseline;">:</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &quot;-- Step 3: Atomically checkpoint agent results and ACK the message\r\n-- BEGIN TRANSACTION;\r\n\r\nUPDATE Orders\r\nSET RefundTransactionId = @externalRefundId,\r\n    Status = &#x27;REFUND_COMPLETED&#x27;\r\nWHERE OrderId = @orderId;\r\n\r\nDELETE FROM OrderAgentTasks\r\nWHERE OrderId = @orderId\r\n  AND TaskId = @taskId\r\n  AND TaskType = @taskType\r\nASSERT_ROWS_MODIFIED 1;\r\n\r\n-- COMMIT;&quot;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f569b7ccc10&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">Using </span><span style="vertical-align: baseline;">ASSERT_ROWS_MODIFIED 1</span><span style="vertical-align: baseline;"> protects your system against lease-expiration races. If a worker stalled due to a network pause and its lease expired, another worker may have already processed and deleted the task. When the stalled worker resumes and attempts to execute the statement, </span><span style="vertical-align: baseline;">ASSERT_ROWS_MODIFIED 1</span><span style="vertical-align: baseline;">  detects that the queue row is already gone and throws a statement-level error. Catching that error and aborting that transaction prevents stale workers from overwriting newer database state.</span></p>
<h3><strong style="vertical-align: baseline;">Spanner change streams vs. Spanner queues</strong></h3>
<p><span style="vertical-align: baseline;">Spanner change streams capture database data changes (inserts, updates, and deletes) in near real-time for downstream integration and auditing.</span><span style="vertical-align: baseline;"> </span><span style="vertical-align: baseline;">While both change streams and queues allow applications to react to data changes, Spanner change streams are designed for continuous change data capture (CDC) and data streaming to downstream analytics or storage. In contrast, Spanner queues are explicitly designed for transactional task orchestration, supporting native message leases, scheduled deliveries, SQL-based pulling, and atomic acknowledgments within read-write transactions.</span></p>

      <p>Yet, platform engineers and developers face a persistent dilemma: Applications often demand significantly more CPU power during startup than they do during steady-state operations. Sizing CPU requests for normal, steady-state usage leads to CPU throttling during launch, which can result in sluggish cold starts and readiness probe timeouts. <div class="block-paragraph_advanced"><h3><strong style="vertical-align: baseline;">Why modern applications need extra CPU at boot time</strong></h3>
<p><span style="vertical-align: baseline;">When a new container launches, it may perform intensive initialization tasks before it begins serving user requests. Depending on your tech stack, the following startup workloads require substantial CPU cycles:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Java JVM applications</strong><span style="vertical-align: baseline;">: Frameworks like Spring Boot require high CPU burst capacity for class loading, classpath scanning, instantiating dependency injection containers, and running Just-in-Time (JIT) compilation.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Node.js servers</strong><span style="vertical-align: baseline;">: Apps parse JavaScript files, build complex module dependency trees (</span><code style="vertical-align: baseline;">require</code><span style="vertical-align: baseline;">/</span><code style="vertical-align: baseline;">import</code><span style="vertical-align: baseline;">), and execute V8 engine optimization and JIT compilation passes during initial execution.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Python and AI/ML microservices</strong><span style="vertical-align: baseline;">: These services spend initial cycles importing heavy libraries (such as PyTorch, NumPy, or LangChain), compiling </span><code style="vertical-align: baseline;">.pyc</code><span style="vertical-align: baseline;"> bytecode, establishing ORM database schemas, and pre-loading cache structures.</span></p>
</li>
</ul>
<p><span style="vertical-align: baseline;">If you size CPU requests strictly for steady-state performance, these initialization workloads experience CPU throttling on launch, delaying readiness probes. To prevent slow cold starts, teams frequently overprovision CPU requests. However, once the application stabilizes, those extra CPU resources sit idle, increasing your cloud spend without adding value.</span></p></div>

<div class="block-paragraph_advanced"><h3><strong style="vertical-align: baseline;">Under the hood: Kubernetes In-place Pod Resize</strong></h3>
<p><span style="vertical-align: baseline;">Historically, changing a pod's resource requests or limits required deleting and recreating the pod. This disruptive process triggered container restarts, cache invalidation, and node rescheduling overhead.</span></p>
<p><span style="vertical-align: baseline;">To fix that, CPU startup boost builds on Kubernetes </span><a href="https://kubernetes.io/docs/tasks/configure-pod-container/resize-container-resources/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">In-place Pod Resize (IPPR)</span></a><span style="vertical-align: baseline;">.</span></p>
<p><span style="vertical-align: baseline;">Tracked under </span><a href="https://github.com/kubernetes/enhancements/tree/master/keps/sig-node/1287-in-place-pod-resize" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">KEP-1287</span></a><span style="vertical-align: baseline;">, IPPR introduced dynamic, in-place resource mutation. Introduced as Alpha in Kubernetes 1.27, promoted to Beta in v1.33, and graduating to General Availability (GA) in v1.35, IPPR allows the Kubernetes control plane and </span><code style="vertical-align: baseline;">kubelet</code><span style="vertical-align: baseline;"> to update container CPU and memory requests on running pods </span><strong style="vertical-align: baseline;">without restarting the container process</strong><span style="vertical-align: baseline;">.</span></p>
<p><span style="vertical-align: baseline;">GKE leverages IPPR within the VPA  to apply startup CPU boosts at pod admission and smoothly step them down post-readiness.</span></p>
<h3><strong style="vertical-align: baseline;">How CPU startup boost works (pod lifecycle overview)</strong></h3>
<p><span style="vertical-align: baseline;">CPU startup boost operates across three distinct phases:</span></p>
<ol>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Admission phase</strong><span style="vertical-align: baseline;">: When you deploy a pod, the VPA admission webhook intercepts the creation request. It calculates the elevated CPU request based on your policy (e.g., 2x multiplier or +2 vCPUs) and injects the boosted CPU request along with tracking annotations into the pod spec.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Startup phase</strong><span style="vertical-align: baseline;">: The pod is scheduled and initialized with the boosted CPU allocation. Your application completes class loading, JIT compilation, or module parsing at top speed without experiencing CPU throttling.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Unboosting phase</strong><span style="vertical-align: baseline;">: As soon as the pod's </span><code style="vertical-align: baseline;">readinessProbe</code><span style="vertical-align: baseline;"> passes (plus any configured </span><code style="vertical-align: baseline;">durationSeconds</code><span style="vertical-align: baseline;"> cooldown delay), the VPA updater issues an in-place resize request. The CPU request steps back down to your baseline level while the container continues running uninterrupted.</span></p>
</li>
</ol>
<h3><strong style="vertical-align: baseline;">Prerequisites and availability</strong></h3>
<p><span style="vertical-align: baseline;">CPU startup boost is available today in preview on GKE:</span></p>
<ul>
<li style="vertical-align: baseline;">

<h3><strong style="vertical-align: baseline;">Getting started: Configuring CPU startup boost</strong></h3>

<h3><span style="vertical-align: baseline;">Best practices for production workloads</span></h3>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Pairing with Horizontal Pod Autoscaler (HPA)</strong><span style="vertical-align: baseline;">: When using HPA alongside CPU startup boost, ensure a robust </span><code style="vertical-align: baseline;">readinessProbe</code><span style="vertical-align: baseline;"> is defined and keep </span><code style="vertical-align: baseline;">durationSeconds</code><span style="vertical-align: baseline;"> short (e.g., </span><code style="vertical-align: baseline;">0s</code><span style="vertical-align: baseline;">–</span><code style="vertical-align: baseline;">10s</code><span style="vertical-align: baseline;">). This prevents HPA from falsely interpreting initialization CPU spikes as high steady-state load.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Handle traffic spikes with </strong><a href="https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-capacity-buffer"><strong style="text-decoration: underline; vertical-align: baseline;">GKE capacity buffers API</strong></a><span style="vertical-align: baseline;">: By reducing the startup tax at scale, you can achieve higher workload density on fewer nodes to improve overall utilization. Consider adopting the GKE capacity buffers API to absorb sudden traffic surges with minimal operational overhead while maintaining strict SLOs. </span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">GKE Autopilot resource ratios</strong><span style="vertical-align: baseline;">: On GKE Autopilot, remember that pods must maintain valid CPU-to-memory ratios. Ensure baseline memory allocations accommodate the boosted CPU ratio during startup.</span></p>
</li>
</ul>

<h3><span style="vertical-align: baseline;">The gridlock of high-utilization clusters</span></h3>
<p><span style="vertical-align: baseline;">Prior to leveraging GKE for orchestration, we used to negotiate capacity by hand in Slack. If you needed capacity for a training run, you posted in #gpu-resources and hoped for the best.</span></p>
<p><span style="vertical-align: baseline;">That worked fine when the cluster had headroom. It stopped working once utilization pinned near 100%, which is where you want a reserved compute fleet to sit.</span></p>
<p><span style="vertical-align: baseline;">Over time, every request became a negotiation. Team leads spent their time refereeing compute disputes. Our high-priority jobs — the large, multi-node training runs that need half or more of the cluster at once and serve as the critical path for model projects — could sit blocked for up to 72 hours waiting for enough contiguous capacity to open up. </span></p></div>

<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">Sometimes we had plenty of capacity free on paper, but it was scattered across different machines in chunks too small for a larger job to actually land. Without all-or-nothing admission, the cluster could reach a deadlock, with machines holding resources without doing useful work until someone stepped in manually. </span></p>
<p><span style="vertical-align: baseline;">It was clear the status quo wasn’t working and we needed something better.</span></p>
<h3><span style="vertical-align: baseline;">Choosing the right scheduler</span></h3>
<p><span style="vertical-align: baseline;">We looked at a few open-source batch schedulers, including Apache YuniKorn, Volcano, and </span><a href="https://kueue.sigs.k8s.io/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Kueue</span></a><span style="vertical-align: baseline;">. YuniKorn didn’t cover all our use cases. And while Volcano had more features, integrating it with our environment would have required replacing core Kubernetes scheduler components. </span></p>
<p><span style="vertical-align: baseline;">Kueue won on simplicity and integration. It worked with standard Kubernetes, didn’t require replacing core components, and didn’t force us to rewrite our job specs.</span></p>
<p><span style="vertical-align: baseline;">Pairing Kueue with AI Hypercomputer’s flexible, open operations through GKE also contributed to our success. We rely on GKE because it gives us the right level of control for compute-intensive AI work — close access to GPU hardware and drivers, without the overhead of managing raw instances ourselves. Kueue’s native integration with GKE, including with Google Cloud capacity types like</span> <a href="https://cloud.google.com/spot-vms"><span style="text-decoration: underline; vertical-align: baseline;">Spot VMs</span></a><span style="vertical-align: baseline;"> and</span><a href="https://cloud.google.com/blog/products/compute/introducing-dynamic-workload-scheduler"><span style="vertical-align: baseline;"> </span><span style="text-decoration: underline; vertical-align: baseline;">Dynamic Workload Scheduler</span></a><span style="vertical-align: baseline;">, meant that once our reserved capacity filled up, the same scheduling logic could reach out to elastic capacity automatically instead of leaving jobs stuck.</span></p>
<h3><span style="vertical-align: baseline;">Closing the loop with open source</span></h3>
<p><span style="vertical-align: baseline;">Adopting Kueue turned into something bigger than a simple process change. Because we partner with Google Cloud, we have a direct line to a Technical Account Manager, who saw an opportunity to make AI21 a design partner for the Kueue team. This way, we wouldn’t just be a user, but a source of real production requirements that could help shape where the tool went next. </span></p>
<p><span style="vertical-align: baseline;">One of the first things to come out of that partnership was a requirements document we shared with the Kueue team, describing behavior we needed that didn’t exist yet: fair admission ordering across teams for multi-node jobs, without the preemption that usually comes bundled with fairness. The Kueue team built it.</span> <a href="https://kueue.sigs.k8s.io/docs/concepts/admission_fair_sharing/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Admission Fair Sharing</span></a><span style="vertical-align: baseline;"> (AFS) reorders the admission queue to favor teams that have historically used less capacity without disrupting jobs already running. Around the same time, we also turned on</span> <a href="https://kueue.sigs.k8s.io/docs/concepts/topology_aware_scheduling/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Topology Aware Scheduling</span></a><span style="vertical-align: baseline;">. This existing feature made Kueue aware of our physical cluster layout, so it can refuse to admit jobs that won’t fit on a single node rather than placing them with nowhere to run. </span></p>
<p><span style="vertical-align: baseline;">For us, that’s what the best-case open-source feedback loop looks like: Real requirements surfaced through production use, fed directly back into Kueue.</span></p>
<h3><span style="vertical-align: baseline;">Same fleet, less friction</span></h3>
<p><span style="vertical-align: baseline;">The Slack </span><span style="vertical-align: baseline;">#gpu-resources channel is archived now. Every workload, whether a debug pod, a multi-node training run, or an inference deployment, gets queued, prioritized, and scheduled automatically. The results were immediate. Manual interventions dropped from about 20 a week to zero. High-priority jobs that used to wait up to 72 hours now wait 12. Fragmentation across the cluster fell from 15% to 8%, and the “zombie job” problem — workloads partially admitted with nowhere to run — is gone.</span></p>
<p><span style="vertical-align: baseline;">None of this changed our total cost. We run our reserved fleet at close to 100% utilization on purpose, so raw spend was never the variable we were optimizing. What changed is where our people’s time goes. Team leads aren’t refereeing compute disputes anymore, and researchers aren’t waiting on replies in Slack. That frees everyone to run more experiments and iterate faster.</span></p></div>
