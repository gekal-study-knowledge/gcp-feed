### Querying Databricks Apache Iceberg Tables with the borderless Lakehouse

- **Link**: [https://cloud.google.com/blog/products/data-analytics/querying-databricks-iceberg-tables-with-google-clouds-lakehouse/](https://cloud.google.com/blog/products/data-analytics/querying-databricks-iceberg-tables-with-google-clouds-lakehouse/)

- **Fetched**: 2026-10-30 01:36:45

<details class="entry-summary">
<summary>詳細を表示</summary>
<div class="block-paragraph_advanced"><p style="text-align: justify;"><span style="vertical-align: baseline;">Enterprise organizations often leverage multiple data platforms, including Databricks, to execute heavy Apache Spark jobs alongside BigQuery to power highly concurrent analytics workloads. Historically, bridging these systems often meant building complex pipelines to copy data between environments. This approach increases storage costs, introduces latency, and fragments security controls.</span></p>
<p style="text-align: justify;"><span style="vertical-align: baseline;">With Google Cloud’s borderless Lakehouse, you can now query Databricks-managed Apache Iceberg tables straight from BigQuery. This zero-copy approach removes the need to duplicate data: BigQuery reads the same files Databricks writes, and new changes appear after Lakehouse's next scheduled metadata refresh (as often as every 5 minutes).</span></p></div>

<div class="block-paragraph_advanced"><h4 style="text-align: justify;"><strong style="vertical-align: baseline;">How Lakehouse and Databricks work together</strong></h4>
<p style="text-align: justify;"><span style="vertical-align: baseline;">Managed Iceberg tables automatically generates Iceberg-compatible metadata alongside native Delta logs. Data engineering teams can store Parquet files once in Google Cloud Storage (GCS) using Databricks. Rather than loading this information into BigQuery, Lakehouse reads the Iceberg metadata directly, applying BigQuery’s vectorized engine directly to open-format files in GCS.</span></p>
<p style="text-align: justify;"><span style="vertical-align: baseline;">Although Google Cloud Storage (GCS) serves as the primary storage layer in the above example, Lakehouse extends this borderless federation directly to external cloud environments like Amazon S3 and Azure Blob Storage. By pairing the open Apache Iceberg REST Catalog with cross-cloud connections, Lakehouse lets BigQuery query data across clouds without moving it. Each federated catalog lives in a Google Cloud location you choose, ideally the region closest to your data. This lets BigQuery read open-format Parquet files where they live, delivering multi-cloud analytics without replication pipelines. Remote-cloud egress charges still apply, but Cross-Cloud Interconnect (AWS) and Lakehouse caching can reduce them.</span></p>
<p style="text-align: justify;"><span style="vertical-align: baseline;">Beyond simply querying external data, Lakehouse framework establishes true read and write (R/W) interoperability across engines. Because the platform is built on an open Apache Iceberg foundation, data teams can effortlessly execute multi-statement SQL commands directly inside BigQuery.</span></p>
<h4 style="text-align: justify;"><strong style="vertical-align: baseline;">Centralized security and governance</strong></h4>
<p style="text-align: justify;"><span style="vertical-align: baseline;">Handling access controls across disparate systems can introduce vulnerabilities. Lakehouse addresses this through delegated access. Administrators can configure a BigQuery Cloud Resource Connection tied to a service account that manages IAM rights for GCS buckets. Granting users access to the Lakehouse table entity lets you enforce BigQuery controls including row-level, column-level security, and dynamic data masking on external Iceberg tables while Databricks handles ingestion.</span></p>
<h4 style="text-align: justify;"><strong style="vertical-align: baseline;">Catalog federation and credential vending</strong></h4>
<p style="text-align: justify;"><span style="vertical-align: baseline;">Previously, connecting these platforms meant manually configuring BigQuery queries to point at static metadata paths. Modern setups leverage the open Apache Iceberg REST Catalog API. Databricks Unity Catalog functions as the central metadata layer, allowing a BigQuery administrator to establish a Lakehouse runtime catalog with a federated connection. When running a query, Lakehouse contacts Unity Catalog for current table state, and short-lived tokens are issued through credential vending to grant BigQuery temporary read access to GCS.</span></p>
<h4 style="text-align: justify;"><strong style="vertical-align: baseline;">Partition pruning</strong></h4>
<p style="text-align: justify;"><span style="vertical-align: baseline;">BigQuery uses each table's Iceberg metadata to plan the query, then reads only the relevant data files in place. Iceberg's hidden partitioning lets you filter on logical columns, such as timestamps, without knowing the directory layout. Note that Databricks managed Iceberg tables don't support partition transforms; Databricks recommends liquid clustering instead.</span></p>
<p style="text-align: justify;"><span style="vertical-align: baseline;">Filters in a standard WHERE clause let BigQuery use the Iceberg manifests to skip partitions that can't match. Compare partition columns with literal values so pruning can apply. These manifests maintain detailed column-level statistical bounds, enabling BigQuery to bypass irrelevant manifest records and unneeded Parquet files immediately. Consequently, queries scan only necessary byte ranges, accelerating query execution while significantly reducing on-demand slot consumption and storage scan costs.</span></p>
<h4 style="text-align: justify;"><strong style="vertical-align: baseline;">Fast queries with Iceberg metadata and Lakehouse caching</strong></h4>
<p style="text-align: justify;"><span style="vertical-align: baseline;">Iceberg manifests already identify which data files to read, so BigQuery doesn't need a metadata cache for Iceberg tables. For cross-cloud tables, such as those in Amazon S3, Lakehouse caching (Preview) keeps retrieved data blocks in Google Cloud so repeat queries read them locally. BigQuery reads the Iceberg manifest files directly when it plans each query; there's no metadata caching to enable. This dynamic partition pruning bypasses unneeded files, significantly reducing runtime and bytes scanned.</span></p>
<h4 style="text-align: justify;"><strong style="vertical-align: baseline;">Maintenance and lifecycle management</strong></h4>
<p style="text-align: justify;"><span style="vertical-align: baseline;">Modern lakehouses demand active upkeep; without routine care, performance degrades into an inefficient repository. Fortunately, both BigQuery and Databricks supply native capabilities to preserve table hygiene and accelerate analytical workloads.</span></p>
<h4 style="text-align: justify;"><strong style="vertical-align: baseline;">Keeping your tables optimized</strong></h4>
<p style="text-align: justify;"><span style="vertical-align: baseline;">To maintain optimal query performance, active maintenance of your lakehouse storage footprint remains necessary.</span></p>
<ol>
<li style="vertical-align: baseline;">
<p style="text-align: justify;"><span style="vertical-align: baseline;">Trigger regular compaction pipelines via Databricks APIs to merge tiny Parquet files into larger, optimized layouts and use Predictive Optimization.</span></p>
</li>
<li style="vertical-align: baseline;">
<p style="text-align: justify;"><span style="vertical-align: baseline;">Execute the Databricks VACUUM command to clear unreferenced files outside active snapshots, avoiding extra GCS storage costs.</span></p>
</li>
</ol>
<h4 style="text-align: justify;"><strong style="vertical-align: baseline;">Compaction and the small file problem</strong></h4>
<p style="text-align: justify;"><span style="vertical-align: baseline;">Frequent write operations, continuous ingestion jobs, and streaming workloads continuously produce thousands of small Parquet files. This fragmentation creates a storage bottleneck that can limit BigQuery’s reading efficiency. Establishing thousands of network connections to GCS and processing metadata footers across numerous tiny files consumes significant compute time, diminishing the performance advantages of vectorized query execution.</span></p>
<p style="text-align: justify;"><span style="vertical-align: baseline;">Running routine compaction within Iceberg resolves these inefficiencies. Databricks manages this automatically using Liquid Clustering which dynamically adjusts file layouts based on access patterns or through native table management utilities.</span></p>
<p style="text-align: justify;"><span style="vertical-align: baseline;">To compact small files manually on Databricks, run OPTIMIZE:</span></p></div>

    <dt>code_block</dt>

The binpack approach operates rapidly by prioritizing total file size balancing, though alternative sorting strategies can organize dataset ordering along specific column keys.</span></p>
<h4 style="text-align: justify;"><strong style="vertical-align: baseline;">Managing orphan files and snapshot retention (VACUUM)</strong></h4>
<p style="text-align: justify;"><span style="vertical-align: baseline;">Every transactional update, record modification, and table compaction creates fresh snapshots within Iceberg to preserve dataset integrity. Over time, historical Parquet objects detached from active table states become orphaned. Although these legacy files facilitate time-travel analytics, neglecting them can drive up GCS storage charges over time.</span></p>
<p style="text-align: justify;"><span style="vertical-align: baseline;">Data teams can use the Databricks VACUUM operation to scan and purge abandoned storage files.</span></p></div>

    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &quot;ALTER TABLE customer_events SET TBLPROPERTIES (&#x27;delta.deletedFileRetentionDuration&#x27; = &#x27;7 days&#x27;);\r\nVACUUM customer_events FULL;&quot;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7fbba8b31710&gt;)])]&gt;</dd>

<div class="block-paragraph_advanced"><p style="text-align: justify;"><span style="vertical-align: baseline;">Standard configurations apply a mandatory seven-day threshold (deletedFileRetentionDuration) before executing VACUUM routines. Preserving this delay prevents active analytical jobs from encountering missing file errors while keeping historical recovery options available. Scheduling routine VACUUM jobs, or letting predictive optimization run them, removes unreferenced data files and, for tables with Iceberg reads, old Iceberg metadata. That keeps storage costs low and performance high across your lakehouse.</span></p>
<h4 style="text-align: justify;"><strong style="vertical-align: baseline;">Conclusion</strong></h4>
<p style="text-align: justify;"><span style="vertical-align: baseline;">Connecting Databricks Apache Iceberg datasets to Lakehouse can help you activate your data with BigQuery. By separating processing from underlying storage, embracing open formats, and using standard REST APIs with credential vending, you can run scalable engineering workloads and concurrent analytics without migrating data or sacrificing performance</span></p>
<p style="text-align: justify;"><span style="vertical-align: baseline;">Pairing Databricks Iceberg reads (UniForm) with Lakehouse federation, Lakehouse caching, and regular OPTIMIZE and VACUUM maintenance helps you build an efficient, zero-copy lakehouse. This approach can help lower storage spend, avoids fragile pipeline maintenance, and prepares your data environment for modern analytics and emerging AI workloads.</span></p>
<p style="text-align: justify;"><span style="vertical-align: baseline;">Constructing a unified architecture no longer requires moving data files across platforms. You can begin querying Databricks Iceberg tables by registering them with the Lakehouse runtime catalog today for bi-directional federation. Learn more by reading our </span><a href="https://docs.cloud.google.com/lakehouse/docs/set-up-cross-cloud-connection-databricks"><span style="text-decoration: underline; vertical-align: baseline;">documentation</span></a><span style="vertical-align: baseline;"> to get started.</span></p></div>

      <p>The Google Cloud Vulnerability Reward Program (VRP) partners with the global security research community to help elevate cloud security for all by encouraging the discovery of critical software vulnerabilities. In an era when automated research has made it more challenging to verify authentic vulnerabilities, we have a critical need to boost high-level, human-led research that can transcend automated-only discovery.</p><p>Today, we are expanding our top reward tier with a <a href="https://bughunters.google.com/">new $250,000 Root-in-Cloud reward</a>, specifically designed to recognize high-impact architectural research. Identifying tenant-isolation bypasses and complex cross-service logic flaws requires human creativity, intuition, and rigorous systems analysis combined with the power of agentic systems.</p><p>To earn this premier reward, you must demonstrate full administrative control, the equivalent of “roles/owner” or complete IAM control, over arbitrary Google Cloud organizations or projects with no prior access or special project setup.</p><p>The exploit path can not depend on:</p><ul><li>Pre-existing access or footholds in the victim project.</li><li>Leaked, phished, or stolen credentials.</li><li>User interaction or social engineering.</li></ul>

<div class="block-paragraph_advanced"><p><strong><span style="vertical-align: baseline;">Proof-of-root: Clear, cryptographic validation</span></strong></p>
<p><span style="vertical-align: baseline;">To make testing safe, clear, and reproducible, without impacting production environments, we have defined </span><a href="https://bughunters.google.com/about/rules/google-friends/cloud-vulnerability-reward-program-rules" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">technical criteria for validating root-in-cloud access</span></a><span style="vertical-align: baseline;">.</span></p>
<p><span style="vertical-align: baseline;">Additionally, valid vulnerability reports demonstrating remote code execution (RCE) in underlying Google production infrastructure (Borg) or achieving root-in-prod will automatically be evaluated by the Google Cloud VRP panel for root-in-cloud eligibility.</span></p>
<p><span style="vertical-align: baseline;">Because code execution in Borg has the potential to impact service availability or cross-tenant data, researchers must halt all probing immediately upon achieving any execution in Borg. Escalation, extracting production credentials, and lateral movement are not allowed and will result in researcher disqualification. </span></p>
<p><span style="vertical-align: baseline;">The Google Cloud VRP panel will analyze the initial entry point, execution context, and attack surface to determine whether full arbitrary tenant or project takeover is achievable from that position, and award the bounty accordingly. </span></p>
<p><span style="vertical-align: baseline;">This new bounty tier reflects how security research continues to evolve, and the importance of continuing to recognize the most innovative and valuable security research. As part of those efforts, Google Security held its annual Escal8 conference in Singapore last week, and I had the opportunity to discuss the changing landscape with Michael Cote, Google Cloud’s vulnerability reward program lead. </span></p>
<p><span style="font-style: italic; vertical-align: baseline;">The following transcript has been lightly edited.</span></p>
<p><strong style="vertical-align: baseline;">Chris Betz</strong><span style="vertical-align: baseline;">: You are at Escal8 in Singapore announcing the new $250,000 Root-in-Cloud tier for our VRP. Why introduce this tier now, and what kind of research are you hoping to spark?</span></p>
<p><strong style="vertical-align: baseline;">Michael Cote</strong><span style="vertical-align: baseline;">: This is a recognition of how the field of security research has changed over the past year. We value quality submissions from anyone, and we’ve seen that the combination of human creativity and agentic power is much richer than either on its own.</span></p>
<p><span style="vertical-align: baseline;">While automated scanners generate a high volume of low-impact noise, first-time researchers who pair human intuition with agentic tools are finding, on average, more interesting bugs than novices did two years ago. With the new Root-in-Cloud tier, we want to challenge the community and increasingly reward the complex, high-impact findings — like tenant-isolation bypasses and cross-service logic flaws — that require deep architectural intuition alongside agentic tools, because getting that information is essential to protecting our customers.</span></p>
<p><strong style="vertical-align: baseline;">Chris Betz</strong><span style="vertical-align: baseline;">: Google Threat Intelligence Group (GTIG) recently shared research showing that </span><a href="https://cloud.google.com/blog/topics/threat-intelligence/vulnerability-discovery-and-exploitation-trends-in-the-ai-era"><span style="text-decoration: underline; vertical-align: baseline;">monthly CVE disclosures have doubled</span></a><span style="vertical-align: baseline;"> as agentic tools mature. From your seat leading the Cloud VRP, how has automation technology impacted the reports we’ve received? </span></p>
<p><strong style="vertical-align: baseline;">Michael Cote</strong><span style="vertical-align: baseline;">: It has transformed our intake volume, though not in the way many people assume. While the number of valid vulnerability reports submitted to the Google Cloud VRP has remained stable over the last 18 months, the total number of reports has grown tremendously. </span></p>
<p><span style="vertical-align: baseline;">Automation has helped democratize vulnerability discovery, and the barrier to entry has been rapidly flattening, something even our top researchers noted at Escal8. Because we’re seeing more researchers and more first-timers with interesting bugs, that creates pressure on more experienced researchers to move faster and bring more impactful findings — although their experience continues to be a key differentiator in success.</span></p>
<p><strong style="vertical-align: baseline;">Chris Betz</strong><span style="vertical-align: baseline;">: I’ve been working with the research community for more than 20 years. One of the things I appreciate most is how much the community values making the world more secure. Bounty programs let us recognize this valuable work. How do you see the community changing as we move further into the agentic era? </span></p>
<p><strong style="vertical-align: baseline;">Michael Cote</strong><span style="vertical-align: baseline;">: That shared commitment to making the world more secure is still the heart of this community, which is why the pressure to move faster is something we have to watch closely. As our GTIG colleagues found, the sharpest rise in the number of exploited vulnerabilities comes from </span><a href="https://cloud.google.com/blog/topics/threat-intelligence/vulnerability-discovery-and-exploitation-trends-in-the-ai-era"><span style="text-decoration: underline; vertical-align: baseline;">n-days, not zero-days</span></a><span style="vertical-align: baseline;">. </span></p>
<p><span style="vertical-align: baseline;">Open source accounts have suggested that threat actors are using LLMs to rapidly turn newly-public vulnerability details into working exploits. When triage teams are already working through a surge in report volume, disclosing an unmitigated vulnerability well ahead of the standard 90-day coordinated disclosure window gives attackers the exact knowledge and time window they need to target customers.</span></p>
<p><span style="vertical-align: baseline;">With the influx of new submissions, I worry about a growing pressure to rush to publish. Something that concerns me because we’re already seeing early indications of it. Because LLMs lower the barrier to finding bugs in source-available software, researchers worry that waiting to verify risks will allow someone else to be first to publish. Even more concerning, that same competitive pressure can tempt even established security companies to disclose unmitigated vulnerabilities without coordination, and that rush puts our users directly at risk.</span></p>
<p><a href="https://projectzero.google/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Project Zero</span></a><span style="vertical-align: baseline;"> helped establish the industry’s 90-plus-30-day responsible disclosure policy, and autonomous detection and exploitation capabilities make following coordinated disclosure more important than ever. In the long run, rushing to be first works against a security company's own self-interest. Novel discoveries may bring temporary visibility, but customers will ultimately choose not to work with organizations that put them and the broader ecosystem at risk. </span></p>
<p><strong style="vertical-align: baseline;">Chris Betz</strong><span style="vertical-align: baseline;">: When you offer a $250,000 bounty, how do you make sure researchers can validate their findings without putting customer environments or service availability at risk?</span></p>
<p><strong style="vertical-align: baseline;">Michael Cote</strong><span style="vertical-align: baseline;">: High incentives require clear, safe rules of engagement. We never want researchers testing exploits against real customer projects. Instead, we created a deterministic proof-of-root mechanism using a designated service account. Researchers can cryptographically prove unauthorized access against that identity.</span></p>
<p><span style="vertical-align: baseline;">We’ve also updated our </span><a href="https://bughunters.google.com/about/rules/google-friends/cloud-vulnerability-reward-program-rules#root-in-cloud-technical-validation" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">program rules</span></a><span style="vertical-align: baseline;"> to establish strict boundaries around underlying production infrastructure. If researchers think they are close to a breakthrough but are uncertain where the boundary lies, we encourage them to reach out. We are always more than happy to work with them to ensure they are recognized and rewarded for the value of their research without taking steps that would invalidate the bounty.</span></p>
<p><strong style="vertical-align: baseline;">Chris Betz</strong><span style="vertical-align: baseline;">: What should enterprise CISOs take away from these trends? Especially those who run their own vulnerability management pipelines and partner with external researchers, what advice would you offer for navigating this AI inflection point?</span></p>
<p><strong style="vertical-align: baseline;">Michael Cote</strong><span style="vertical-align: baseline;">: First, prepare your vulnerability triage workflows for agent-generated submissions. To keep valid reports from getting stuck in a backlog, security teams need ways to separate plausible-sounding hallucinations from real security risks.</span></p>
<p><span style="vertical-align: baseline;">Second, compress your remediation timelines once a vulnerability becomes public. Defensive patching and mitigations have to move faster because autonomous technology compresses the time from disclosure to working exploits.</span></p>
<p><span style="vertical-align: baseline;">Finally, hold your security partners and vendors to high standards of coordinated disclosure. It’s important that our industry continues to </span><a href="https://cloud.google.com/blog/products/identity-security/cloud-ciso-perspectives-ai-vendors-should-share-vulnerability-research-heres-why/"><span style="text-decoration: underline; vertical-align: baseline;">normalize agentic vulnerability research</span></a><span style="vertical-align: baseline;">, but we must do so responsibly. Let’s continue to keep user safety at the center of everything we do.</span></p>
<p><span style="vertical-align: baseline;">For more information on the Google Cloud VRP, including detailed endpoint specifications, JSON payloads, and CLI examples, please check out our </span><a href="https://bughunters.google.com/about/rules/google-friends/cloud-vulnerability-reward-program-rules#root-in-cloud-technical-validation" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">rules page</span></a><span style="vertical-align: baseline;">.</span></p></div>

### Grounding agents in one context graph connecting semantic models you already trust

- **Link**: [https://cloud.google.com/blog/products/data-analytics/expanded-semantic-model-support-in-knowledge-catalog/](https://cloud.google.com/blog/products/data-analytics/expanded-semantic-model-support-in-knowledge-catalog/)

<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">Picture the scene: Before an executive business review, your VP of Sales asks an AI assistant, </span><span style="font-style: italic; vertical-align: baseline;">"What was net revenue for our top enterprise accounts last quarter?"</span><span style="vertical-align: baseline;"> In seconds, the agent returns a polished chart! Unfortunately, the numbers don't match the finance report. Why? Because the agent counted cancelled orders as revenue and pulled from an unvalidated staging table.</span></p>
<p><span style="vertical-align: baseline;">The agent didn't fail because of the model, or because it couldn't translate a user question into a query. It failed because </span><span style="font-style: italic; vertical-align: baseline;">it didn't understand your business</span><span style="vertical-align: baseline;">. The real kicker is that understanding usually already exists in the form of a semantic model in a Looker, dbt, Snowflake, Databricks, or SAP system. But because each definition stays locked inside its own tool, every agent guesses at it… and often gets it wrong. </span></p>
<p><span style="vertical-align: baseline;">This is where </span><a href="https://cloud.google.com/products/knowledge-catalog"><span style="text-decoration: underline; vertical-align: baseline;">Knowledge Catalog</span></a><span style="vertical-align: baseline;"> comes in. It brings the semantic models from all of those tools into one context graph, so every agent works from the same trusted definitions. And when two tools define the same metric differently, both definitions appear with their provenance, so data stewards can reconcile the conflict before it reaches end users.</span></p>
<p><span style="vertical-align: baseline;">Today, we're announcing the general availability of expanded semantic model support. Knowledge Catalog now natively ingests semantic models and metric definitions from Looker LookML, BigQuery Graph (including BigQuery measures), dbt MetricFlow, Snowflake Semantic Views, Databricks Metric Views, and SAP Core Schema Notation (CSN), and connects them with schema, lineage, data profiles, business glossary and other key metadata in a single context graph, without moving data or rewriting business logic in a new language. </span></p>
<p><span style="vertical-align: baseline;">By grounding your AI agents in those models, they get the same business definitions your analysts rely on, so their answers line up with the numbers your business trusts. In fact, based on internal benchmarks, grounding agents in Knowledge Catalog makes them nearly 4X more accurate, with up to 33% lower latency, and using up to 75% fewer tokens.</span></p>
<p><span style="vertical-align: baseline;">The unified context graph enables you to:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Reuse the semantic models you already trust:</strong><span style="vertical-align: baseline;"> Knowledge Catalog grounds </span><a href="https://docs.cloud.google.com/gemini/enterprise/docs/connectors/connect-knowledge-catalog#configure-knowledge-catalog"><span style="text-decoration: underline; vertical-align: baseline;">Gemini </span></a><span style="vertical-align: baseline;">agent, BigQuery Conversational Analytics, and your custom agents in the metrics, filters, and join paths your teams have already defined, wherever they live.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Go beyond hand-curated definitions with self-learned context: </strong><span style="vertical-align: baseline;">Knowledge Catalog pairs the well-defined metrics and KPI definitions in your semantic models with relevant context it extracts from unstructured knowledge sources, such as operational playbooks, meeting notes, chat threads, code, and more. Powered by Gemini, </span><a href="https://cloud.google.com/blog/products/data-analytics/knowledge-catalog-self-learning-context-enrichment-for-ai-agents?e=48754805"><span style="text-decoration: underline; vertical-align: baseline;">self-learning enrichment</span></a><span style="vertical-align: baseline;"> continuously finds missing or outdated context and turns it into governed, reusable context sets, ensuring your agents' context stays current as definitions change, without relying only on manual curation.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Pair business logic with enterprise trust: </strong><span style="vertical-align: baseline;">Even the right formula produces the wrong answer when it runs on stale or uncertified data. ### DHL Express が長年にわたる現場の知見をスマートなグローバル ネットワークへと進化させた方法

<details class="entry-summary">
<summary>詳細を表示</summary>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">※この投稿は米国時間 2026 年 9 月 16 日に、Google Maps Platform blog に</span><a href="https://mapsplatform.google.com/resources/blog/how-dhl-express-is-turning-decades-of-courier-knowledge-into-a-smarter-global-network/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">投稿</span></a><span style="vertical-align: baseline;">されたものの抄訳です。</span></p>
<p><span style="font-style: italic; vertical-align: baseline;">編集者注: 今回のブログ記事は、DHL Express の EVP 兼 CTO である Dirk Olufs 氏によるものです。DHL Express が Google Maps Platform を活用して B2C オペレーションをグローバルに拡大し、配送の正確性を向上させるとともに、約 4 万人の配達員にリアルタイムのナビゲーションとインテリジェンスを提供している方法をご紹介いただきました。</span></p>
<hr />
<p><span style="vertical-align: baseline;">DHL Express は、誰も不可能だと思う速さで荷物を届けるという、シンプルなアイデアから生まれました。創業当初は、創業者自らが手作業で荷物を運んでいました。それが数年後には、株式市場が開く前のニューヨークに届けるため、銀行書類を携えてコンコルドで大西洋を飛び越えるまでになりました。テクノロジーは常に、約束を果たすためのものでした。e コマースが普及し、1 日 150 万件の配送のほぼ半分が、日々異なる 220 か国にわたる住宅宛てになったときも、その約束は変わりませんでした。しかし、テクノロジーは進化させる必要がありました。</span></p>
<p><span style="vertical-align: baseline;">ある世界向けに構築されたネットワークを、別の世界にサービスを提供するためにモダナイズする必要があった際、課題となったのは技術的なことではなく、「人」に関わることでした。DHL Express の最大の強みは、常に「人」にあります。何十年も現場を支えてきた配達員たちは、いかなるシステムでも再現し得ない貴重な知識を持っています。どの入口を使用するか、どこに駐車するか、受付が正午に閉まるのはどの建物か。私たちの仕事は、そうした知識を置き換えることではなく、それらにふさわしいテクノロジーを構築し、現場の人々と共に歩むことでした。</span></p>
<p><span style="vertical-align: baseline;">人を第一に考える企業は、そう簡単に変われない一面も持ち合わせています。テクノロジーが配達員に対し、8 時間ずっと指示を出し続けるだけでは、配達員に大きなストレスがかかるでしょう。そのため、何かを拡大する際は、まず現場の理解と協力を得る必要がありました。トップダウンではなく、現場主導で進める必要があります。</span></p>
<h3><span style="vertical-align: baseline;">可視化されていなかったものから基盤を構築</span></h3>
<p><span style="vertical-align: baseline;">2009 年に、「配達員にナビゲーション機能を提供できないか」という声が上がったとき、答えは明白に思えました。</span><a href="https://mapsplatform.google.com/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Google Maps Platform</span></a><span style="vertical-align: baseline;"> がすでに解決策を提示していたからです。しかし、本当の問題はナビゲーションではなく、住所であることがわかってきました。</span></p>
<p><span style="vertical-align: baseline;">住所の構造は地域によって実にさまざまです。中東では多くの場所に郵便番号、番地、建物名がなく、ランドマークでしか住所を特定できません。また、人口密度の高いアジアの都市では、配達員は個々の住所ではなく、指定の受け渡し場所に荷物を届けるのが一般的です。上海からドバイ宛てに発送するお客様が、中国の住所構造で宛先を記入することもあります。その住所データを、英語で処理するシステム、UAE 現地の配達員、アラビア語を使う受取人の全員が理解できなければなりません。配達が完了するまでのあらゆるステップで、適切な形式の適切な情報が必要になるのです。</span></p>
<p><span style="vertical-align: baseline;">従来のシステムでは、その複雑さに対応することができませんでした。配送フォームに記入する顧客は、不適切なデータを提供しようとしているわけではありません。ただ、適切なデータがどのようなものかを知らないだけです。そこで、配達員に届いた時点で不適切な住所を修正するのではなく、情報の入力元に立ち返ることにしました。</span></p>
<p><span style="vertical-align: baseline;">私たちは Google Maps Platform の実装パートナーである</span><a href="https://onigroupglobal.com/" rel="noopener" target="_blank"><span style="vertical-align: baseline;"> </span><span style="text-decoration: underline; vertical-align: baseline;">OniGroup</span></a><span style="vertical-align: baseline;"> と協力して、</span><a href="https://developers.google.com/maps/documentation/address-validation/overview?hl=en" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Address Validation</span></a><span style="vertical-align: baseline;">、</span><a href="https://developers.google.com/maps/documentation/places/web-service?hl=en" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Places API</span></a><span style="vertical-align: baseline;">、</span><a href="https://developers.google.com/maps/documentation/geocoding/overview?hl=en" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Geocoding</span></a><span style="vertical-align: baseline;"> を活用した DHL 独自の住所インテリジェンス エンジン「DAVE」を構築しました。DAVE は住所入力の時点で情報を検証して補強し、その場所が住宅か、事業所か、営業時間はいつか、配達員はどこから入ればよいかといった情報を教えてくれます。これにより、日中に不在の個人宅や、受付が閉まった後のオフィスビルへ配達員を向かわせずに済むようになりました。一つひとつは些細な労力削減ですが、当社の事業規模では大きな意味を持ちます。DAVE の導入を通じて、レガシー インフラストラクチャから最新のコンテナ化された環境へと移行し、年間運用コストを 75% 削減するとともに、デプロイ速度を 7 倍に向上させることもできました。</span></p></div>

<div class="block-paragraph_advanced"><h3><span style="vertical-align: baseline;">配達員にリストだけでなく計画を提供</span></h3>
<p><span style="vertical-align: baseline;">長年にわたり、当社の配達員はハンドヘルド デバイスのリスト画面を頼りにしていました。表示されるのは配送先の一覧のみで、地図も、前後の状況把握も、1 日の配送ルートを可視化する手段もありませんでした。ルート計画に関する知識はすべて、彼らの頭の中にありました。ロンドンのウェンブリーにいた 20 年の経験を持つスーパーバイザーは、40 人のドライバーに 5,000 件の配送を割り当てる方法を知っていました。しかしその人が異動すると、知識も失われてしまいました。</span></p>
<p><span style="vertical-align: baseline;">私たちは、現場に一方的な指示を強制することなく、この状況を変えたいと考えました。</span><a href="https://mapsplatform.google.com/maps-products/navigation-sdk/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Navigation SDK</span></a><span style="vertical-align: baseline;"> と</span><a href="https://developers.google.com/maps/documentation/mobility/fleet-engine?hl=en" rel="noopener" target="_blank"><span style="vertical-align: baseline;"> </span><span style="text-decoration: underline; vertical-align: baseline;">Fleet Engine</span></a><span style="vertical-align: baseline;"> を統合することで、配達員に Android デバイスでターンバイターン方式のナビゲーションと、現地の状況を反映したリアルタイムの配送計画をを提供できるようになりました。しかし、最も重要だったのは、双方向のやりとりを可能にすることでした。配達員がデバイス上で直接住所を修正できるようになり、システムの位置情報が間違っていれば正しい場所にピンを立てるだけで、その修正がプラットフォームにフィードバックされます。配達員たちの暗黙知が、インフラストラクチャの一部になっていくのです。</span></p>
<p><span style="vertical-align: baseline;">テクノロジーが単に指示を出すだけでなく、学習するようになったことを知ると、配達員たちの意識は変わっていきました。テクノロジーが自分たちの作業負担を減らしてくれることを、配達員たちは実感しています。20 年間この仕事をしてきた私にとって、これは大きなことです。1 つの国で試験運用を行い、フィードバックを収集し、改善を重ねるといった形で、機能を段階的にリリースしてきました。常に長期的なビジョンを見据えつつ、一度にすべてを受け入れるよう強いることは決してしませんでした。このアプローチこそが、現場からの抵抗感をなくし、スムーズな定着を実現したのです。</span></p>
<h3><span style="vertical-align: baseline;">これまでの成果</span></h3>
<p><span style="vertical-align: baseline;">2021 年にお届け時間帯の提供を開始したとき、その時間帯に配達できたのは約 50% でした。現在の達成率は 80% 台後半で、主要市場では 90% に近づいています。2023 年にリリースされた Follow My Parcel 機能では、受取人が配達員の直前の立ち寄り先を追跡できます。</span></p>
<p><span style="vertical-align: baseline;">現在は、Google Maps Platform を活用した AI による </span><a href="https://developers.google.com/maps/documentation/route-optimization?hl=en" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Route Optimization </span></a><span style="vertical-align: baseline;">機能を試験運用しており、数十台の車両による数千件の配送データを分析して、移動時間と距離を短縮できる最適な配送計画を提案しています。私たちが提示するのは選択肢であり、命令ではありません。配達員は、確認、調整、フィードバックを行います。最良の結果は常に、テクノロジーが計算できるものと、人間が知っているものを組み合わせることで生まれます。</span></p>
<p><span style="vertical-align: baseline;">私たちが描く長期的なビジョンは、住所インテリジェンス、ナビゲーション、リアルタイムの可視化、そしてルート計画を一つに融合させた、シームレスな配送オペレーションの実現です。これまで数年にわたり、テクノロジーに自分たちを合わせるのではなく、DHL Express の働き方にテクノロジーを合わせるという形で、その基盤を築いてきました。目標はずっと変わっていません。誰もが不可能だと思うスピードで荷物を届けること、そして、それを現場で支える人々に、彼らにふさわしい最高のツールを提供することです。</span></p>

<div class="block-paragraph"><p>全国に 281 店舗以上のホームセンターを展開し、独自のプライベート ブランド（PB）商品の開発やデジタル戦略に注力する株式会社カインズ（以下、カインズ）。同社では、膨大な商品の発注・在庫管理を最適化するため、Google Cloud を基盤とした需要予測プロジェクトを推進しています。本記事では、アルゴリズムを自律的に進化させる AlphaEvolve（プレビュー版）を導入し、3 年間のチューニングの壁を突破して需要予測の誤差を 19% 改善した取り組みについて、同社の矢口氏と神戸氏にお話を伺いました。</p><p><b>利用しているサービス:<br /></b>BigQuery、AlphaEvolve</p><h3><b>全店舗・最大 3,000 万行におよぶ需要予測の歩みと、属人化からの脱却</b></h3><p>カインズにおける需要予測プロジェクトは 2021 年 11 月に発足し、約半年間のプロトタイプ検証を経て、2022 年 6 月にミニマムでの本番運用をスタートしました。その後、段階的に対象を拡大し、2024 年 9 月には約 200 店舗、2025 年 10 を対象に、単品別で 39 週先の需要予測を行っています。</li><li><b>短期予測（店舗の自動発注・在庫管理向け）：</b>店舗の在庫が一定水準を下回った際に自動で発注を行う「自動発注点管理」に用いられます。店舗の限られた在庫スペースを最適にコントロールするため、店舗別・単品別（SKU 別）に 6 週先の細かい予測を実施しています。通常時で約 190 万 SKU、繁忙期には最大 500 万 SKU（× 6 週間分で約 3,000 万行）という膨大な規模の予測を処理しています。</li></ul><p>この仕組みを導入する以前、長期予測においては各ディストリビューターの経験や個人のオペレーション マニュアルに依存しており、担当者のスキルによって発注精度にばらつきが生じることが課題でした。また、短期予測においても、従来は表計算ソフトで前年や直近の実績をもとに発注点を管理していましたが、直近実績だけでは季節性商品の立ち上がりを捉えきれず、欠品が発生するなどの課題を抱えていました。</p><p>Google Cloud の Vertex AI Forecasting 回、業務ユーザーと打ち合わせを行い、『ピークにもっと追従してほしい』『特定のイベントによる特需の影響は来年の予測から除外してほしい』といったドメイン知識や要望をヒアリングし、特徴量の出し入れやハイパーパラメーターの調整を行っていました。しかし、人間が自分で考えて調整し、検証を回すやり方では、試せる回数にも限界があり、本当にこのモデルが最適なのかを追求しきれないという実情がありました。」（矢口氏）</p><p>また、新商品が投入された際に既存商品の売上が分散する「カニバリゼーション（社内競合）」の予測も難題の一つでした。月 1 回のモデル再学習を行っていたものの、新商品の売れ行きトレンドが実績として現れるまでにはタイムラグが生じるため事前の予測が難しく、実績が出始めた後のトレンド変化やカテゴリー内の需要分散を素早く捉えるための特徴量設計も複雑を極めていました。3 年間にわたり PDCA 自身が自己学習的に新しいパラメーターや特徴量を何百、何千と自動で試し、テストと検証を繰り返して最適解を導き出してくれる仕組みでした。AlphaEvolve を見たとき、『これならモデルの改善を自動でやってくれるのではないか』と強い可能性を感じました。」（矢口氏）</p><p>「需要予測の精度を高める」という明確な評価指標を持っていたカインズにとって、目標に向かって自律的にアルゴリズムを進化させる <div class="block-paragraph_advanced"><h3><strong style="vertical-align: baseline;">予測誤差を 19% 削減し、複数モデルの統合による運用効率化とコスト削減を実現</strong></h3>

<h3><strong style="vertical-align: baseline;">今後の展望：人が特徴量を考える時代から、AI が自らモデルを進化させる時代へ</strong></h3>

### AURA、Google Maps Platform で緊急対応を迅速化し、派遣コストを 50% 削減

<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">※この投稿は米国時間 2026 年 10 月 2 日に、Google Maps Platform blog に</span><a href="https://mapsplatform.google.com/resources/blog/aura-speeds-up-emergency-response-and-reduces-dispatch-costs-by-50-percent-with-google-maps-platform/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">投稿</span></a><span style="vertical-align: baseline;">されたものの抄訳です。</span></p>

<h3><span style="vertical-align: baseline;">信頼性と拡張性に優れたグローバル規模の地図プロバイダでユーザーの信頼を構築</span></h3>
<p><span style="vertical-align: baseline;">緊急通報があった場合、一分一秒が重要になります。しかし、従来の緊急対応システムは、多くの場合、人手による電話対応、地域ごとの管制センター、無線による派遣に頼っています。通報者も、いつ救助が到着するかわからない不安のなかで待たされることもあります。</span></p>
<p><a href="https://www.aurasos.com/en-us" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">AURA</span></a><span style="vertical-align: baseline;"> は、この問題の解決を目指しています。南アフリカで設立された当社の使命は、緊急対応を迅速かつ透明性の高いものにし、どこからでもアクセスできるようにすることで、より安全な世界を作ることです。当社のプラットフォームは、モバイルアプリ、インターネットに接続されたパニックボタン、ウェアラブル、配車サービスなどのソースから緊急信号を受信し、支援を必要とする人々を、最も近い検証済みの民間警備会社や医療従事者に直接つなげます。</span></p>
<p><span style="vertical-align: baseline;">この迅速な対応を実現するためには、正確な地理空間データと地図データが必要です。以前は、さまざまな地域のさまざまな地図プロバイダを使用していましたが、これらのツールは、リアルタイム交通情報や通行止めを考慮した正確な予定到着時刻（ETA）を提供することが困難でした。そのため、困った状況にある利用者に不必要な不安を与え、プラットフォームに対する信頼を損なうリスクが生じていました。さらに、地域間の一貫性がなかったため、一部の現場対応者は他の地域よりも不便な思いをしていました。当社がその地域に導入した地図サービスを利用する代わりに、個人のスマートフォンで Google マップを利用する者さえいました。</span></p>
<p><span style="vertical-align: baseline;">英国や米国など、グローバル市場への急速な拡大をサポートするには、正確で一貫性のあるリアルタイムの交通データとグローバルな規模を備えた最高クラスのマッピング パートナーが必要でした。そこで、Google Maps Platform のパートナーである</span><a href="https://www.localyse.eu/" rel="noopener" target="_blank"><span style="vertical-align: baseline;"> </span><span style="text-decoration: underline; vertical-align: baseline;">Localyse</span></a><span style="vertical-align: baseline;"> との連携を通じて、サービスの基盤として</span><a href="https://mapsplatform.google.com/" rel="noopener" target="_blank"><span style="vertical-align: baseline;"> </span><span style="text-decoration: underline; vertical-align: baseline;">Google Maps Platform</span></a><span style="vertical-align: baseline;"> を選択しました。Google マップは、当社が必要とするデータ品質、ユーザーの親しみやすさ、グローバルなリーチを提供してくれます。通報者が「救助が向かっている」と聞けば、その言葉を信じて待つことができます。</span></p>
<p><span style="vertical-align: baseline;">緊急対応は本質的に複雑でリスクが高いため、この移行を進めるには、コンプライアンスに関する特有の課題を克服する必要がありました。位置情報インテリジェンスにおけるパートナーである Localyse は、プロジェクトを推進するための重要なサポートとガイダンスを提供してくれました。Localyse は、Google のプロダクト チームおよびコンプライアンス チームと緊密に連携し、安全性と運用上の要件がすべて満たされていることを確認したうえで、契約への道を開いてくれました。</span></p></div>

<div class="block-paragraph_advanced"><h3><span style="vertical-align: baseline;">Navigation SDK と Places API で派遣と管制室の業務を効率化</span></h3>
<p><span style="vertical-align: baseline;">当社は、派遣プロセス全体に Google Maps Platform を活用しました。現場では、提携する対応者向けモバイルアプリに</span><a href="https://mapsplatform.google.com/maps-products/navigation-sdk/" rel="noopener" target="_blank"><span style="vertical-align: baseline;"> </span><span style="text-decoration: underline; vertical-align: baseline;">Navigation SDK</span></a><span style="vertical-align: baseline;"> を直接組み込みました。対応者は、アプリを離れることなく、ターンバイターンの運転ルート、車線案内、徒歩ルートを取得できるため、緊急事態に可能な限り迅速に対応できます。インターフェースは使い慣れた直感的なものであるため、習得が簡単で、ストレスの多い通話中でもスムーズに操作できます。</span></p>
<p><span style="vertical-align: baseline;">当社の自動派遣エンジンは、Google Maps Platform のルートと到着予定時刻の計算機能を使用して、近くにいる適切な対応者（高度な救命処置の訓練を受けた救急隊員など）を追跡します。距離と運転時間を自動的に計算して、現場に最も近い対応者をマッチングします。緊急時には、この迅速なマッチングが不可欠です。これにより、物理的な派遣が迅速化されるとともに、正確な到着予定時刻がわかるため、救助を要請している人に即座に安心感を与えることができます。</span></p>
<p><span style="vertical-align: baseline;">当社はまた、</span><a href="https://developers.google.com/maps/documentation/places/web-service?hl=en" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Places API</span></a><span style="vertical-align: baseline;"> と</span><a href="https://developers.google.com/maps/documentation/places/web-service/place-autocomplete?hl=en" rel="noopener" target="_blank"><span style="vertical-align: baseline;"> </span><span style="text-decoration: underline; vertical-align: baseline;">Autocomplete</span></a><span style="vertical-align: baseline;"> を使用して、利用者がサービスに登録する際に任意の建物や場所を登録できるようにしています。これにより、以前の地図プロバイダよりも高い精度で住所をシステムに取り込めるようになりました。24 時間 365 日稼働する管制室では、オペレーターが静的地図と動的地図を使用して、派遣状況をリアルタイムで監視しています。担当者は、航空写真ビューで建物のレイアウトや敷地の入り口を確認し、リバース ジオコーダーを使用して緯度と経度の座標を人が読める形式の住所に変換することで、対応者を現場に直接誘導できます。</span></p>
<p><span style="vertical-align: baseline;">銀行、保険会社、配車サービス会社などのビジネス クライアントに完全な運用の透明性を提供するために、派遣データは</span><a href="https://cloud.google.com/bigquery"><span style="vertical-align: baseline;"> </span><span style="text-decoration: underline; vertical-align: baseline;">BigQuery</span></a><span style="vertical-align: baseline;"> に転送し、パフォーマンス指標を</span><a href="https://cloud.google.com/looker-studio"><span style="text-decoration: underline; vertical-align: baseline;">データポータル</span></a><span style="vertical-align: baseline;">で可視化しています。クライアントは、平均対応時間とインシデントの傾向をリアルタイムで確認し、パフォーマンスを把握できます。</span></p>
<p><span style="vertical-align: baseline;">一方で、当社のエンジニアは、Google Maps Platform の事前構築済みソフトウェア キットに切り替えたことで、さまざまなモバイル オペレーティング システム用のカスタム ネイティブ コードを維持する必要がなくなりました。これにより、技術的なメンテナンスが簡素化され、開発者は新しい安全機能の構築に集中できるようになりました。</span></p>
<h3><span style="vertical-align: baseline;">Google Maps Platform で派遣コストを 50% 以上削減し、グローバルな保護を拡大</span></h3>
<p><span style="vertical-align: baseline;">Google Maps Platform を利用したことで、運用面と財務面ですぐにメリットが得られました。地域ごとの複数のサービスを単一のプロバイダに置き換えたことで、派遣 1 回あたりのコストを 0.26 ドルから 0.11 ドルへ、50% 以上削減できました。これにより、年間約 56,000 ドルのコスト削減が見込まれ、パートナーやエンドユーザーが緊急対応を低コストで利用できるようになります。</span></p>
<p><span style="vertical-align: baseline;">現在、Google Maps Platform を利用して、45 秒ごとに緊急信号を処理しています。120 万件を超える過去のインシデントにおいて、1 か月あたりの派遣件数は約 45,000 件で、前月比で 13% の増加を見せています。このグローバル インフラストラクチャにより、世界中の 26 のパートナー ネットワークにわたり、シームレスな拡大が可能となっています。</span></p>
<p><span style="vertical-align: baseline;">ヨーロッパ、英国、米国への拡大を続けるなか、今後は </span><a href="https://developers.google.com/maps/documentation/isochrones/overview?hl=en" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Isochrones API</span></a><span style="vertical-align: baseline;"> を実装して、リアルタイム交通情報に基づいて、対応者がいつでも到達できるエリアをマッピングする予定です。これにより、サービスレベル契約を追跡し、対応者のカバレッジを増やす必要があるエリアを特定できるようになります。当社は今後も、Localyse をこの取り組みを通じた重要な位置情報インテリジェンスのパートナーとして、グローバル展開を進めるとともに、Destination API などの新機能を使って対応者を建物の入り口まで誘導する方法を探っていきます。</span></p>
<p><span style="vertical-align: baseline;">当社は、スマート テクノロジーと信頼性の高いナビゲーション データを組み合わせることで、より安全で透明性の高い緊急対応ネットワークを構築しています。利用者がパニックボタンを押すとき、救助が必ず来ると確信できなければなりません。Google Maps Platform を使用することで、世界中の人々との間でその約束を果たすための精度と規模を確保できるのです。</span></p>

<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">※この投稿は米国時間 2026 年 10 月 9 日に、Google Maps Platform blog に</span><a href="https://mapsplatform.google.com/resources/blog/ubcab-reducing-average-passenger-pickup-times-by-25-percent-with-google-maps-platform/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">投稿</span></a><span style="vertical-align: baseline;">されたものの抄訳です。</span></p>
<p><span style="font-style: italic; vertical-align: baseline;">編集者注: 今回のブログ記事は、UBCab の CTO で共同創業者でもある Erdem Batsaikhan 氏によるものです。モンゴルの大手テクノロジー企業である UBCab が、Google Maps Platform を使用して、交通状況を考慮したリアルタイムのルート設定、配車効率の向上、乗客の待ち時間の大幅な短縮を実現した方法をご紹介いただきました。</span></p>
<hr />
<h3><strong style="vertical-align: baseline;">交通状況を考慮したルート案内で極寒の冬の課題を克服</strong></h3>
<p><span style="vertical-align: baseline;">モンゴルのウランバートルは、世界で最も寒い首都です。冬には気温がマイナス 40 度に達することもよくあります。このような極寒の中で配車を依頼する場合、外に立って待つ余裕などありません。お客様が求めているのは、車が時間どおりに到着することです。これが、モンゴルの成人人口の 80% 以上が</span><a href="https://www.ubcab.mn/en" rel="noopener" target="_blank"><span style="vertical-align: baseline;"> </span><span style="text-decoration: underline; vertical-align: baseline;">UBCab</span></a><span style="vertical-align: baseline;"> を利用している理由です。</span><a href="https://mapsplatform.google.com/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Google Maps Platform</span></a><span style="vertical-align: baseline;"> のおかげで、180 万人のお客様を寒い中お待たせすることなく迎えに行くことができています。</span></p>
<p><span style="vertical-align: baseline;">Google Maps Platform</span><a href="https://developers.google.com/maps/documentation/mobility?hl=en" rel="noopener" target="_blank"><span style="vertical-align: baseline;"> </span><span style="text-decoration: underline; vertical-align: baseline;">モビリティ サービス</span></a><span style="vertical-align: baseline;">を導入する前は、直線距離の計算に基づいて近くのドライバーを見つける自動ドライバー マッチング システムでしたが、技術的な限界がありました。この計算では実際の道路網や交通渋滞が考慮されなかったため、地図上では近くにいても、実際には車で遠回りしなければならないドライバーが割り当てられることがありました。その結果、お客様の待ち時間が長くなったり、ドライバーが配車依頼を拒否したり、予定到着時刻（ETA）が大きく変動したりして、お客様からの苦情に発展することもありました。また、ドライバーが交通状況を確認してルートを計画するために、UBCab アプリと外部のナビゲーション アプリを切り替えなくてはなりませんでした。</span></p>
<p><span style="vertical-align: baseline;">こうしたルート設定の課題を解決し、お客様に正確な ETA を提供するため、当社は Google Maps Platform のモビリティ サービスを採用しました。これにより、実際の運転時間に基づいてお客様の最も近くにいるドライバーをマッチングして、お客様には確実な到着時間を、ドライバーには大幅に改善されたルートを提供できるようになりました。</span></p></div>

<div class="block-paragraph_advanced"><h3><strong style="vertical-align: baseline;">Google Maps Platform のモビリティ サービスでドライバーと乗客のエクスペリエンスを向上</strong></h3>
<p><span style="vertical-align: baseline;">Google Cloud パートナーの</span><a href="https://www.hkmci.com/" rel="noopener" target="_blank"><span style="vertical-align: baseline;"> </span><span style="text-decoration: underline; vertical-align: baseline;">Master Concept</span></a><span style="vertical-align: baseline;"> と協力することで、UBCab の中核となる配車エンジンにモビリティ サービスを直接組み込むことができました。</span><a href="https://developers.google.com/maps/documentation/routes?hl=en" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Routes API</span></a><span style="vertical-align: baseline;"> の Compute Routes を使用して、直線距離によるマッチングからリアルタイムの交通状況を考慮したルート選択に移行し、到着時間を予測できるようにしました。この API は、リアルタイムの交通データと道路網を考慮して、配車リクエストを割り当てる前に実際の運転時間を計算します。これにより、ドライバーには迅速に迎えに行ける配車リクエストを割り当て、お客様にはリアルタイムの道路状況に基づいた正確な ETA と適正な運賃見積もりを提示することができます。</span></p></div>

### データ主権の境界内におけるマネージド RAG 検索: Gemini on GDC エンタープライズ検索

<div class="block-paragraph"><p>※この投稿は米国時間 2026 年 10 月 21 日に、Google Cloud blog に<a href="https://cloud.google.com/blog/topics/hybrid-cloud/managed-rag-search-inside-the-sovereign-perimeter-gemini-on-gdc-enterprise-search?e=48754805&amp;hl=en">投稿</a>されたものの抄訳です。</p><p>国家安全保障機関をはじめ、データ主権の保護を求められる厳しい規制下の組織では、機密報告書、現場のマニュアル、取り扱いに注意を要するマルチモーダル データセットなど、非常に機密性の高いデータを扱っています。パブリック クラウドで利用可能な検索とマルチモーダル インテリジェンスは、チームがそのデータを管理および分析するのに役立ちますが、厳格なデータ主権の規制により、データをお客様の施設内から持ち出すことはできません。</p><p>代替手段として、安全で切断された境界内にカスタム エージェント検索をデプロイする方法がありましたが、これまでは、モデルの統合、音声文字変換と光学式文字認識（OCR）パイプラインの構築、ベクトル データベースの構成、独自のユーザー インターフェースの管理など、カスタム インフラストラクチャの構築と維持に数か月を要していました。</p><p>このたび、上述の課題を解決するために、NVIDIA Blackwell Ultra で高速化された<a href="https://cloud.google.com/distributed-cloud"> Google Distributed Cloud（GDC）</a>エアギャップ上の Gemini によるエンタープライズ検索機能が利用可能になったことをお知らせいたします。プレビュー版では、このフルマネージドの検索拡張生成（RAG）検索エクスペリエンスは、物理的なセキュリティ境界内で完全に実行され、公共のインターネットや Google Cloud のグローバル インフラストラクチャには接続されません。チームは、会話にファイルをアップロードして、Gemini にそのファイルに関する情報の検索、要約、比較、翻訳を依頼できるようになりました。すべての回答には出典が明記され、会話はセッション間で保持されます。</p><p>GDC のエンタープライズ検索機能により、チームはサイロ化されたデータを検索して、強力な分析情報を引き出すことができます。これらの機能によって、次のことができるようになりました。</p><ul><li><b>数百ページから引用された回答を取得:</b> 長いマニュアル、レポート、ポリシーを対象に質問し、各回答がどのファイルから取得されたかを正確に確認できます。</li><li><b>言語の壁を越えて作業:</b> ある言語で質問すると、別の言語で書かれたドキュメントに基づいて回答を得られます。Gemini に翻訳してもらうこともできます。</li><li><b>多様なフォーマットをまとめて質問:</b> 音声録音、動画クリップ、画像、スプレッドシートを組み合わせることができ、個別の文字起こしや OCR の手順は不要です。</li><li><b>中断したところから再開:</b> 会話とファイルはセッション間で保持されるため、長時間の作業でも最初からやり直す必要はありません。</li><li><b>アクセス権限を必要最小限に制限:</b> 各ユーザーのチャットとファイルはそのユーザーのみに限定され、アクセス権はすでに管理している ID プロバイダ グループに従います。</li></ul><p>ユーザーは、PDF、Microsoft Word、PowerPoint、Excel ファイルのほか、TXT、HTML、PNG、JPEG 画像、WAV 音声、MP4 動画を操作できます。各ファイルの最大サイズは 100 MB、各チャットの最大サイズは 500 MB です。</p><p><b>コア アーキテクチャ レイヤ: 仕組み</b></p><p>ユーザーのクエリが、ログイン、ファイルの取り込み、Gemini による回答の生成、セッションの保存というスタックの各レイヤを通過する流れを見ていきましょう。どのステップも、組織のエアギャップ環境のネットワーク上で行われます。</p></div>

<div class="block-paragraph"><p>※この投稿は米国時間 2026 年 10 月 22 日に、Google Cloud blog に<a href="https://cloud.google.com/blog/products/data-analytics/analyze-unstructured-data-in-bigquery-with-objectref?e=48754805&amp;hl=en">投稿</a>されたものの抄訳です。</p><p>データ サイエンス、データ エンジニアリング、ML を担当する各チームにとって、画像、動画、音声、ドキュメントなどの非構造化データの価値を引き出すということは、これまで、サイロ化されたデータ パイプラインを管理することを意味していました。構造化データと非構造化データを別々に、さらには、分析と AI / ML のユースケースを別々に扱う必要があると考えられてきました。たとえファイルが Cloud Storage 内にあっても、推論を実行するには外部の ML ワークロードをオーケストレートする必要があり、その後、構造化された推論出力を再度データ ウェアハウスに結合させるという、複雑で脆弱な課題に取り組まなければなりません。この事後的なデータ結合は、運用上のオーバーヘッドを増大させるばかりか、データベースの整合性も危うくします。</p><p>この問題を解決するために、このたび、BigQuery の <b>ObjectRef</b> とマルチモーダル データ分析が<b>一般提供（GA）</b>となり、BigQuery が包括的なマルチモーダル エージェント データ プラットフォームとして確立されました。</p><p>ObjectRef を使用すると、Cloud Storage と分析エンジンのギャップを BigQuery でネイティブに埋めることができます。非構造化データを ObjectRef 列としてネイティブに取り込み、従来のリレーショナル データベースの構造化データ列と並列で扱うことが可能になったのです。会話分析において、単一の SQL クエリまたは自然言語クエリで<b>マルチモーダル、複数列の入力</b>を Gemini モデルに直接受け渡せるので、スタンドアロン モデル API と比較しても大きなメリットが得られます。BigQuery AI、BigQuery の会話型分析、そして Gemini Enterprise で ObjectRef を使用できるようになったことで、Cloud Storage のファイルを、構造化データベースの豊富なコンテキストや、メタデータ、タイムスタンプ、カスタム エージェントへの指示などと簡単に組み合わせることができます。</p><p>これにより、完全なサーバーレス コンピューティング、低い総所有コスト、大規模な処理が可能な組み込みの推論といった、BigQuery ならではの強みを活用しながら、非構造化から構造化、非構造化から非構造化、そしてマルチモーダルからマルチモーダルへの高度なパイプラインをフルに構築、実行、管理できるようになりました。しかも、これらに個別のコンピューティング クラスタは必要ありません。重要なのは、ObjectRef を非構造化オブジェクトと同じ行に保存することで、抽出された特徴とアノテーションを非構造化オブジェクト自体と直接組み合わせることができる点です。この結合されたデータを会話分析と AI エージェントで直接使用することで、非構造化ファイルを純粋な構造化形式に変換する際に発生しがちな、データやコンテキストのニュアンスの喪失を回避できます。多くのお客様はすでにこのアプローチを使用して、<b>マルチモーダル ベクトル検索用のエンベディングを生成</b>し、<b>生成 AI を使用して大規模な分類</b>を実行し、膨大なドキュメントやメディアのアーカイブから正確な<b>データと特徴を抽出</b>しています。これらは、以下のように、すべて標準 SQL で実行できます。</p></div>

<div class="block-paragraph"><p>これらのポインタを従来の構造化データの列とともに標準の BigQuery テーブルにネイティブに保存することで、BigQuery は非構造化ファイルを第一級オブジェクトのデータとして扱います。さらに、このアーキテクチャは独立したデータ ライフサイクルをサポートします。これは、GCS データと BigQuery テーブルが、他のシステムの基盤となるデータに影響を与えることなく、独立して変更できることを意味します。</p><p>このアプローチは、複数のデータペルソナに対し、大きなメリットをもたらします。</p><ul><li><b>ゼロコピー アーキテクチャ:</b> 大量のメディア ファイルを Cloud Storage に安全に保管し、BigQuery で即座にクエリを実行できます。データ グラビティを尊重し、コストのかかるデータ重複を回避できます。</li><li><b>SQL と Python の相互運用性:</b> 標準 SQL または BigQuery DataFrames を使用して非構造化データをクエリできます。重要なのは、ObjectRef を BigQuery Python UDF に受け渡すことができる点です。これにより、OpenCV などのオープンソース Python ライブラリをデータに直接適用し、データを移動することなくカスタム ロジックを実行できます。</li><li><b>独立したライフサイクルとバージョニング:</b> ObjectRef は、特定の GCS 世代番号を追跡することで、推論の再現性を確保します。基盤となる GCS ファイルが変更された場合でも、クエリは、行が書き込まれたときに存在していたファイルの正確なバージョンを参照できます。</li><li><b>ガバナンスの統一:</b> BigQuery の既存のセキュリティ ポリシーと IAM 制御を使用して、構造化された列とそれに関連する非構造化ファイルの両方へのアクセスを保護、監査、共有できます。</li></ul><p><b>SQL で完全な忠実度の ETL を構築</b></p><p>ObjectRef のプレビュー版をリリースして以来、ユーザーの間で、<b>SQL のみで完全な忠実度の ETL パイプラインを構築する</b>、盤石で非常に効果的なパターンが醸成されています。</p></div>

<div class="block-paragraph"><p>データや ML の担当チームは BigQuery のサーバーレス アーキテクチャを活用して、AI / ML をデータ環境に直接統合できます。データの移動や推論の処理のために個別のコンピューティング クラスタを用意する必要はありません。GCS 内の非構造化データを標準の BigQuery を同じ行に固定したまま、特徴を抽出して非構造化データにアノテーションを付けることで、<b>2 層式の分析</b>が可能になります。つまり、構造化された出力が高速フィルタリング、レポート、BI ダッシュボードを可能にし、アタッチされた非構造化オブジェクトは、コンテキストを重視した詳細な推論に利用できます。たとえば、顧客との通話録音のアーカイブから感情スコアとトピックタグを抽出し、BI ダッシュボード（構造化レイヤ）でリスクのある顧客アカウントにすばやくフラグを立てることも可能です。同時に、エスカレーション プロセスを評価する会話分析エージェントは、元の音声ファイルにシームレスにフォールバックして、発信者とカスタマー サービス担当者のやり取りを分析できます。これにより、非構造化から構造化への ETL パイプラインで発生しがちな、重要なニュアンスの喪失を防ぐことができます。</p><p><b>業界リーダーの声（実証済みユースケース）</b></p><p>「Snap では、コミュニティの安全を最優先に考えており、コミュニティ ガイドラインに違反するコンテンツをユーザーから遮断できるよう取り組んでいます。そこで、公開投稿のサンプルを定期的に審査しているのですが、ObjectRef と BigQuery AI の活用により、単純なランダム サンプリングから事後層別サンプリングへの移行を実現しました。この移行により、人間による審査プロセスの効率が向上し、時間と労力が節約できて新しいワークフローや既存ワークフローの拡充に再投資できるようになったため、有害リスクのコンテンツを検出して対処する能力がさらに向上しました。」 - <b>Snap、データ サイエンティストCarlos
