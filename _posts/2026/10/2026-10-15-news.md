<summary>詳細を表示</summary>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">The </span><a href="https://docs.cloud.google.com/bigquery/docs/generative-ai-overview"><span style="text-decoration: underline; vertical-align: baseline;">generative AI functions in BigQuery</span></a><span style="vertical-align: baseline;"> (</span><code style="vertical-align: baseline;">AI.GENERATE</code><span style="vertical-align: baseline;">, </span><code style="vertical-align: baseline;">AI.IF</code><span style="vertical-align: baseline;">, </span><code style="vertical-align: baseline;">AI.CLASSIFY</code><span style="vertical-align: baseline;">, </span><code style="vertical-align: baseline;">AI.SCORE</code><span style="vertical-align: baseline;">, and more) bring large language models (LLMs) directly into your SQL, so a single query can classify millions of support tickets or score each product review for sentiment. However, because these functions are billed by the token, scaling them across massive datasets highlights the importance of managing your budget proactively. </span></p>
<p><span style="vertical-align: baseline;">We recently announced the general availability (GA) of </span><strong style="vertical-align: baseline;">token-based </strong><a href="https://docs.cloud.google.com/bigquery/docs/control-genai-costs"><strong style="text-decoration: underline; vertical-align: baseline;">cost management</strong></a><strong style="vertical-align: baseline;"> for BigQuery generative AI functions</strong><span style="vertical-align: baseline;">: daily quotas that let administrators set self-serve guardrails on AI token consumption, so teams can innovate while staying within your budget. In this blog, we provide an overview of cost management for BigQuery generative AI functions, walk through a few practical examples, and share resources to help you get started. Let’s jump in.  </span></p>
<h3><span style="vertical-align: baseline;">Quotas for managing costs</span></h3>
<p><span style="vertical-align: baseline;">Four daily quotas, managed through the Google Cloud Identity and Access Management (IAM) quota system, provide controls at the </span><strong style="vertical-align: baseline;">project</strong><span style="vertical-align: baseline;"> level and the </span><strong style="vertical-align: baseline;">per-user</strong><span style="vertical-align: baseline;"> level. Per-user limits apply to each user within a project, not across your organization.<br /><br /></span></p>

<h3><span style="vertical-align: baseline;">Token quotas vs. billing spend caps</span></h3>
<p><span style="vertical-align: baseline;">Token quotas aren't the only cost guardrail in Google Cloud.</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><a href="https://docs.cloud.google.com/bigquery/docs/control-genai-costs"><strong style="text-decoration: underline; vertical-align: baseline;">Token quotas (this feature)</strong></a><span style="vertical-align: baseline;"> are </span><span style="font-style: italic; vertical-align: baseline;">preventive</span><span style="vertical-align: baseline;"> and </span><span style="font-style: italic; vertical-align: baseline;">AI-specific</span><span style="vertical-align: baseline;">. BigQuery tracks token usage during query execution and stops work close to the limit, with separate limits per project and per user.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Cloud Billing </strong><a href="https://docs.cloud.google.com/billing/docs/how-to/budgets-spend-caps#eligible-services"><strong style="text-decoration: underline; vertical-align: baseline;">spend caps</strong></a><span style="vertical-align: baseline;"> operate on </span><span style="font-style: italic; vertical-align: baseline;">dollars</span><span style="vertical-align: baseline;"> at the project and service level and can automatically block usage when a threshold is reached. They're a broad, financial backstop rather than a precise usage control, and because enforcement is not instant, some overages are incurred.</span></p>
</li>
</ul>
<p><span style="vertical-align: baseline;">Use token quotas as your first line of defense for AI spend, and a spend cap as a project-wide safety net.</span></p>
<h3><span style="vertical-align: baseline;">How enforcement works</span></h3>
<p><span style="vertical-align: baseline;">Quotas are enforced by stopping work rather than letting a query run past your limit. A query is rejected up front with a </span><code style="vertical-align: baseline;">QuotaExceeded</code><span style="vertical-align: baseline;"> error only if a quota it needs is already exhausted. Otherwise, it starts, and if a quota runs out mid-query, BigQuery stops sending new LLM calls:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Functions that support </strong><code><strong style="vertical-align: baseline;">max_error_ratio</strong></code><span style="vertical-align: baseline;"> (such as </span><code style="vertical-align: baseline;">AI.IF</code><span style="vertical-align: baseline;">) return partial results if unprocessed rows stay within the ratio, and otherwise fail.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">General-purpose functions</strong><span style="vertical-align: baseline;"> (such as </span><code style="vertical-align: baseline;">AI.GENERATE</code><span style="vertical-align: baseline;">) still succeed. Skipped rows have no generated value, and their </span><code style="vertical-align: baseline;">status</code><span style="vertical-align: baseline;"> field contains the quota-exceeded error.</span></p>
</li>
</ul>
<p><span style="vertical-align: baseline;">For details, see </span><a href="https://docs.cloud.google.com/bigquery/docs/control-genai-costs#quota_enforcement_behavior"><span style="text-decoration: underline; vertical-align: baseline;">quota enforcement behavior</span></a><span style="vertical-align: baseline;"> in the documentation.</span></p>
<h3><span style="vertical-align: baseline;">Sizing your input data: </span><code style="vertical-align: baseline;">AI.COUNT_TOKENS</code></h3>
<p><span style="vertical-align: baseline;">To choose quota values, it helps to know how much text your workloads send to a model. The </span><a href="https://docs.cloud.google.com/bigquery/docs/reference/standard-sql/bigqueryml-syntax-ai-count-tokens"><code style="text-decoration: underline; vertical-align: baseline;">AI.COUNT_TOKENS</code></a><span style="vertical-align: baseline;"> function helps with this.</span></p>
<p><code style="vertical-align: baseline;">AI.COUNT_TOKENS</code><span style="vertical-align: baseline;"> returns the number of tokens a model's tokenizer produces for a text string, without making a billable generation call. Run it over a column to measure your input data:</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &quot;-- Count the input text tokens for each product review\r\nSELECT\r\n  SUM(\r\n    AI.COUNT_TOKENS(\r\n      CONCAT(&#x27;Classify the sentiment of this review as positive, negative, or neutral: &#x27;, review_text),\r\n\r\n      endpoint =&gt; &#x27;gemini-3.1-flash-lite&#x27;).result) AS total_input_tokens\r\nFROM\r\n  `my_project.my_dataset.product_reviews`;&quot;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f5eb4e965d0&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">The count is a lower bound on input tokens. It doesn't include output or thinking tokens, the instructions each AI function adds around your input, or non-text inputs such as images. Use it to:</span></p>
<ul>
<li style="vertical-align: baseline;">

      <p>Post-quantum cryptography (PQC) is one of the most urgent security shifts of the decade — and one of the easiest to tune out. For security leaders and policymakers, the research is dense, scattered across papers and engineering blogs, and can be challenging to turn into action.</p><p>To help, we're launching <a href="https://notebook.google.com/notebook/68849586-67c5-4165-8f72-64a61991f1dd">Prepare for Post-Quantum Cryptography</a>, a public Gemini Notebook that brings Google's PQC research, engineering blogs, and migration guidance together in one place. Ask it questions, listen to an audio overview, or test yourself with flashcards, and quickly get up to speed on the quantum threat.</p><p><b>Why PQC matters now</b></p><p>Quantum computing is rapidly moving from theory to reality. Our <a href="https://blog.google/technology/research/google-willow-quantum-chip/">Willow chip</a> and <a href="https://blog.google/innovation-and-ai/technology/research/quantum-echoes-willow-verifiable-quantum-advantage/">Quantum Echoes algorithm</a> mark substantial progress, and Google research estimates that breaking <a href="https://arxiv.org/abs/2603.28846">ECDLP-256</a> and <a href="https://arxiv.org/abs/2505.15917">RSA-2048</a> encryption — the public-key cryptography schemes protecting much of our online data — would require around 500,000 and 1 million imperfect quantum computer components (noisy qubits), respectively.</p>

<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">This research has consequences now. It indicates that today’s online security is more vulnerable to future quantum computers than previously thought.</span></p>
<p><span style="vertical-align: baseline;">In </span><a href="https://www.ietf.org/archive/id/draft-reddy-uta-pqc-app-03.html#name-timeline-for-transition" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">Store Now, Decrypt Later</span></a><span style="vertical-align: baseline;"> attacks, adversaries may steal encrypted data now and wait to decrypt it once a sufficiently powerful quantum computer exists. Data that we’ve long considered sensitive — health records, financial data, intellectual property, and government secrets — is already at risk</span><span style="vertical-align: baseline;">.</span><span style="vertical-align: baseline;"> </span></p>
<p><span style="vertical-align: baseline;">With continued advances in architecture, quantum algorithms, and quantum error correction shrinking future quantum hardware requirements, waiting to upgrade our digital locks is not a viable option. To help organizations stay ahead of the curve, Google has published a </span><a href="https://blog.google/innovation-and-ai/technology/safety-security/cryptography-migration-timeline/" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">migration timeline</span></a><span style="vertical-align: baseline;"> noting our plans to transition to PQC by 2029, and we urge others to consider the same.</span></p>
<p><span style="vertical-align: baseline;">As the technology advances, policymakers should consider urging critical infrastructure owners and operators to recognize condensed timelines, and build PQC readiness into existing risk mitigation plans. We also recommend governments engage with global counterparts to promote a harmonized approach to standards development, and include technical and security experts in the building of policy and regulatory requirements focused on quantum safety. </span></p>

<p><strong style="vertical-align: baseline;">What's at stake</strong></p>
<p><span style="vertical-align: baseline;">Previous cryptographic migrations, such as moving from SHA-1 or upgrading TLS, have taken a decade or more. Waiting for the availability of a cryptographically-relevant quantum computer before beginning the migration journey represents a significant security risk given the importance of</span><span style="vertical-align: baseline;"> public-key cryptography for securing digital essentials like web traffic, software updates, digital identities, and signatures.</span></p>

<hr />
<h3><span style="vertical-align: baseline;">Introduction</span><strong style="vertical-align: baseline;"> </strong></h3>
<p><span style="vertical-align: baseline;">On October 15, BeyondTrust disclosed a vulnerability, CVE-2026-102764, impacting BeyondTrust Remote Support (formerly Bomgar) appliances. BeyondTrust Remote Support is an enterprise secure remote access solution that enables IT teams to securely access and troubleshoot remote endpoints. The successful exploitation of this vulnerability results in the arbitrary upload of files. </span></p>
<p><span style="vertical-align: baseline;">During an incident response engagement, Mandiant identified evidence that ARMORY CASTLE, a suspected PRC-nexus espionage threat actor (formerly tracked as </span><a href="https://cloud.google.com/blog/topics/threat-intelligence/brickstorm-espionage-campaign?e=48754805"><span style="text-decoration: underline; vertical-align: baseline;">UNC5221</span></a><span style="vertical-align: baseline;">), exploited this vulnerability as a zero-day, in late August 2026. This blog describes how ARMORY CASTLE escalated privileges and established persistent access to compromised BeyondTrust Remote Support appliances following exploitation of CVE-2026-102764, and provides actionable guidance for defenders.</span></p>
<p><span style="vertical-align: baseline;">Organizations should prepare for potential widespread exploitation following this disclosure, as ARMORY CASTLE and other threat actors have historically conducted broad, opportunistic exploitation once the vulnerability becomes public. </span></p>
<h3><span style="vertical-align: baseline;">Exploitation</span></h3>
<p><span style="vertical-align: baseline;">Mandiant identified evidence of CVE-2026-102764 exploitation within the access, syslog, messages, thin-scc, brain and SSL log files, which are only accessible via an LUKS-encrypted partition which contains the </span><code style="vertical-align: baseline;">/home</code><span style="vertical-align: baseline;"> directory. We strongly recommend that affected organizations immediately apply the security </span><a href="https://www.beyondtrust.com/trust-center/security-advisories/bt26-05" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">patches</span></a><span style="vertical-align: baseline;"> provided by BeyondTrust to remediate the vulnerability, and review additional guidance in their </span><a href="https://www.beyondtrust.com/blog/entry/bt26-05" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">blog</span></a><span style="vertical-align: baseline;">.</span></p>
<h3><span style="vertical-align: baseline;">Post-Exploitation</span></h3>
<p><span style="vertical-align: baseline;">Following the successful exploitation of CVE-2026-102764, Mandiant observed ARMORY CASTLE leverage multiple distinct TTPs to establish a foothold, escalate privileges, and enable lateral movement. Throughout the intrusion, ARMORY CASTLE leveraged a deep understanding of BeyondTrust appliance internals, as evidenced by their abuse of proprietary CLI utilities, startup configuration templates and local reverse-proxy routing. The threat actor used newly identified custom malware, the SAWFLY webshell and the BARECLAW tunneler to interact with the BeyondTrust device. Additionally, the actor routinely deleted appliance logs and endpoint artifacts to maintain access and evade detection.</span></p></div>

<div class="block-paragraph_advanced"><h4><span style="vertical-align: baseline;">Staging Webshell</span></h4>
<p><span style="vertical-align: baseline;">After successful exploitation of CVE-2026-102764, ARMORY CASTLE initiated POST requests to </span><code style="vertical-align: baseline;">/app_84304470%2Ephp</code><span style="vertical-align: baseline;">. Mandiant was unable to recover the file associated with the POST requests. Approximately 11 minutes following the initial POST request, the file system recorded the creation of the SAWFLY webshell at the web root path </span><code style="vertical-align: baseline;">/%SITE_SERVICE_ACCOUNT%/ingredi/app/laravel/public/</code><span style="vertical-align: baseline;">. ARMORY CASTLE leveraged the SAWFLY webshell as one of their primary footholds within the environment over the course of the intrusion. </span></p>
<h4><span style="vertical-align: baseline;">SAWFLY Webshell</span></h4>
<p><span style="vertical-align: baseline;">SAWFLY </span><span style="vertical-align: baseline;">(</span><code style="vertical-align: baseline;">mangoapi.php</code><span style="vertical-align: baseline;">)</span><span style="vertical-align: baseline;"> is an obfuscated, lightweight PHP webshell that implements bidirectional encrypted C2 communication using a custom Base32 transport layer and a 256-bit RC4 stream cipher. The webshell inspects incoming HTTP POST requests for the obfuscated parameter </span><code style="vertical-align: baseline;">_c94mfe</code><span style="vertical-align: baseline;">. </span></p>
<p><span style="vertical-align: baseline;">If the parameter is absent, the script immediately sets HTTP status 404 Not Found (</span><code style="vertical-align: baseline;">http_response_code(404)</code><span style="vertical-align: baseline;">) and exits to evade automated web crawlers and vulnerability scanners. When the </span><code style="vertical-align: baseline;">_c94mfe</code><span style="vertical-align: baseline;"> parameter is supplied, the webshell Base32-decodes the payload, decrypts it using RC4 with a hardcoded 32-byte key and executes the resulting PHP code via </span><code style="vertical-align: baseline;">@eval()</code><span style="vertical-align: baseline;">. Any non-null return value from the evaluated code is RC4-encrypted with the same key, Base32-encoded, and echoed back to the client. </span></p>
<h4><span style="vertical-align: baseline;">Privilege Escalation via SUID Bit Permissions</span></h4>
<p><span style="vertical-align: baseline;">The SAWFLY webshell ran under the site's service account, an unprivileged local user. To escalate privileges, the threat actor copied the system shell executable (</span><code style="vertical-align: baseline;">/bin/sh</code><span style="vertical-align: baseline;">) to the file </span><code style="vertical-align: baseline;">/usr/bin/dbus-authd</code><span style="vertical-align: baseline;">.</span></p>
<p><span style="vertical-align: baseline;">The threat actor then modified the file's ownership to root and enabled Set User ID (SUID) permissions. When a binary has SUID permissions enabled, it executes with the privileges of the file's owner (root) rather than the user running the command, effectively granting the threat actor a persistent root-level backdoor on the host system.</span></p>
<p><span style="vertical-align: baseline;">After establishing a foothold through the web shell, the actor elevated from the web service account to root-level control of the appliance host. This gave them access to every credential the appliance stored or brokered and the ability to modify files that survive reboot and configuration reset.</span></p>
<h4><span style="vertical-align: baseline;">Credential Harvesting: BeyondTrust Vault Extraction</span></h4>
<p><span style="vertical-align: baseline;">Mandiant observed the threat actor attempt to harvest credentials directly from the appliance's native secrets management database. To achieve this, the actor leveraged the </span><code style="vertical-align: baseline;">/ns/sbin/bt-secrets</code><span style="vertical-align: baseline;"> binary which is a proprietary, administrative Command Line Interface (CLI) utility native to BeyondTrust appliances used to manage, store, and retrieve passwords, API keys, and endpoint credentials.</span></p>
<p><span style="vertical-align: baseline;">The threat actor systematically iterated through several CLI syntax variations to locate and dump the appliance's credential vault:</span></p></div>
<div class="block-paragraph_advanced"><pre class="language-markup"><code>/ns/sbin/bt-secrets get -p %SITE_SERVICE_ACCOUNT% vault
/ns/sbin/bt-secrets get %SITE_SERVICE_ACCOUNT% vault
/ns/sbin/bt-secrets get vault
</code></pre>

<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">First, the threat actor attempted to target the vault for a specific site service account in order to pull passwords and keys assigned exclusively to that profile.</span></p>
<p><span style="vertical-align: baseline;">Next, they issued a fallback command, targeting the global, appliance-level password safe to dump all stored administrative credentials.</span></p>
<p><span style="vertical-align: baseline;">The threat actor concluded their interaction with the bt-secrets binary by forcibly removing the records stored i</span><span style="vertical-align: baseline;">n</span><span style="vertical-align: baseline;"> </span><code style="vertical-align: baseline;">/home/bomgar/log/bt-secrets.log</code><span style="vertical-align: baseline;"> and any archived files.</span></p></div>

<div class="block-paragraph_advanced"><h4><span style="vertical-align: baseline;">Persistence</span></h4>
<p><span style="vertical-align: baseline;">For long-term persistent access, Mandiant observed the threat actor target the BeyondTrust configuration templates to grant passwordless root privileges to the site service account.</span></p>
<p><span style="vertical-align: baseline;">First, the threat actor created the </span><code style="vertical-align: baseline;">/home/bomgar/sbin/post_boot.d</code><span style="vertical-align: baseline;"> directory, which is reserved for scripts executed automatically at system startup. Within this directory, they created a shell script named </span><code style="vertical-align: baseline;">zz-root-persist</code><span style="vertical-align: baseline;">.</span></p>
<p><span style="vertical-align: baseline;">The contents of the </span><code style="vertical-align: baseline;">zz-root-persist</code><span style="vertical-align: baseline;"> script indicate that it first checks if the user account is already granted passwordless root privileges within the </span><code style="vertical-align: baseline;">/ns/config/sudoers.template</code><span style="vertical-align: baseline;"> file. If the entry is missing, the script appends</span><code style="vertical-align: baseline;"> </code><code style="vertical-align: baseline;">'%SITE_SERVICE_ACCOUNT% ALL=(ALL) NOPASSWD: ALL'</code><code style="vertical-align: baseline;"> </code><span style="vertical-align: baseline;">to the template. This entry added  to the sudoers template grants the site user account passwordless administrative privileges to execute any command on the host system.</span></p>
<p><span style="vertical-align: baseline;">Finally, the script executes</span><code style="vertical-align: baseline;"> </code><code style="vertical-align: baseline;">'/ns/sbin/bt-sysconfig' --no-restart misc</code><span style="vertical-align: baseline;">, which forces the appliance backend to immediately parse </span><code style="vertical-align: baseline;">/ns/config/sudoers.template</code><span style="vertical-align: baseline;"> and rebuild the active </span><code style="vertical-align: baseline;">/etc/sudoers</code><span style="vertical-align: baseline;"> file. This strategy ensures the threat actor's privilege escalation survives system reboots and configuration resets, which would normally overwrite manual changes made directly to </span><code style="vertical-align: baseline;">/etc/sudoers</code><span style="vertical-align: baseline;">.</span></p></div>
<div class="block-paragraph_advanced"><pre class="language-markup"><code>#!/bin/bash

'/ns/sbin/bt-sysconfig' --no-restart misc
</code></pre>

<div class="block-paragraph_advanced"><h4><span style="vertical-align: baseline;">Internal Reconnaissance</span></h4>
<p><span style="vertical-align: baseline;">Once the threat actor obtained elevated administrative privileges, Mandiant observed the threat actor establish a remote support session to target internal endpoints.</span></p>
<p><span style="vertical-align: baseline;">Once connected, the threat actor leveraged the appliance’s built-in support tools to request and obtain full file-system access. The threat actor utilized the native BeyondTrust Remote Support file transfer service to download and exfiltrate sensitive internal documents useful for network reconnaissance, such as software inventories, directly from the user's desktop environment. </span></p>
<h4><span style="vertical-align: baseline;">BARECLAW Tunneler</span></h4>
<p><span style="vertical-align: baseline;">Mandiant observed the threat actor tunnel traffic through the BeyondTrust device via a custom SOCKS5 proxy tunneler. BARECLAW is a tunneler written in C that provides a SOCKS5 proxy service carried over the WebSocket transport and relays TCP connections between a remote client and destinations. BARECLAW statically embeds a CivetWeb WebServer to supply its HTTP and WebSocket functionality and utilizes OpenSSL for TLS. BARECLAW is configurable and provides the option to require authentication, to encrypt data between the client and tunneler, to restrict reachable destinations to specific CIDR ranges, to chain traffic to an upstream proxy, and to modify its default WebSocket endpoint and listening ports. TLS is enabled by providing a PEM certificate while authentication, encryption, destination filtering, and TLS are disabled by default. </span></p>
<p><span style="vertical-align: baseline;">BARECLAW receives its configuration through CLI input and it provides a CLI option menu:</span></p></div>
<div class="block-paragraph_advanced"><pre class="language-markup"><code>Usage: %s [options]
  --listen PORT            plain ws port (default 8080)
  --listen-tls PORT        wss port (default 8443, needs --ssl-cert)
  --ssl-cert FILE          PEM certificate (enables wss)
  --token STRING           shared secret (?token= auth + obfs seed)
  --obfs                   enable XOR stream obfuscation
  --timeout SEC            idle timeout (default 300)
  --connect-timeout SEC    target connect timeout (default 10)
  --max-tunnels N          concurrent tunnel limit (default 100)
  --allow-net CIDR         allowed target subnet (repeatable)
  --upstream [socks5://]host:port   route via upstream SOCKS5
  --threads N              civetweb worker threads (default 64)
  --ws-path PATH           websocket endpoint path (default /wsproxy)
  -q, --quiet              zero output (all logging suppressed)
  -h                       this help
</code></pre>
<p style="text-align: center;"><span style="color: #5f6368; display: block; font-size: 16px; font-style: italic; margin-top: 8px; width: 100%;"><span style="vertical-align: baseline;">Figure 8: BARECLAW CLI Option Menu</span></span></p>
<p><span style="color: #5f6368; display: block; font-size: 16px; margin-top: 8px; width: 100%;"><span style="vertical-align: baseline;"><span style="vertical-align: baseline;">The threat actor executed BARECLAW through the following command line arguments:</span></span></span></p></div>
<div class="block-paragraph_advanced"><pre class="language-markup"><code>/tmp/ingredi_ws --listen 19800 --token %REDACTED% --obfs -q --ws-path /uidchanarge
</code></pre>
<p style="text-align: center;"><span style="color: #5f6368; display: block; font-size: 16px; font-style: italic; margin-top: 8px; width: 100%;"><span style="vertical-align: baseline;">Figure 9: BARECLAW full Command-Line Arguments</span></span></p></div>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">This command line configures BARECLAW to listen on TCP port 19800 and create the WebSocket endpoint </span><code style="vertical-align: baseline;">/uidchanarge</code><span style="vertical-align: baseline;"> on the victim system. Clients are required to authenticate using the token specified in the command line arguments while the -q argument suppresses the tunneler’s logging. Tunneled data is encrypted with an XOR-based routine derived from that token and an 8-byte value provided by the client at the start of the session. The lack of the --ssl-cert and --listen-tls arguments in the CLI options means TLS was not enabled in this specific instance.</span></p>
<h4><span style="font-style: italic; vertical-align: baseline;">Modifications to Haproxy.conf</span></h4>
<p><span style="vertical-align: baseline;">In addition to the creation of the BARECLAW tunneler, Mandiant observed the threat actor modify the </span><code style="vertical-align: baseline;">/ns/config/haproxy.conf</code><span style="vertical-align: baseline;"> file in order for BARECLAW to be accessible directly from the internet. The HAProxy service running on BeyondTrust devices acts a reverse proxy for the device that accepts incoming requests on behalf of the BeyondTrust server and forwards the request to the appropriate backend services running on the local system (such as web interfaces, administration portals, or application gateways) based on the request's port or URL path. </span></p>
<p><span style="vertical-align: baseline;">The <code style="vertical-align: baseline;">haproxy.conf</code> </span><span style="vertical-align: baseline;">file is the primary configuration script that dictates how the BeyondTrust appliance handles, routes, and secures incoming traffic. The threat actor modifications first established an Access Control List (ACL) named </span><code style="vertical-align: baseline;">wswsws</code><span style="vertical-align: baseline;"> to monitor incoming traffic for the specific URI path </span><code style="vertical-align: baseline;">/uidchanarge</code><span style="vertical-align: baseline;">. When a request matching this path is detected, HAProxy bypasses normal appliance web services and routes the traffic to a custom backend <span style="vertical-align: baseline;">designated as </span><code style="vertical-align: baseline;">webskd3</code><span style="vertical-align: baseline;">.</span></span></p></div>
<div class="block-paragraph_advanced"><pre class="language-markup"><code>    acl wswsws path /uidchanarge
    use_backend webskd3 if wswsws
</code></pre>

<div class="block-paragraph_advanced"><h3><span style="vertical-align: baseline;">Attribution</span></h3>
<p><span style="vertical-align: baseline;">GTIG attributes the zero-day exploitation of CVE-2026-102764 and the subsequent deployment of SAWFLY and BARECLAW to the suspected PRC-nexus espionage actor ARMORY CASTLE (formerly tracked as UNC5221). The tooling and TTPs leveraged within this intrusion align with previously observed activity from ARMORY CASTLE.</span></p>
<p><span style="vertical-align: baseline;">GTIG has </span><a href="https://cloud.google.com/blog/topics/threat-intelligence/china-nexus-exploiting-critical-ivanti-vulnerability?e=0"><span style="text-decoration: underline; vertical-align: baseline;">previously reported</span></a><span style="vertical-align: baseline;"> ARMORY CASTLE exploiting multiple vulnerabilities in edge appliances and deploying an extensive suite of custom tooling to support their objectives, ranging from passive backdoors and webshells to trojanized components of edge devices. ARMORY CASTLE has been active as early as October 2023 and has targeted a wide range of countries and verticals during their operations. </span></p>
<h3><span style="vertical-align: baseline;">Outlook and Implications</span></h3>
<p><span style="vertical-align: baseline;">In past campaigns, ARMORY CASTLE has conducted widespread and opportunistic exploitation following the public disclosure of vulnerabilities it had exploited selectively as zero-days, racing to infiltrate target organizations before patches are deployed. It is possible that we will observe similar widespread exploitation attempts associated with CVE-2026-102764. </span></p>
<p><span style="vertical-align: baseline;">GTIG assesses with high confidence that ARMORY CASTLE will continue to leverage zero-day vulnerabilities in edge devices to gain access to environments to support their espionage objective. Defenders should also prepare for the possibility that following disclosure of CVE-2026-102764, ARMORY CASTLE may conduct widespread exploitation similar to what GTIG </span><a href="https://cloud.google.com/blog/topics/threat-intelligence/ivanti-connect-secure-vpn-zero-day"><span style="text-decoration: underline; vertical-align: baseline;">observed</span></a><span style="vertical-align: baseline;"> in 2024 following the disclosure of CVE-2023-46805 and CVE-2024-21887. </span></p>
<h3><span style="vertical-align: baseline;">Remediation and Hardening</span></h3>
<p><span style="vertical-align: baseline;">Organizations that have not yet applied the </span><a href="https://www.beyondtrust.com/trust-center/security-advisories/bt26-05" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">BT26-05 patch</span></a><span style="vertical-align: baseline;"> should immediately assess their exposure and risk, and review additional guidance from BeyondTrust in their </span><a href="https://www.beyondtrust.com/blog/entry/bt26-05" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">blog</span></a><span style="vertical-align: baseline;">. CVE-2026-102764 affects all supported Remote Support versions up to 26.2.3 and allows an unauthenticated remote attacker to perform file operations on the appliance, which can lead to host-level control and access to every credential the appliance stores or brokers. Any appliance that was reachable from the internet on a vulnerable version during the exploitation window should be treated as potentially compromised until it has been reviewed. Mandiant recommends a phased, patch-first approach that balances containment against disruption to support operations.</span></p>
<h4><span style="vertical-align: baseline;">Immediate Mitigation</span></h4>
<p><span style="vertical-align: baseline;">Organizations should choose among the following options based on their risk tolerance, evidence of compromise, and operational needs.</span></p>
<h4><span style="font-style: italic; vertical-align: baseline;">Option 1: Apply the BT26-05 Patch (Mandiant Recommended)</span></h4>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Remote Support SaaS</strong><span style="vertical-align: baseline;">: BeyondTrust applied the patch to all SaaS tenants on October 9, 2026. No customer action is required for the appliance itself. The credential and configuration steps in Option 3 still apply.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Self-hosted, version 24.3.1 or later</strong><span style="vertical-align: baseline;">: Apply the BT26-05-RS patch from the </span><code style="vertical-align: baseline;">/appliance</code><span style="vertical-align: baseline;"> interface, or confirm it was applied automatically if the appliance is subscribed to automatic updates.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Self-hosted, older than 24.3.1</strong><span style="vertical-align: baseline;">: Upgrade to a supported version, then apply the patch. Upgrading closes the vulnerability but does not remediate prior exposure.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">If the patch is not visible in </span><code style="vertical-align: baseline;">/appliance</code><span style="vertical-align: baseline;">, open a case with BeyondTrust Support referencing BT26-05.</span></p>
</li>
</ul>
<h4><span style="font-style: italic; vertical-align: baseline;">Option 2: Isolate Compromised or Suspected Appliances</span></h4>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Preserve before acting</strong><span style="vertical-align: baseline;">: Snapshot virtual appliances with memory and export the disk before any change or reboot. For B Series hardware and SaaS tenants, request forensic preservation through BeyondTrust Support. Collect syslog, reverse-proxy or WAF, and perimeter firewall logs for the full exposure window, since an attacker with host access can delete on-appliance logs. Mandiant determined that the actor removed logs throughout the incident.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Isolate at the perimeter</strong><span style="vertical-align: baseline;">: Block inbound traffic to the appliance's public address at the firewall rather than in </span><code style="vertical-align: baseline;">/appliance</code><span style="vertical-align: baseline;">, so the configuration remains intact for review.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Restrict egress</strong><span style="vertical-align: baseline;">: Deny outbound traffic except to BeyondTrust update and licensing endpoints, and log every denied connection.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Terminate access paths</strong><span style="vertical-align: baseline;">: End active support sessions and disable new sessions, Jump Clients, Jumpoints, and API accounts from </span><code style="vertical-align: baseline;">/login</code><span style="vertical-align: baseline;">. Disable rather than delete so the audit trail survives.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Rebuild rather than clean</strong><span style="vertical-align: baseline;">: Redeploy appliances with confirmed or unknown compromise status from a clean, fully patched image. Customers cannot audit the appliance host file system, and host-level persistence survives reboot and configuration reset. Restore only a configuration backup dated before the exposure window, or restore the newest backup while isolated and complete the review in Option 3, Part B, before reconnecting anything. Issue a new TLS certificate and redeploy Jump Clients, Jumpoints, and the representative console from the rebuilt appliance.</span></p>
</li>
</ul>
<p><strong style="vertical-align: baseline;">Note</strong><span style="vertical-align: baseline;">: Isolation and session termination interrupt support operations. Organizations should coordinate with help desk and vendor-support stakeholders before proceeding.</span></p>
<h4><span style="font-style: italic; vertical-align: baseline;">Option 3: Apply Targeted Compensating Controls</span></h4>
<p><span style="vertical-align: baseline;">The following controls reduce exposure and limit post-exploitation impact. They do not substitute for the patch.</span></p>
<h4><span style="vertical-align: baseline;">Part A: Network Restrictions</span></h4>
<ul>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">Restrict access to the </span><code style="vertical-align: baseline;">/login</code><span style="vertical-align: baseline;"> and </span><code style="vertical-align: baseline;">/appliance</code><span style="vertical-align: baseline;"> administrative interfaces by IP or network segment at the appliance level. Only representative console, customer portal, and Jump Client traffic should be reachable from the internet.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">Where operationally possible, place a reverse proxy or WAF with full URI logging in front of the appliance to keep a record of request paths that the appliance cannot alter.</span></p>
</li>
</ul>
<h4><span style="vertical-align: baseline;">Part B: Credential Rotation and Configuration Review</span></h4>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Revoke sessions and enrollments</strong><span style="vertical-align: baseline;">: End all active support sessions, then redeploy Jump Clients, Jumpoints, and the representative console from the patched or rebuilt appliance to invalidate existing tokens.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Rotate credentials in dependency order</strong><span style="vertical-align: baseline;">: </span><code style="vertical-align: baseline;">/appliance</code><span style="vertical-align: baseline;"> administrative credentials; /login administrators and local users; API client secrets; security provider bind accounts and SAML signing keys; Remote Support Vault and integrated Password Safe or Privileged Remote Access (PRA) credentials, rotated at the target system; integration credentials (SMTP, syslog, Information Technology Service Management (ITSM) connectors, outbound event secrets); and any credential typed into a support session during the window.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Review the </strong><strong style="vertical-align: baseline;">/login</strong><strong style="vertical-align: baseline;"> configuration against a pre-window baseline</strong><span style="vertical-align: baseline;">: user and role changes, particularly Jump Item roles raised to Administrator; group and session policies; API accounts; security providers; Jump Items and Jumpoints; and outbound event or syslog destinations. Remove anything without a change record or a named owner.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Review support session reports</strong><span style="vertical-align: baseline;"> for the window, including file transfers, to establish which endpoints were accessed and what left them. Every endpoint touched is in scope for downstream hunting.</span></p>
</li>
</ul>
<p><strong style="vertical-align: baseline;">Note</strong><span style="vertical-align: baseline;">: Rotate credentials only after the appliance has been patched or rebuilt. Rotating earlier exposes the new credentials to an attacker who still controls the appliance.</span></p></div>
<div class="block-paragraph_advanced"><h4><span style="vertical-align: baseline;">Part C: Control Plane Restrictions</span></h4>
<ul>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">Require SAML single sign-on with phishing-resistant MFA for all </span><code style="vertical-align: baseline;">/login</code><span style="vertical-align: baseline;"> users, and remove local accounts except one vaulted break-glass account with alerting on use.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">Ensure the built-in Admin account is configured with Multi-Factor Authentication (MFA) in accordance with the official </span><a href="https://docs.beyondtrust.com/rs/docs/two-factor-authentication#activate-two-factor-authentication" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">BeyondTrust Two-Factor Authentication Guidelines</span></a><span style="vertical-align: baseline;">.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">Set the default Jump Item role in every group policy to No Access, and grant roles through policy rather than per user.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">Scope API accounts to the minimum permission set, with a named automation owner for any account holding user or Jump Item management rights, and rotate API secrets on a schedule.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">Keep privileged credentials in Password Safe or an external vault with credential injection rather than in the Remote Support Vault, and store only non-interactive service account credentials on the appliance.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">Apply default-deny outbound filtering from the appliance, allowing only BeyondTrust endpoints and the organization's own syslog and directory servers.</span></p>
</li>
</ul>
<h4><span style="vertical-align: baseline;">Part D: Logging and Detection Engineering</span></h4>
<h3><span style="vertical-align: baseline;">Logging and Visibility</span></h3>
<ul>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">Forward appliance syslog to a SIEM over TLS with retention that covers a multi-month exposure window, and collect reverse-proxy or WAF and perimeter firewall logs for the appliance's address.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><span style="vertical-align: baseline;">Export </span><code style="vertical-align: baseline;">/login</code><span style="vertical-align: baseline;"> session, team activity, and user audit reports on a schedule.</span></p>
</li>
</ul>
<h3><span style="vertical-align: baseline;">Detection Engineering</span></h3>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Account and policy changes</strong><span style="vertical-align: baseline;">: </span><code style="vertical-align: baseline;">user_changed</code><span style="vertical-align: baseline;"> events that raise a Jump Item or team role; </span><code style="vertical-align: baseline;">user_added</code><span style="vertical-align: baseline;">, </span><code style="vertical-align: baseline;">api_account</code><span style="vertical-align: baseline;">, and </span><code style="vertical-align: baseline;">security_provider</code><span style="vertical-align: baseline;"> events with no change ticket; any change to outbound events or syslog destinations.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Authentication</strong><span style="vertical-align: baseline;">: </span><code style="vertical-align: baseline;">/login</code><span style="vertical-align: baseline;"> success from residential-broadband or commercial-VPN address space, and administrative logins outside business hours.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Session activity</strong><span style="vertical-align: baseline;">: file-transfer events, and sessions started by accounts whose roles changed during the window.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Request paths</strong><span style="vertical-align: baseline;">: at the reverse proxy or WAF, paths outside the known Remote Support path set, including unknown .php paths and WebSocket upgrades from outside support staff and endpoint address ranges.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Anti-forensics:</strong><span style="vertical-align: baseline;"> gaps in syslog forwarding from the appliance; an interruption bounded by a single session is a strong indicator of log tampering.</span></p>
</li>
</ul></div>

<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">執筆者: Robin Grunewald、Supriya Mazumdar、Kelli Vanderlee</span></p>
<hr />
<h4><strong style="vertical-align: baseline;">はじめに</strong></h4>
<p><span style="vertical-align: baseline;">Google Threat Intelligence Group（GTIG）は、脆弱性の開示と悪用の統計情報を調査し、脆弱性の脅威ランドスケープに対する AI の影響を評価しています。AI によって、脆弱性の発見と悪用のペースだけでなく、発見される脆弱性の種類や典型的なリスク プロファイルも目に見えて変化していることがわかりました。</span></p>
<p><span style="vertical-align: baseline;">主な調査結果: </span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">脆弱性の開示が倍増: </strong><span style="vertical-align: baseline;">1 か月あたりに開示された脆弱性の数は、2026 年 1 月には 5,045 件でしたが、2026 年 7 月には 10,477 件と倍増し、2026 年 8 月にはさらに増加して 10,740 件となりました。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">脆弱性の悪用がほぼ倍増:</strong><span style="vertical-align: baseline;"> 悪用された脆弱性の数は、2025 年には月平均 10.5 件でしたが、2026 年 1 月から 2026 年 8 月までの期間には月平均 18 件に増加しました。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">ゼロデイ脆弱性の悪用がわずかに増加:</strong><span style="vertical-align: baseline;"> ゼロデイ脆弱性の悪用は、2025 年には月平均 8 件でしたが、2026 年 1 月から 2026 年 8 月までの期間には月平均 11 件に増加しました。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">AI はより重大な脆弱性を検出: </strong><span style="vertical-align: baseline;">AI を活用して発見した脆弱性については、低リスクの脆弱性の割合が低く、中リスクの脆弱性とリモートコード実行（RCE）につながる脆弱性の割合が高くなりました。</span></p>
</li>
</ul>
<p><span style="vertical-align: baseline;">GTIG は、脆弱性の発見と悪用が短中期的に増加し続けると予測しています。脆弱性の迅速な発見と悪用によるリスクの増大に対抗するには、優先順位がないパッチの一括適用から、脅威インテリジェンスに基づくトリアージに移行し、標的型のエッジ防御とエージェントによる自動修復を組み合わせる必要があります。</span></p>
<h4><strong style="vertical-align: baseline;">範囲と手法</strong></h4>
<p><span style="vertical-align: baseline;">GTIG のこの分析では、2025 年 1 月 1 日から 2026 年 8 月 31 日までに開示された脆弱性の傾向を調査しています。このデータセットは、脆弱性とともに、悪用の影響、</span><a href="https://cloud.google.com/blog/topics/threat-intelligence/separating-signal-noise-how-mandiant-intelligence-rates-vulnerabilities-intelligence"><span style="text-decoration: underline; vertical-align: baseline;">GTIG の脆弱性リスク評価</span></a><span style="vertical-align: baseline;">、実際の悪用など、重要な運用上の側面も追跡しています。このブログ記事でリスク評価に言及する場合、</span><a href="https://nvd.nist.gov/vuln-metrics/cvss" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">CVSS の重大度</span></a><span style="vertical-align: baseline;">ではなく、GTIG の脆弱性リスク評価を使用しています。</span></p>
<p><span style="vertical-align: baseline;">ベースラインのモニタリング対象期間は 20 か月間（2025 年 1 月～2026 年 8 月）ですが、このレポートでは特に、増加速度と新たな脅威ベクトルに焦点を当てています。</span></p>
<p><span style="vertical-align: baseline;">この調査では、共通脆弱性識別子（CVE）の開示率と悪用率の両面から、サイバーセキュリティ環境全体における AI の影響を評価することを目的としています。また、AI / 大規模言語モデル（LLM）の運用スタックを標的とする脆弱性についても検証しています。</span></p>
<h4><strong style="vertical-align: baseline;">2026 年に CVE の開示が倍増</strong></h4>
<p><span style="vertical-align: baseline;">脆弱性の開示件数は、2026 年 1 月には 5,045 件でしたが、7 月には 10,477 件と倍増し、8 月には 10,740 件とピークに達しました（図 1）。</span></p>
<p><strong style="vertical-align: baseline;">脅威リスクと膨らんだ CVE 件数の区別</strong></p>
<p><span style="vertical-align: baseline;">ただし、脅威インテリジェンスのコンテキストがなければ、2026 年を通じた元の開示件数は誤解を招く可能性があります。オープンソース エコシステム全体で CVE Numbering Authority（CNA）の割り当てポリシーが自動化されているため、ベースラインの数値が膨らむ可能性があります。たとえば、説明に「Linux カーネル」のみが含まれる脆弱性により、2026 年 1 月から 2026 年 8 月までの間に約 5,000 件の CVE が生成されましたが、実際に悪用されたゼロデイは確認されていません。</span></p></div>

<div class="block-paragraph_advanced"><h4><strong style="vertical-align: baseline;">ゼロデイの悪用はほぼ横ばい</strong></h4>
<p><span style="vertical-align: baseline;">悪用されたゼロデイの数は、2025 年の月平均 8 件から 2026 年の月平均 11 件へとわずかに増加しました。1 か月あたりに特定されたゼロデイの数は、2026 年半ばまでベースライン レベル（8～12 件）付近でしたが、8 月には 22 件に急増しました（図 4）。ゼロデイの悪用は、依然として、開示されたすべての脆弱性のうち、ごく一部を占めるにすぎませんが、2026 年 1 月から 2026 年 8 月までに確認された、悪用されたすべての脆弱性の大部分（62%）を占めています。</span></p>
<p><strong style="vertical-align: baseline;">脅威アクターは N デイの悪用でより多くの成功を収めているか？</strong></p>
<p><span style="vertical-align: baseline;">脅威アクターは、新しいゼロデイを発見するよりも、LLM や AI ツールを使用して、製品バージョン、パッチ、脆弱性開示の発表、概念実証（POC）コードの違いの分析を自動化し、N デイを迅速に武器化する方が、簡単または効率的であると考えている可能性があります。</span></p>
<p><strong style="vertical-align: baseline;">CVE の悪用はよりリスクの高い脆弱性に向かう傾向</strong></p>
<p><span style="vertical-align: baseline;">ゼロデイの悪用率はわずかに増加したのみであることから、2026 年 1 月から 2026 年 8 月にかけての脆弱性悪用の増加の主な要因は、N デイの迅速な武器化に集中していると考えられます。特に、高リスクの脆弱性の悪用は、2025 年には 28 件でしたが、2026 年 1 月～8 月には 75 件と 2 倍以上に増加しました。</span></p></div>

<div class="block-paragraph_advanced"><h4><strong style="vertical-align: baseline;">ハンターとしての AI: AI を活用した脆弱性の発見</strong></h4>
<p><strong style="vertical-align: baseline;">検出手法と帰属特定の現実</strong></p>
<p><span style="vertical-align: baseline;">現在の公開データでは、2 つの構造的な要因により、AI によって発見された脆弱性が大幅に過小評価されています。</span></p>
<ol>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">標準化されたメタデータの欠如</strong><span style="vertical-align: baseline;">: 公開 CVE リポジトリには、AI への帰属を示す統一されたメタデータタグがまだないため、手動でヒューリスティックな追跡を行う必要があります。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">ファーストパーティとクラウドのサイレント パッチ適用</strong><span style="vertical-align: baseline;">: CVE の割り当ては通常、顧客によるパッチ適用の調整が必要なオンプレミス ソフトウェアやサードパーティ ソフトウェアのために予約されているため、大手のクラウド プロバイダや SaaS プロバイダは日常的に、正式な CVE ID をリクエストすることなく、AI が検出した脆弱性を本番環境で直接修正しています。また、多くの調査結果は、確立された協調的な脆弱性の開示（CVD）の期間中、公開が制限されます。</span></p>
</li>
</ol>
<p><span style="vertical-align: baseline;">しかし、多層検証プロセスを使用することで、自律型エージェントによって表面化する可能性が高い脆弱性を特定できます。</span></p>
<ol>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">検証済みのラボとベンダーの台帳</strong><span style="vertical-align: baseline;">: フロンティア AI 研究プログラムから確認済みの開示情報を直接取り込みます。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">アドバイザリとリリースの解析: </strong><span style="vertical-align: baseline;">サイバーセキュリティ インフラストラクチャ セキュリティ庁（CISA）のアドバイザリ、MITRE の記録、セキュリティに関するベンダーの公開情報をプログラムでモニタリングし、根本原因の発見や PoC の合成が自律型 AI エージェント（Hacktron AI、AISLE など）によるものであることを明示的に認めているものを特定します。</span></p>
</li>
</ol>
<p><strong style="vertical-align: baseline;">リスク プロファイルの違い: AI による発見と従来型の発見</strong></p>
<p><span style="vertical-align: baseline;">AI が発見した可能性が高いと特定できた、開示済みの脆弱性を分析すると、人間やスキャナによる従来型の発見とは構造的に異なることが示唆されます。AI エージェントは、低リスクの脆弱性を比較的少なく、中リスクと高リスクの脆弱性を比較的多く検出するために使用されています。</span></p>

<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">AI が発見した脆弱性と AI が発見していない脆弱性の違いは、悪用の結果という点でも明らかです。リモートコード実行（RCE）につながる脆弱性は、AI が発見した脆弱性のうち、ちょうど 50% ですが、広範な CVE エコシステム全体ではわずか 26% です。逆に、AI エージェントは影響の小さいカテゴリでは脆弱性発見率が低く、情報開示（8% 対 18%）とデータ操作（5% 対 9%）の脆弱性発見率は、AI が発見したと特定されなかった脆弱性の半分以下でした。</span></p>
<p><span style="vertical-align: baseline;">コード実行に集中しているのは、フロンティア エージェントの動作方法に起因していると考えられます。自律システムは、コア C/C++ ライブラリ、ランタイム、ハイパーバイザにわたる複雑なマルチステップのセマンティック コードパスをナビゲートするように設計されています。AI モデルは、ファジング ハーネスの合成、メモリ状態のモデル化、不明瞭なエッジケース ロジックの連鎖により、従来の静的</span><a href="https://cloud.google.com/blog/topics/threat-intelligence/staying-ahead-of-adversarial-ai-through-agentic-source-code-review"><span style="text-decoration: underline; vertical-align: baseline;">アナライザ</span></a><span style="vertical-align: baseline;">では一貫して検出できなかったメモリ破損（バッファ オーバーフロー、解放後の使用）やロジック バイパスを特定することに優れています。</span></p>
<p><span style="vertical-align: baseline;">AI が発見した脆弱性の悪用が確認されたことは、現時点では、確立された傾向というよりは初期の兆候ですが、AI が発見した欠陥によるリスクの増大が単なる理論上の話ではないことを示しています。</span></p>
<p><span style="vertical-align: baseline;">注目すべき事例は、</span><a href="https://www.hacktron.ai/blog/cve-2026-1731-beyondtrust-remote-support-rce" rel="noopener" target="_blank"><span style="text-decoration: underline; vertical-align: baseline;">CVE-2026-1731</span></a><span style="vertical-align: baseline;"> です。これは、サードパーティのリサーチ エージェント（Hacktron AI）が自律的に発見した、BeyondTrust Privileged Remote Access（PRA）および Remote Support の未認証 OS コマンド インジェクションの欠陥です。開示後、GTIG は、脅威アクターがこの脆弱性を標的型初期アクセス キャンペーンで武器化し、企業の境界をバイパスしていることを確認しました。具体的には、GTIG は、開示から 4 日以内にこの脆弱性を悪用する脅威クラスタを観察し、公開から 7 日以内にさらに 5 つの脅威クラスタを観察しました。GTIG は、これらの脅威アクターが、権限昇格、データの引き出し、二次ペイロード（SNOWLIGHT、SPARKRAT、クリプトマイナーなど）のドロップなど、悪用後にさまざまな活動を行っていることを確認しました。この運用上の衝突は、脅威アクターが積極的に悪用しようとしている影響の大きい脆弱性を、防御 AI エージェントが発見していることを浮き彫りにしています。</span></p>
<h4><strong style="vertical-align: baseline;">AI を狙う: AI / LLM 運用スタックを標的とする脆弱性</strong></h4>

<h4><strong style="vertical-align: baseline;">新たな戦場: オーケストレーションと推論</strong></h4>
<p><span style="vertical-align: baseline;">2026 年 1 月から 8 月にかけて、AI アプリケーションの脆弱性の開示は、エージェント オーケストレーション フレームワーク、バックエンド サービング インフラストラクチャ、エンタープライズ AI ゲートウェイの 3 つの主要領域に集中していました。</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">エージェント オーケストレーションが主なチョークポイントに</strong><span style="vertical-align: baseline;">: オーケストレーション ミドルウェアは、AI 関連のすべての欠陥の 50% を占め、2026 年には開示件数が 347% 急増しています。ビジュアル ワークフロー ビルダー（Flowise、Langflow など）や自律型フレームワークは、環境とのやり取りを容易にするために、動的なコード実行ノードをデプロイすることがよくあります。攻撃者は、プロンプト インジェクションや細工されたワークフロー JSON を介してこれらのノードを悪用し、実行ループをハイジャックして、自然言語プロンプトを認証されていないリモートコード実行に変換します。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">一元化された AI ゲートウェイとクラウドのラテラル ムーブメント</strong><span style="vertical-align: baseline;">: 企業の AI ゲートウェイは、壊滅的な二重脅威ベクトルとなります。アプリケーション レイヤでは、侵害されたゲートウェイにより、サードパーティのアプリケーション プログラミング インターフェース（API）キーや、個人を特定できる情報（PII）または独自のソースコードを含むプライベート プロンプト ストリームが漏洩します。インフラストラクチャ レイヤでは、このようなゲートウェイが、攻撃者がデータベースの認証情報を収集し、内部のクラウド環境へのラテラル ムーブメントを行うための最初の足がかりとなります。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">新たな境界としての推論ゲートウェイ</strong><span style="vertical-align: baseline;">: バックエンド サービング インフラストラクチャ（vLLM、Triton、LiteLLM、Ollama など）全体で、2026 年に 212 件の脆弱性が開示されました。これらの欠陥の約 4 分の 1（24%）は、認証されていない API エンドポイントまたはサーバーサイド リクエスト フォージェリ（SSRF）に直接起因しています。これにより、リモートの攻撃者は、境界ファイアウォールをバイパスしたり、コストの高い GPU コンピューティング リソースを枯渇させたり、独自のモデル チェックポイントを抽出したりするための直接的なエントリ ポイントを得ることができます。</span></p>
</li>
</ul>
<h4><strong style="vertical-align: baseline;">AI ミドルウェアの実際の脆弱性悪用</strong></h4>
<p><span style="vertical-align: baseline;">AI インフラストラクチャのゼロデイ脆弱性の悪用はまだ確認されていませんが、脅威アクターは、公開されているミドルウェアで新たに開示された脆弱性を積極的に悪用しています。しかし、累積 2,076 件の開示のうち、実際に悪用されたことが確認されている脆弱性はごくわずかです。これらの事例の中で、脅威リスクが高いと評価され、認証されていない RCE、コマンド インジェクション、任意のファイル書き込みが行われるものをいくつか特定しました。</span></p>
<ol>
<li style="vertical-align: baseline;">
<p><a href="https://labs.cloudsecurityalliance.org/research/csa-research-note-litellm-cve-2026-42271-ai-gateway-exploita/" rel="noopener" target="_blank"><strong style="text-decoration: underline; vertical-align: baseline;">CVE-2026-42271（BerriAI LiteLLM）</strong></a><span style="vertical-align: baseline;">: Model Context Protocol（MCP）サーバーのプレビュー エンドポイント（</span><code style="vertical-align: baseline;">POST /mcp-rest/test/connection</code><span style="vertical-align: baseline;">）におけるコマンド インジェクションにより、ホストの乗っ取りや API 認証情報の盗難が行われます。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><a href="https://labs.cloudsecurityalliance.org/research/csa-research-note-langflow-cve-2026-5027-active-exploitation/" rel="noopener" target="_blank"><strong style="text-decoration: underline; vertical-align: baseline;">CVE-2026-5027（Langflow）</strong></a><span style="vertical-align: baseline;">: </span><code style="vertical-align: baseline;">POST /api/v2/files</code><span style="vertical-align: baseline;"> アップロード ハンドラにおけるパストラバーサル ファイルの書き込みにより、リモートの脅威アクターが不正なファイル（cron ジョブ、Secure Shell（SSH）キーなど）をホストにドロップできるようになります。</span></p>
</li>
<li style="vertical-align: baseline;">
<p><a href="https://www.cisa.gov/news-events/alerts/2025/05/05/cisa-adds-one-known-exploited-vulnerability-catalog" rel="noopener" target="_blank"><strong style="text-decoration: underline; vertical-align: baseline;">CVE-2025-3248（Langflow）</strong></a><span style="vertical-align: baseline;">: </span><code style="vertical-align: baseline;">/api/v1/validate/code</code><span style="vertical-align: baseline;"> で </span><code style="vertical-align: baseline;">exec()</code><span style="vertical-align: baseline;"> を介して認証されていない Python コードが挿入され、即時の RCE が可能になります。</span></p>
</li>
</ol>
<h4><strong style="vertical-align: baseline;">今後の展望</strong></h4>
<p><span style="vertical-align: baseline;">GTIG は、脆弱性の発見と悪用の割合が短中期的に増加し続ける可能性が高いと予測しています。</span><a href="https://cloud.google.com/blog/topics/threat-intelligence/ai-vulnerability-exploitation-initial-access"><span style="text-decoration: underline; vertical-align: baseline;">5 月の AI 脅威トラッカー</span></a><span style="vertical-align: baseline;">などの他の調査では、生成 AI で開発されたゼロデイ エクスプロイト スクリプトを所有する脅威アクターの最初の既知の事例を報告しました。実際の攻撃が実行される前の作戦計画段階で阻止されましたが、エクスプロイトの構造的アーティファクトを分析したところ、高い信頼度の LLM 生成マーカーが検出されました。</span><a href="https://cloud.google.com/blog/topics/threat-intelligence/from-prompting-to-autonomy-the-evolution-of-adversarial-ai"><span style="text-decoration: underline; vertical-align: baseline;">9 月の AI 脅威トラッカー</span></a><span style="vertical-align: baseline;">では、脅威アクターがリソースを共有し、エージェント型の脆弱性発見ツールのプロトタイプを作成していることを指摘しました。</span></p>
<p><span style="vertical-align: baseline;">AI によって強化された脆弱性発見と、AI インフラストラクチャおよびテクノロジーを標的とした脆弱性の両方について、一般公開されているデータはまだ初期段階にあります。それでも、AI が脆弱性の発見に貢献していることを示す兆候は現れ始めています。自律型リサーチ エージェントは、重要な攻撃対象領域を対象とするように指示された場合、重大度の高い欠陥を検出する優れた能力を発揮します。エージェント ワークフローは、複雑なセマンティック コードパスについて推論し、動的な証明ハーネスを合成することで、コア ライブラリやランタイムにおけるメモリ破損やロジック バイパスを特定することに優れています。これにより、高度な攻撃者が積極的に悪用しようとする欠陥の正確な種類が明らかになります。</span></p>
<p><span style="vertical-align: baseline;">脅威アクターが AI システムの脆弱性を実際に悪用し始めているため、組織は AI セキュリティを後回しにできません。この環境全体を保護するには、即時の封じ込め戦略、自律型エージェント ワークロードのサンドボックス化、リスクベースの脆弱性の管理の実装により、新たな境界を防御する必要があります。</span></p>

<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">※この投稿は米国時間 2026 年 10 月 3 日に、Google Cloud blog に</span><a href="https://cloud.google.com/blog/products/databases/spanner-queues-provide-native-transactional-messaging?e=48754805&amp;hl=en"><span style="text-decoration: underline; vertical-align: baseline;">投稿</span></a><span style="vertical-align: baseline;">されたものの抄訳です。</span></p>
<p><span style="vertical-align: baseline;">AI エージェントは、クエリに回答するだけでなく、自律的に払い戻しを行ったり、在庫を管理したり、複数ステップのハンドオフを実行したり、サブエージェントをオーケストレートしたりできます。これらは、複雑なエージェント型ワークフローのほんの一例です。そのため、多くの場合、エージェントは運用データベースで内部状態を維持しながら、別のメッセージング システムやイベントキュー システムを介して非同期アクションをディスパッチする必要があります。残念ながら、これらのアプリケーションを構築するチームにとって、commit ポイントが異なる 2 つのシステムを管理することは、エージェント システムにおけるトランザクションの一貫性を破壊することになります。</span></p>
<p><span style="vertical-align: baseline;">このたび、</span><a href="https://docs.cloud.google.com/spanner/docs/queues/queues-overview"><strong style="text-decoration: underline; vertical-align: baseline;">Spanner キュー</strong></a><span style="vertical-align: baseline;">の一般提供が開始されました。これは、Spanner に直接組み込まれたネイティブなトランザクション メッセージング機能です。Spanner キューは、信頼性の高いエージェント実行に特化して設計されており、メッセージの作成はトランザクションにおける単なる書き込み操作にすぎません。エージェントの状態変更と、意図したダウンストリーム アクションは、アトミックにまとめて commit されるか、完全に失敗します。</span></p>
<p><span style="vertical-align: baseline;">これを従来のアプローチと比較してみましょう。データベースの状態の更新は成功したものの、アクションのディスパッチが失敗した場合、AI エージェントは行動を決定したにもかかわらず、実際には実行されないという状態になります。メッセージのディスパッチが成功しても、状態トランザクションがロールバックされると、エージェントは無効な状態に基づいてアクションを実行します。非同期のマルチエージェント調整では、再試行、投機的実行、競合状態によってこれらの障害が増幅され、開発者は複雑なアウトボックス パターン、べき等性レイヤ、データ整合ワーカーを構築せざるを得なくなります。これは、エージェント アーキテクチャにおける信頼性担保のための大きな負担となります。</span></p>
<h4><strong style="vertical-align: baseline;">エージェント アーキテクチャの主な機能</strong></h4>
<p><span style="vertical-align: baseline;">Spanner キューは、インフラストラクチャのオーバーヘッドを発生させることなく、こうした複雑な非同期ワークフローをサポートするいくつかのコア機能を提供します。</span></p>
<p><strong style="vertical-align: baseline;">アトミックな「意思決定とアクション」のエンキュー。</strong><span style="vertical-align: baseline;">単一の Spanner 読み取り / 書き込みトランザクション内で、エージェントは内部メモリまたは状態テーブルを更新し、同時にピア エージェントへのタスクをエンキューできます。Spanner の厳格な直列化可能性とグローバルな外部整合性に支えられ、状態の変化と実行インテントは 1 つのアトミックな単位として commit されます。</span></p>
<p><strong style="vertical-align: baseline;">スケジュール実行と遅延実行。</strong><span style="vertical-align: baseline;">キュー メッセージは、commit 時にすぐにディスパッチすることも、将来の配信をスケジュールすることもできます。遅延再試行、スケジュールされたエージェント チェックイン、SLA エスカレーション タイマーなどのエージェント型パターンは、外部の cron スケジューラやポーリング インフラストラクチャを必要とせずに、メモリの更新とともにトランザクション的にエンキューできます。</span></p>
<p><strong style="vertical-align: baseline;">エージェント ワーカー向けのストリーミング SQL pull。</strong><span style="vertical-align: baseline;">自律型エージェントは、ストリーミング SQL 読み取りを使用してタスクを動的に取り込んで処理します。エージェント ランタイムは、受信タスクをストリーミングしながら、処理能力に空きができ次第それらを処理し、トランザクション内でタスクの完了を確認応答（ACK）することで、エンドツーエンドのタスク実行状態の信頼性を保証します。</span></p>
<p><strong style="vertical-align: baseline;">エピソード記憶の永続性とハンドオフ。</strong><span style="vertical-align: baseline;">エージェント メモリの更新（長期的なエピソードの要約、内省的な状態遷移、サブエージェント間のコンテキストのハンドオフなど）は、キューを介して非同期かつトランザクション的に永続化できます。これにより、リアルタイムのインタラクティブなターンをブロックすることなく、エージェントの内部メモリが実行履歴と完全に同期された状態に保たれます。</span></p>
<h4><strong style="vertical-align: baseline;">Spanner キューが自律型エージェントに不可欠な理由</strong></h4>
<p><strong style="vertical-align: baseline;">トランザクションによる exactly-once のエージェント実行: </strong><span style="vertical-align: baseline;">エージェントがツール呼び出しの結果を評価すると、状態の変更、推論の永続化、ダウンストリーム ツール呼び出しタスクが 1 つのトランザクションに保存されます。少なくとも 1 回の配信と、最大 1 回の ACK を保証することで、exactly-once の処理を実現できます。</span></p>
<p><strong style="vertical-align: baseline;">堅牢なマルチエージェント オーケストレーションとハンドオフ:</strong><span style="vertical-align: baseline;"> マルチエージェント システム（A2A）では、プライマリ エージェントからスペシャリスト エージェントへの状態のハンドオフは、永続的でトランザクション的に commit されたメッセージとして処理されます。スペシャリスト エージェント ワーカーは、エージェント間のやり取りの完全に監査可能なリネージを維持しながら、配信されたメッセージを受信します。</span></p>
<p><strong style="vertical-align: baseline;">ファースト クラスのタイムアウトと人間参加型ワークフロー:</strong><span style="vertical-align: baseline;"> エージェント ワークフローでは、人間の承認やスケジュールされたフォローアップのために一時停止が必要になることがよくあります。Spanner キューはタイムアウト管理をネイティブに処理します。単一のトランザクションが承認待ち状態を記録し、自動エスカレーション メッセージをスケジュールして、どちらか先にトリガーされた方の処理を確定させます。</span></p>
<p><strong style="vertical-align: baseline;">エージェント キューの SQL ネイティブなオブザーバビリティ:</strong><span style="vertical-align: baseline;"> 処理中のエージェント ワークロードの検査、タスク バックログのモニタリング、エージェント実行履歴の監査は、キューテーブルに対する標準 SQL クエリで実行できるため、中身の見えないメッセージストアのブラックボックス化を防ぐことができます。</span></p>
<h4><strong style="vertical-align: baseline;">エージェント ワークフローの先</strong></h4>
<p><span style="vertical-align: baseline;">AI エージェント以外にも、Spanner キューは、さまざまな従来のイベント ドリブン アーキテクチャに対応する柔軟な多目的メッセージング プラットフォームとして機能します。ソーシャル アプリケーションでのリアルタイムのアクティビティ フィードの強化、ニュース配信でのライブ情報の提供、小売業での注文処理と在庫ワークフローのオーケストレーション、金融サービスでの高スループットの非同期タスク処理とトランザクション通知の処理など、Spanner キューは、プライマリ データベース内での非同期メッセージ配信とトランザクション イベント ドリブン ワークフローのための堅牢な基盤を提供します。</span></p>
<h4><strong style="vertical-align: baseline;">仕組み: Spanner キューのトランザクション メカニズム</strong></h4>
<p><span style="vertical-align: baseline;">Spanner キューは Spanner のファースト クラスのリレーショナル構造として表されるため、使い慣れた GoogleSQL を使用してキューを定義、検査、管理できます。</span></p>
<p><strong style="vertical-align: baseline;">1. キューの定義とアトミックなエンキュー</strong></p>
<p><span style="vertical-align: baseline;">エージェントが顧客への払い戻しを承認すると、単一の ACID トランザクション内で Orders テーブルを更新し、OrderAgentTasks キューに実行タスクをディスパッチします。</span></p></div>

<p><span style="vertical-align: baseline;">ダウンストリーム エージェント ワーカーは、ストリーミング SQL 接続（ExecuteStreamingSql）経由で RECEIVE_&lt;QueueName&gt; テーブル値関数（TVF）を使用してタスクを消費します。Spanner はメッセージ リースを自動的に管理し、リースされたタスクごとに一意の SpannerLeaseToken と有効期限のタイムスタンプを返します。</span></p></div>

<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">ASSERT_ROWS_MODIFIED 1 を使用すると、リースの期限切れに伴う競合状態からシステムを保護できます。ネットワークの一時停止が原因でワーカーが停止し、リースが期限切れになった場合、別のワーカーがすでにタスクを処理して削除している可能性があります。停止したワーカーが再開してステートメントを実行しようとすると、ASSERT_ROWS_MODIFIED 1 は、キュー行がすでに存在しないことを検出し、ステートメント レベルのエラーをスローします。このエラーをキャッチしてトランザクションを中止することで、古いワーカーが新しいデータベースの状態を上書きするのを防ぎます。</span></p>
<h4><strong style="vertical-align: baseline;">Spanner 変更ストリームと Spanner キューの比較</strong></h4>
<p><span style="vertical-align: baseline;">Spanner の変更ストリームは、データベースのデータ変更（挿入、更新、削除）を準リアルタイムでキャプチャし、ダウンストリームの統合や監査に提供します。変更ストリームとキューはどちらも、アプリケーションがデータの変更を検知して処理できるようにするものですが、Spanner の変更ストリームは、継続的な変更データ キャプチャ（CDC）や、ダウンストリームの分析 / ストレージへのデータ ストリーミング向けに設計されています。一方、Spanner キューは、トランザクション タスクのオーケストレーション向けに明示的に設計されており、ネイティブ メッセージ リース、スケジュール配信、SQL ベースの pull、読み取り / 書き込みトランザクション内でのアトミックな確認応答をサポートしています。</span></p>
<h4><strong style="vertical-align: baseline;">使ってみる</strong></h4>
<p><span style="vertical-align: baseline;">Spanner は、リレーショナル、ハイブリッド検索、グラフ、Key-Value の機能を厳格なグローバル整合性の下で組み合わせ、エージェント データのための統合された基盤を提供します。Spanner キューは、エージェントが単一の統合プラットフォーム内でデータの推論からトランザクション アクションの実行にシームレスに移行できるようにすることで、エージェント ループを完成させます。Spanner キューの一般提供が開始されました。</span></p>

<h3><span style="vertical-align: baseline;">Token quotas vs. billing spend caps</span></h3>
<p><span style="vertical-align: baseline;">Token quotas aren't the only cost guardrail in Google Cloud.</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><a href="https://docs.cloud.google.com/bigquery/docs/control-genai-costs"><strong style="text-decoration: underline; vertical-align: baseline;">Token quotas (this feature)</strong></a><span style="vertical-align: baseline;"> are </span><span style="font-style: italic; vertical-align: baseline;">preventive</span><span style="vertical-align: baseline;"> and </span><span style="font-style: italic; vertical-align: baseline;">AI-specific</span><span style="vertical-align: baseline;">. BigQuery tracks token usage during query execution and stops work close to the limit, with separate limits per project and per user.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Cloud Billing </strong><a href="https://docs.cloud.google.com/billing/docs/how-to/budgets-spend-caps#eligible-services"><strong style="text-decoration: underline; vertical-align: baseline;">spend caps</strong></a><span style="vertical-align: baseline;"> operate on </span><span style="font-style: italic; vertical-align: baseline;">dollars</span><span style="vertical-align: baseline;"> at the project and service level and can automatically block usage when a threshold is reached. They're a broad, financial backstop rather than a precise usage control, and because enforcement is not instant, some overages are incurred.</span></p>
</li>
</ul>
<p><span style="vertical-align: baseline;">Use token quotas as your first line of defense for AI spend, and a spend cap as a project-wide safety net.</span></p>
<h3><span style="vertical-align: baseline;">How enforcement works</span></h3>
<p><span style="vertical-align: baseline;">Quotas are enforced by stopping work rather than letting a query run past your limit. A query is rejected up front with a </span><code style="vertical-align: baseline;">QuotaExceeded</code><span style="vertical-align: baseline;"> error only if a quota it needs is already exhausted. Otherwise, it starts, and if a quota runs out mid-query, BigQuery stops sending new LLM calls:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Functions that support </strong><code><strong style="vertical-align: baseline;">max_error_ratio</strong></code><span style="vertical-align: baseline;"> (such as </span><code style="vertical-align: baseline;">AI.IF</code><span style="vertical-align: baseline;">) return partial results if unprocessed rows stay within the ratio, and otherwise fail.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">General-purpose functions</strong><span style="vertical-align: baseline;"> (such as </span><code style="vertical-align: baseline;">AI.GENERATE</code><span style="vertical-align: baseline;">) still succeed. Skipped rows have no generated value, and their </span><code style="vertical-align: baseline;">status</code><span style="vertical-align: baseline;"> field contains the quota-exceeded error.</span></p>
</li>
</ul>
<p><span style="vertical-align: baseline;">For details, see </span><a href="https://docs.cloud.google.com/bigquery/docs/control-genai-costs#quota_enforcement_behavior"><span style="text-decoration: underline; vertical-align: baseline;">quota enforcement behavior</span></a><span style="vertical-align: baseline;"> in the documentation.</span></p>
<h3><span style="vertical-align: baseline;">Sizing your input data: </span><code style="vertical-align: baseline;">AI.COUNT_TOKENS</code></h3>
<p><span style="vertical-align: baseline;">To choose quota values, it helps to know how much text your workloads send to a model. The </span><a href="https://docs.cloud.google.com/bigquery/docs/reference/standard-sql/bigqueryml-syntax-ai-count-tokens"><code style="text-decoration: underline; vertical-align: baseline;">AI.COUNT_TOKENS</code></a><span style="vertical-align: baseline;"> function helps with this.</span></p>
<p><code style="vertical-align: baseline;">AI.COUNT_TOKENS</code><span style="vertical-align: baseline;"> returns the number of tokens a model's tokenizer produces for a text string, without making a billable generation call. Run it over a column to measure your input data:</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &quot;-- Count the input text tokens for each product review\r\nSELECT\r\n  SUM(\r\n    AI.COUNT_TOKENS(\r\n      CONCAT(&#x27;Classify the sentiment of this review as positive, negative, or neutral: &#x27;, review_text),\r\n\r\n      endpoint =&gt; &#x27;gemini-3.1-flash-lite&#x27;).result) AS total_input_tokens\r\nFROM\r\n  `my_project.my_dataset.product_reviews`;&quot;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f445b622b10&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">The count is a lower bound on input tokens. It doesn't include output or thinking tokens, the instructions each AI function adds around your input, or non-text inputs such as images. Use it to:</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Gauge the input side of a workload</strong><span style="vertical-align: baseline;"> before you launch it.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Right-size your quotas</strong><span style="vertical-align: baseline;"> together with a small sample run that measures actual input and output usage.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Translate tokens into dollars</strong><span style="vertical-align: baseline;"> using the published </span><a href="https://cloud.google.com/vertex-ai/generative-ai/pricing"><span style="text-decoration: underline; vertical-align: baseline;">Gemini platform pricing</span></a><span style="vertical-align: baseline;"> for your model.</span></p>
</li>
</ul>
<h3><span style="vertical-align: baseline;">From tokens to budget: a worked example</span></h3>
<p><span style="vertical-align: baseline;">Suppose you want to keep a project's daily AI spend around </span><strong style="vertical-align: baseline;">$100</strong><span style="vertical-align: baseline;"> with the </span><a href="https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-1-flash-lite"><span style="text-decoration: underline; vertical-align: baseline;">Gemini 3.1 Flash-Lite</span></a><span style="vertical-align: baseline;"> model. As of today's published pricing (BigQuery processes in batch which provides a 50% discount):</span></p>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Input tokens:</strong><span style="vertical-align: baseline;"> $0.125 per 1 million tokens</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Output tokens (response + reasoning):</strong><span style="vertical-align: baseline;"> $0.75 per 1 million tokens</span></p>
</li>
</ul>
<p><span style="vertical-align: baseline;">If a small sample run shows an average </span><strong style="vertical-align: baseline;">100:1 input-to-output token ratio</strong><span style="vertical-align: baseline;">, you can solve for a daily budget:</span></p></div>
<div class="block-code"><dl>
    <dt>code_block</dt>
    <dd>&lt;ListValue: [StructValue([(&#x27;code&#x27;, &#x27;Cost:   0.125 × I + 0.75 × O = 100     (I, O in millions of tokens)\r\nRatio:  I = 100 × O&#x27;), (&#x27;language&#x27;, &#x27;&#x27;), (&#x27;caption&#x27;, &lt;wagtail.rich_text.RichText object at 0x7f445ae5cf10&gt;)])]&gt;</dd>
</dl></div>
<div class="block-paragraph_advanced"><p><span style="vertical-align: baseline;">Solving gives about </span><strong style="vertical-align: baseline;">754 million input tokens</strong><span style="vertical-align: baseline;"> and </span><strong style="vertical-align: baseline;">7.54 million output tokens</strong><span style="vertical-align: baseline;"> per day. Set </span><strong style="vertical-align: baseline;">AI input tokens per day</strong><span style="vertical-align: baseline;"> and </span><strong style="vertical-align: baseline;">AI output tokens per day</strong><span style="vertical-align: baseline;"> to these values to hold the project near $100/day. If a project uses models with different prices, budget per model or blend the rates.</span></p>
<h3><span style="vertical-align: baseline;">Best practices for managing AI cost</span></h3>
<ul>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Start with per-user quotas.</strong><span style="vertical-align: baseline;"> They stop one user or runaway experiment from draining the project's budget.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Measure before you scale.</strong><span style="vertical-align: baseline;"> Use </span><code style="vertical-align: baseline;">AI.COUNT_TOKENS</code><span style="vertical-align: baseline;"> to size your input, then check a small sample run in the usage chart before setting limits.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Mind the output side.</strong><span style="vertical-align: baseline;"> Output tokens cost more. Where a function accepts </span><code style="vertical-align: baseline;">max_output_tokens</code><span style="vertical-align: baseline;">, set it to bound generation length.</span></p>
</li>
<li style="vertical-align: baseline;">
<p><strong style="vertical-align: baseline;">Monitor and iterate.</strong><span style="vertical-align: baseline;"> Adjust limits as real usage and budgets change.</span></p>
</li>
</ul>
